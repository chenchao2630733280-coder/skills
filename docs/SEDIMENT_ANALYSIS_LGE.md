## 0. 一句话结论

**LGE 的可迁移价值不在"生成算法"，而在六条与机制无关的判定纪律。**
生成算法本体（反向剥离、切轴、填盘拓扑、DFS 求解器、PNG 解析）强绑定「拼豆-线轴」拓扑，搬运即过拟合；
但这套引擎在**打通流程的过程中被迫回答的六个问题**——"分数刻度用满了吗""这关是不是天生不可能输""修复会不会把难度买光""这个判据是必要的还是充分的""这个旋钮还有效吗""这次提速是真账吗"——每一个都能直接落成检查项。

其中 **D1（维度区分度自检）和 D2（结构性必赢判据）是 `game-level-design` 的真空缺**：现有实现会报"参数离群"，但不会报"这个维度全战役恒定/顶格/只用了一半刻度"，也不会报"这关的槽位已经 ≥ 色数，难度分再高也是假的"。这两条是本次分析的主产出。

## 3. D1 量尺自检 ⭐ 最高价值

### 3.1 来源与现象

LGE 第一版难度分五个维度，分母是"拍脑袋的理论极值"。100 关实测（`probe_score.mjs`）直接打在脸上：

```
维度            p10   p50   p90   max   诊断
slotPressure   0.00  0.48  0.71  0.79
buryDepth      0.22  0.33  0.44  0.56   ← 天花板 0.56，分母过大
parallel       0.00  0.29  0.50  0.70
waitCost       0.00  0.17  0.67  1.00   ← 中位 0.17，八成关卡几乎拿不到分
punish         0.00  0.38  1.00  1.00   ← p90 就顶格，没有区分度
peekFill       0.75  1.00  1.00  1.00   ← 中位 1.00，恒定
加权总分 max 65 → 5★ 永远够不着
```

三种病一次全暴露：**分母过大**（刻度只用了 56%）、**分母过小**（p90 就顶格）、**指标恒定**（中位=最大值，等于给所有关加同一个常数）。
修法是"分母对齐实测 p90"，并把恒定的 `peekFill` 从**加分项改成减分项**（填不满说明槽位一直有余量，应当更简单——**符号反了，怎么标定都救不回来**）。

星级也随之从 `round(total/20)` 改成**固定阈值**（`≥78` 5★ / `≥62` 4★ / `≥46` 3★ / `≥30` 2★）。理由一句话：

> `round(total/20)` 假设分数在 0~100 均匀分布，而实测是集中在 30~70 的正态；那样切出来所有关都落在 2~3★——**这正是第一版"只用到一半"的直接原因**。

### 3.2 与现有 skill 的差距（已核实）

```
game-level-design/tools/cdl/score.py   只有 score_features / top_dimensions / load_shift
game-level-design/tools/cdl/diagnose.py  _param_cv() 算的是「参数级」CV，不是「维度级」分布
grep p50|p90|percentile|calibrat        仅 calibrate.py（逻辑回归基线），无分布自检
```

也就是说：**参数可以剧烈变化，而它映射到的维度贡献始终是常数，现有实现看不出来。** 反过来，维度可以恒定，而参数看着很健康。缺的是维度级的那张表。

### 3.3 建议改动

**新增 `tools/cdl/dist.py`**（纯函数，不引入依赖）：

```python
def dim_profile(campaign, weights=None) -> dict:
    """每个维度的 p10/p50/p90/max/std，以及贡献占比。全战役一次算完。"""
def diagnose_scale(profile, star_thresholds) -> list:
    """返回 DIM_UNDERUSED / DIM_SATURATED / DIM_CONSTANT / STAR_UNREACHABLE 四类告警。"""
```

判据（保守取值，宁可漏报不要误报）：

| 条件 | 异常码 | 含义 |
|---|---|---|
| `p90 <= 0.35 and max <= 0.5` | `DIM_UNDERUSED` | 分母过大，刻度浪费（对标 `buryDepth` 0.56） |
| `p10 >= 0.90` | `DIM_SATURATED` | 顶格，无区分度（对标 `punish` p90=1.00） |
| `p50 >= 0.99`（或全体同值） | `DIM_CONSTANT` | 恒定，等于给所有关同样的分（对标 `peekFill`） |
| `max_total < star_thresholds[4]` | `STAR_UNREACHABLE` | 加权上限够不到 5★（对标"max 65 → 5★ 永远够不着"） |

**报告新增一节 `D0 量尺自检`**，放在现有诊断之前——因为量尺坏了，后面的 CLIFF/DIP/OVERLOAD 全是噪声。这一节失败时，报告顶部应显式写「**本报告的异常结论可信度下降**」，而不是照常输出 10 条 HIGH。

**`schema.py` 的 `DEFAULT_WEIGHTS` 加来源注释**：每个权重与分母必须写清是"实测 p90 标定"还是"设计意图"。现在 8 个权重只有数值，没有出处，下一个维护者无法判断能不能动。

> 与既有机制的关系：这条与 `CONFIG_OUTLIER`（参数离群）**正交**，不替换它——一个查输入，一个查量尺。

## 4. D2 结构性必赢判据 ⭐

### 4.1 来源与现象

`LEVEL_REBUILD_AUDIT.md` 里最刺眼的一行：

| 指标 | 实测 | 判读 |
|---|---|---|
| 槽/色 | 0.79（**前 20 关有 18 关 = 1.00**） | 槽位 ≥ 色数 ⇒ 按 §1.1 的证明，**数学上不可能输** |

以及同一文档 §3 的三处结构修正之二：

> **降级只动色数、不动槽位。** 一开始按"加槽"降级，L10 变成 6 色 6 槽、L21 变成 7 色 7 槽——可解了，但**难度被买光**（槽 ≥ 色数 = 数学上不可能输）。

这是两个方向相反的事实叠在一起：

1. **有一类参数关系一旦成立，"输"在数学上就不可能**，此时难度分再高也是假的——它描述的是一个不存在的事件。
2. **修"不可解"的标准手段（加槽）恰好会制造"不可输"**。梯子往上爬，爬到顶就是悬崖。

现有 `game-level-design` 只有统计信号能碰到这件事：`BAND_MISS`（实际首通率偏离目标带）、`DIP`、`PLATEAU`。它们都说"偏低"，但都需要**真实数据**才能触发；而 D2 是**结构性判据，读配置即可判定，零数据也能报**。

### 4.2 建议改动

**(a) 让 campaign 可以声明"支配关系"**（纯声明式，不做表达式求值，避免注入与解析风险）：

```json
{
  "meta": { "name": "demo" },
  "dominance": [
    { "lhs": "slotMax", "op": ">=", "rhs": "colors",
      "means": "槽位不少于颜色数 ⇒ 每种颜色都能独占一槽，数学上不可能输" }
  ],
  "levels": [ ... ]
}
```

**(b) `diagnose.py` 新增 `TRIVIAL_BY_CONSTRUCTION`**：逐关检查 `dominance` 关系，成立即报（severity `HIGH`，`meta` 带 lhs/rhs 实际值）。没有 `dominance` 声明时不报，保持向后兼容。

**(c) `recommend.py` 加护栏（这是最关键的一步）**：任何推荐 option，若执行后会让某条 `dominance` 关系**从不成立变为成立**，直接丢弃并在报告里记一行 `REJECTED_WOULD_TRIVIALIZE`。等价于把"不许把难度买光"从一句文档里的告诫变成过滤器。

**(d) 分类表补一条**：`references/10_jump_and_anomaly_taxonomy.md` 的异常族里加 `TRIVIAL_BY_CONSTRUCTION`，并写明它与 `BAND_MISS` 的分工：

| 异常 | 判据来源 | 触发条件 | 什么时候能发现 |
|---|---|---|---|
| `BAND_MISS` | 数据 | 实测首通率偏离 `target_win` 超容差 | 有真实数据之后 |
| `TRIVIAL_BY_CONSTRUCTION` | 结构 | 参数关系使"输"不可能 | **读配置即可**，上线前 |

**(e) 顺带补一条"反向阶梯"**：现有公平修复阶梯解决"太难过"，D2 暴露的"太易过"需要相反方向——减槽 / 增色 / 增干扰。两者必须在同一份文档里成对出现，否则维护者只会记得"难了就加槽"。

> 这条与 `resource_pressure` 维度的关系：后者是**连续量**（槽位少 → 压力大），D2 是**开关量**（越过某条线，压力这个维度失去意义）。连续量永远表达不出开关，所以必须单独立项。

## 5. D3 修复阶梯：代价序 + 取最优 + 不许买光

### 5.1 来源

LGE §10 的阶梯是 **A 加槽 → B 平滑 → C 降色**，代价升序，且"加槽是最后手段"。落地数据：

- 42 关需要上调 `slotMax`，其中 **15 关顶到 7 槽上限**（`slotMax` 的合法区间到顶了）；
- "+1 槽均值 3.00 vs 不加 2.22"——加槽确实有效，但**每一档都是买来的**；
- 最终妥协分布：原样 54 / 加槽 36 / 平滑 9 / 降色 1。

`LEVEL_REBUILD_AUDIT.md` §3 还有一条更狠的：

> 3. **可解性裁判换成 `human`。** `look` 输在"同色叠槽"，不代表关卡无解……现在只有 `human` 也打不过才降级。

**裁判选错，会误杀三分之二的可解关**（详见 D5）。

### 5.2 与现有 skill 的差距

`recommend.py` 已经做得不错：单变量、`legal_ranges`、`max_delta`、≤25% 增量、`UNSTABLE` 时禁用随机旋钮、多 scope（对齐邻近/备选）。**缺的是三件事**：

1. **没有"阶梯"概念**——options 是平铺的，没有"先试便宜的，不行再试贵的"的顺序语义；
2. **没有"取最优"**——按首个通过公平闸的解返回，而 LGE 明说"阶梯停在槽 6 就能打通，于是贪大手速只有 10/6（目标 15）"，即**首个可行解往往不是想要的那一档**；
3. **没有和 D2 的护栏联动**（见 4.2c）。

### 5.3 建议

`references/11_recommendation_engine.md` 加一节「阶梯式修复」，并在 `recommend.py` 的 option 上加两个字段：

| 字段 | 取值 | 用途 |
|---|---|---|
| `cost_rank` | 1/2/3（便宜→贵） | 报告里按阶梯分组，而不是按 delta 排序 |
| `expected_star` | float 或 null | 有模拟数据时给出"修完预计几星"，用于"取最高星" |

规则三句话：

- **同一关卡的首选建议必须是 `cost_rank` 最小且通过公平闸的那一档**；
- 若存在多个可行档，**报告主推 `expected_star` 最高的一档**，其余降级为"备选（更省但更弱）"；
- **任何档位都过不了 D2 护栏的，直接不出现在报告里**。

## 6. D4 旋钮失效信号

### 6.1 来源

LGE §10 里有一个被明确命名的**结构性信号**：

> **但有个结构性信号：15 关顶到了 7 槽上限。**

这句话的含义不是"这 15 关还没修好"，而是"**`slotMax` 这个旋钮对这 15 关已经失效了**"——继续在 `legal_ranges` 里找更大的值是无意义的，必须换旋钮（降色 / 改画稿 / 换机制档位）。

`LEVEL_REBUILD_AUDIT.md` §4.4 遗留清单里的 L86/L99 是同一个信号的表现：

> 两关都是「槽 5、6 死锁 → 槽 7 才活」的悬崖，阶梯停在槽 6 就能打通，于是贪大手速只有 10 / 6……想更硬只能重跑并手工挑槽 7 那一档。

### 6.2 建议

`recommend.py` 增加一个批次级判定：统计每个参数"被推荐到 `legal_ranges` 上界"的次数，超过阈值（例如 ≥ 20% 的关卡，或任一关卡已被顶到上界且仍 `BLOCKER`）时，输出 `KNOB_EXHAUSTED`：

```
KNOB_EXHAUSTED  slotMax  15/42 关已顶到上界 7.0
  → 该旋钮在本批次已失效；继续加槽只会把难度买光（见 TRIVIAL_BY_CONSTRUCTION）
  → 建议换旋钮：colors（降色）/ smooth_window / 机制档位
```

这条的价值在于**它把"数据异常"翻译成了"设计动作"**。现有报告会告诉你"L07 有 blocker"，但不会告诉你"你手上的旋钮已经用完了"。

## 7. D5 判据类型分层（对门禁设计的贡献）

### 7.1 来源：LGE §4 的三级闸门

| 级 | 判据 | 成本 | 通过含义 |
|---|---|---|---|
| L0 | `validateLevel` 六条 + 开局可点 | <1ms | 能进游戏 |
| L1 | `lookSafe ≤ 上限`、`human` 赢 | 5~40ms | 公平 + 有解（**充分**） |
| L2 | DFS `solvable === true` | 50~2500ms | 灰区确认 |

关键实证（这是全篇最有价值的单条结论）：

- **`human` 赢 ⇒ 一定可解**（34/34，零反例）——这是**充分判据**，命中即免掉 DFS，且不会误判；
- **`human` 输 ≠ 无解**（34 个输的里 21 个其实有解，62%）——这是**不充分的**，拿它当闸门会误杀三分之二；
- 灰区只剩 5.9%，且**这 5.9% 是硬成本，靠加固验证解决不了**。

还有一个反直觉的收尾（§15）：

> 全量回归 100 关 闸门阶段 L1×100，**L2 触发 0 次**……**L2 是条冷路径，不在吞吐的关键路径上。**

即：把最贵的判定优化得再好，它根本不跑。

### 7.2 建议

`game-quality-gate/references/` 增加一个约定，每个检查项（G25-0x / 3.28 之类）除现有字段外，标注：

| 字段 | 取值 | 为什么需要 |
|---|---|---|
| `判据类型` | 必要 / 充分 / 精确 | 决定能不能"命中即放行"，以及跳过它时是"漏判"还是"误判" |
| `单次耗时` | <10ms / 10ms~1s / >1s | 决定放在哪一层跑 |
| `不可判定率` | 百分比（可空） | 精确判定的真实覆盖率；没有这个数，跳过就是赌 |

三条规则：

1. **充分判据放前面，命中即放行**（省掉最贵的那层，且零误判风险）；
2. **精确判定只在"必要判据通过 + 充分判据未命中"的灰区开**，并报不可判定率；
3. **轻量模式/降级（`SIM_SKIPPED → PASS_LIGHT` 那类）必须写明降的是"精确"还是"必要"**。降必要判据是**漏判放大**，降精确判定只是**多一次人工复核**——这两件事现在在文档里长得一样。

`skill-auditor` 的"判据覆盖面"维度加一问：**这个检查是充分条件还是必要条件？漏判/误判各是多少？** 多数门禁文档答不上来，答不上来本身就是发现。

## 8. D6 归因三条（并入主文档 P1-1）

三条都是"数据比直觉狠"的实例，与主文档 P1-1（静默假绿三件套）同族，建议合并而非另立条目。

**(1) 假提速。** 并行化后看到 35.3s → 3.9s（9x），实际是假账：

> 那 9x 是假账——旧版 `verify_all.mjs` 每关除了 `generateLevel` 还额外调了一次 `evaluate()`……**那 4 倍是删重复计算，不是并行。真实并行收益是 2.4x。**

判据：**性能收益必须单变量归因**——改并行前后都要有"单线程基线重测"，且基线里不能顺手删重复计算。两件事混在一次提交里，收益就永远说不清。

**(2) 优化错对象。** 为了"提前 cut"试了四种加速（charCode 指纹 / 写时复制 / 干等轴剪枝 / beam 先试解），**全部零收益，全部撤掉**；因为瓶颈根本不在那个函数——L2 触发 0 次。

判据：**优化前先证明该路径会被执行**（插个计数器，别猜）。这条恰好是"先测瓶颈再优化"的可执行版本。

**(3) 先证伪上游。** 复盘到一半准备"全部重新生成 100 幅画"，把原画稿渲染出来之后推翻了：

> 原画稿本来就有 8~12 色、有月/星/村舍窗灯/花瓶四朵花。**画得糙的是 `_redesign_levels` 的重采样与降色，不是画师。**

判据：**归因到上游之前，先把上游产物打出来看一眼**。代价是 `view` 一张图，收益是省掉一个"重画 100 幅"的错误决策。

同族还有 `LEVEL_REBUILD_AUDIT.md` §4.5：用户三条抱怨（没打散 / 线量都没变化 / 可点区域太小）对应**三个互不相干的根因**，文档明写"不是'再调调参数'能一起解决的"。→ **用户抱怨要逐条拆根因，禁止合并成一次调参。**
