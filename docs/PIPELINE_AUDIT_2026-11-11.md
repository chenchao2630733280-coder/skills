## 4 方法说明：为什么 § 引用没有全自动化

脚本第一版会报出 40+ 条"§x.y 引用无对应标题"，人工核对后**绝大多数是误报**，原因有三：

1. 同一个文件里并存两套编号——**SKILL 自身章节**（`## 八、`）与**它要产出的文档章节**（`ART_SPEC §13`）；
2. 跨文件引用常省略文档名（"见 §2.6"其实指 `AUDIO_SPEC` §2.6）；
3. 中文序号与阿拉伯序号混用，"§8" 与 "§八" 可能指不同东西。

所以脚本保留该检查但只做**同文件内**的窄判定，真实校验靠人工按"最近改过编号的文件"定向抽查
（本轮抽查 `game-teardown` 的 §8.x 重编号后引用，发现并修掉了 P1-3）。

工具本身留在 `_shared/audit_pipeline.py`，可重复跑：

```bash
python _shared/audit_pipeline.py
```

### 5.1 描述超限：31 是错的，实际 39

原报告说 31 个，是因为 `audit_stats.py` 只认单行 `description: "…"`。
有 8 个 skill 把描述写成了折叠块（`description: >`）或跨行续写，解析不到就当成了 `desc=-1`（不超限），
于是**统计上"合规"、实际超限**。这类"假绿"正是流水线一直在防的同一个毛病，只是这次出在审计工具自己身上。

处置：
- `_shared/audit_stats.py` 重写 frontmatter 解析，三种写法（单行引号 / 折叠字面 / 无引号续行）都认；
- `_shared/shorten_descriptions.py` 批量改写，39 个全部降到 ≤200（最长 200，最短 82）；
- 改写保留「做什么 + 何时用」结构和原触发词，不动 frontmatter 其他字段。

两个坑，都已固化进脚本：

1. **frontmatter 收尾 `---` 会被当成续行吞掉**。第一版按"遇到新顶层 key 才停"判定字段边界，
   `---` 既不是 key 也不是空行，被并进 description 一起删了 —— 38 个文件的 frontmatter 直接失效，
   而脚本自己不报错。发现方式：改完复查，8 个文件变成 `desc=-1`。
   修法：`---` 作硬边界；且回写前用 `sanity()` 重新解析一遍，值对不上就拒写。
2. **CRLF**。按 `_shared/README.md` 的规矩，先按原 EOL 切行、只在行体上匹配、回写保留原终止符。

### 5.2 顺带查出的真问题：`G25-07` 一码两用

`audit_pipeline.py` 的 D 项报 `G25-07` 出现两次。核对后是**两个不同的检查共用了一个码**：

- 2.5.7「门禁结论可解释」（表格里的正式定义）
- 防作弊段「阈值被静默放宽且未记录理由」（正文里借用了同一个码）

第二条是本轮新增防作弊规则时借码写的，会让"阈值被放宽"和"结论解释不清"在报告里无法区分。
已拆为 **2.5.12 / `G25-12`**，并在 L2 表里补成独立行（条件触发，未做跨版本对比时记
`THRESHOLD_BASELINE_MISSING` WARNING 而不是默认通过）。失败码总数 76 → 77。

同时修了 D 项自己的判定口径：原来"同一个码出现 >1 次"就算重复，把
「表格定义 + 正文交叉引用」误判成重复（`G25-12` 干净了却仍报红）。
现在把**表格行**当作定义、正文只算引用，并新增 `DANGLING`（引用了但没定义）检查 —— 改完 clean。

### 5.3 两个短剧 skill 超 500 行：不改，转独立任务

`ai-short-drama-project-development`（1054）/ `ai-short-drama-topic-planner`（1245）。

不做的理由：

1. **不是清理，是重排版**。要落到 500 行以内，得搬走 550~750 行，等于把这两个 skill 从
   "自带全部手册"改成"路由 + 若干 reference"，是结构改造而不是修数字。
2. **它们是外部包**，不在 game 流水线上，改坏了没人从流水线侧发现。
3. **有拆的前提条件没满足**：`ai-short-drama-topic-planner` 的 `references/` 下已有
   `trend-radar.md`、`diversity-engine.md`、`scoring-model.md`、`viewing-motivation.md` 共 170 行，
   但 **SKILL.md 一次都没提过它们**（`grep references/` 无结果）—— 现状是正文内联了更全的版本、
   reference 成了孤儿。所以先要裁决"以内联为准还是以 reference 为准"，删掉重复的那一份，
   再谈搬迁。这一步需要原作者意图，不该由审计脚本替它决定。

建议做法（留给独立任务）：先比对正文与同主题 reference 的差集 → 保留信息量大的那份 →
SKILL.md 只留"阶段骨架 + 检查点 + 指针"，细节按主题进 `references/`，并在开头给一张
"读哪一份"的索引表。

### 5.4 ISSUE-015（master / gate 压到 ≤300 行）：改判为不压

原判据站不住：

1. **500 行才是硬线**，两者是 443 / 441，本来就合规。≤300 是本轮自己提的加分项，不是规则。
2. **压到 300 的代价正好撞上本流水线的核心原则**。`game-quality-gate` 的 65 个检查判据、
   `game-forge-master` 的阶段裁剪表与引擎决策表，都是**执行那一刻必须当场看见**的东西。
   搬进 `references/` 后，agent 少读一步就等于**静默放行** —— 这正是"静默假绿"这一族问题
   （见 `docs/SEDIMENT_CAPABILITY_MAP.md`）最典型的触发方式。
   一份"短但会把判据藏起来"的门禁，比一份"长但判据就在眼前"的门禁更危险。
3. 真要缩，正确方向是**减少判据条数**（合并同类检查项），而不是把判据挪走。那属于门禁设计，
   需要逐条评估漏检风险，不该混在格式清理里做。

结论：ISSUE-015 关闭，理由记在这里，避免下一轮又被当成待办重新提出来。
`validate.ps1` 第 14 项继续按 500 行硬线告警。
