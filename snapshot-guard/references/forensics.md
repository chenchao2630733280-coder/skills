# 外部改写取证速查

## 一、差异形态判读表

拿到「磁盘 vs 快照」的差异文件后，先判**性质**，再决定处置。

| 形态 | 特征 | 典型元凶 | 处置 |
|---|---|---|---|
| **同长度重排** | 字节数接近、行数不变、多处空白/对齐不同 | 编辑器格式化（markdown 表格、缩进、行尾） | 若不影响语义规范：可接受并重刷快照；否则还原 |
| **内容回退** | 命中「本轮已改掉的旧词」 | 编辑器陈旧缓冲区回写 / 外部脚本用旧副本覆盖 | **必须还原**（这是真丢改动） |
| **回退 + 重排** | 上述两者叠加 | 同时格式化 + 缓存旧内容 | **必须还原**；格式化变更是否保留由需求方定 |
| **新增内容** | 行数/字节数明显增加，出现快照里没有的段落 | 其他会话/协作者写入、生成器重跑 | 需要判定是「合法的外部产出」还是污染 |
| **瞬时写回（自愈型）** | 首跑报差异、**复跑即自愈**；行级 diff = 0 行、归一化换行后逐字节一致 | 编辑器/外部工具写入后数秒内又写回 | **先复跑确认差异仍在再进还原流程**；对自愈型只记档，勿还原（还原瞬间可能覆盖正在写入的会话） |
| **文件缺失** | 磁盘上没有 | 被删除/移动 | 从快照还原 |
| **文件多出** | 快照里没有 | 新增产物或临时文件 | 判定是否应纳入快照 |

**快速判据**：

```
行数不变 + 旧词回退 + 空白重排   ⇒ 格式化工具 + 陈旧缓存 回写（最常见）
字节数增加 > 行数               ⇒ 有新增内容，不是纯重排
字节数减少 ≈ 行数               ⇒ 仅行尾从 CRLF 归一化为 LF（不是内容丢失）
首跑差异 + 复跑自愈 + 行级 diff 0 行 ⇒ 瞬时写回（只记档，勿还原）
```

## 二、mtime 时序定位法

```python
import os, time, zipfile

snap_mtime = os.path.getmtime('current.zip')
print('快照时间:', time.strftime('%H:%M:%S', time.localtime(snap_mtime)))

rows = []
for root, dirs, files in os.walk('.'):
    dirs[:] = [d for d in dirs if d not in ('.git', 'node_modules', '__pycache__')]
    for f in files:
        p = os.path.join(root, f)
        m = os.path.getmtime(p)
        if m > snap_mtime:
            rows.append((m, p))
rows.sort()
for m, p in rows:
    print(time.strftime('%H:%M:%S', time.localtime(m)), p)
```

**判读**：列出来的文件 = 「快照之后被动过的候选」。再与「本轮预期改动的文件清单」求差：

- 在预期清单里 ⇒ 正常，忽略。
- **不在预期清单里 ⇒ 外部改写，进入取证流程。**

这个方法能把排查范围从「全项目」缩到「一两个文件」，是本 skill 最实用的技巧。

## 三、常见元凶（按概率）

1. **编辑器自动格式化 / 保存格式化**（markdown 表格对齐、缩进、行尾）—— 最高频。
2. **编辑器持有陈旧缓冲区**：改动由脚本完成，但编辑器里还是旧内容，一保存就覆盖回去。
3. **其他会话 / 其他 agent 并行写同一目录**。
4. **生成器重跑**：构建脚本用旧输入重新生成产物。
5. **同步/备份工具**：网盘、IDE 插件做了「恢复」操作。
6. **行尾或编码被工具链归一化**（这类表面看像内容变化，实际是格式变化）。

## 四、处置决策树

```
差异只在「格式」且符合项目规范？
├─ 是 → 记录到报告 → 重刷 current.zip → 继续
└─ 否 → 是「内容回退」或「非预期新增」？
        ├─ 是 → 备份现场（.txt 后缀）→ read+write 还原 → 复跑门禁 → 重刷 current.zip
        └─ 否 → 交需求方判定（可能是合法的外部产出）
```

## 五、预防措施（比取证更值钱）

| 措施 | 说明 |
|---|---|
| **收工即比对** | 每轮收工重建 `current.zip` 并跑一次 `snapshot_diff`，让「磁盘 == 快照」成为常态 |
| **关掉保存自动格式化** | 对交付物目录禁用编辑器的 format-on-save；格式由脚本统一处理 |
| **不要把交付物长期开在编辑器里** | 尤其是会被脚本批量改写的文件 |
| **改动只走脚本** | 用落盘脚本批量改（见 `batch-rewrite-surgery`），避免手工多文件编辑 |
| **改完立刻重比** | 脚本落盘后立刻比对，能第一时间发现「改完又被改回去」 |
| **归档与交付物分离** | 归档目录不进 `current.zip`，避免「归档被改」被误报为交付物差异 |

## 六、报告模板（`snapshot-guard-report.md`）

```markdown
# 快照取证报告

- 基准快照：current.zip（YYYY-MM-DD HH:MM:SS，NN 文件）
- 比对结论：不一致 1 处（71/72 一致）
- 快照时间 14:32:42 / 差异文件 mtime 14:35:46（晚 3 分 04 秒）

## 差异清单
| 文件 | 磁盘 | 快照 | 首个差异@ | 性质 |
|---|---|---|---|---|
| path/to/file | 170491 B | 169319 B | 3378 | 内容回退 + 表格重排 |

## 性质判定
- 行数不变（3265 → 3265），无新增内容
- 命中 19 处「本轮已改掉的旧词」
- 23 个差异块，均为表格空白重排
⇒ 判定：外部格式化工具 + 陈旧缓冲区回写

## 处置
1. 现场保全 → `_forensic_<file>_<HHMM>.txt`（170491 B / md5 ...）
2. read + write 还原（未用 extractall）
3. 复跑比对：72/72 ✅
4. 复跑门禁：全绿
5. 重建 current.zip

## 预防
- 对交付物目录关闭保存自动格式化
- 收工流程固定加一步 snapshot_diff
```
