# Game Blueprint — 游戏蓝图生成

本 skill 是 AI 游戏生成流水线的**阶段 1**,职责是把用户的一句话需求扩展成一份一页纸的游戏蓝图,作为后续 PRD/技术设计/美术规范的总纲。

---

## 一、输入与输出

**输入**:
- 用户一句话需求(如"做一个新春赛马跑酷小游戏,带皮肤和抽奖")
- 可选:用户提供的参考游戏名/截图/已有素材
- **复刻模式(若存在)**:`docs/GAME_TEARDOWN.md` §0 摘要 + `docs/TEARDOWN_MATRIX.json`(由 game-teardown 产出)。检测到该文件即视为复刻需求,按 §三.0 处理,不得忽略

**输出**(固定路径,1 份文档):
- `docs/GAME_BLUEPRINT.md`

## 三、生成规则

### 0. 复刻模式(存在 `docs/GAME_TEARDOWN.md` 时必走)

复刻需求不吃"从零设计",而是**收敛拆解结论**。按以下映射填空,不得跳章:

| 拆解结论 | 写入蓝图 |
|---|---|
| §0 一页摘要(决定性变量 3-5 个) | §4 核心玩法循环(以变量为骨架写)、§5 机制清单(按敏感度排序) |
| 复刻档位 T0~T3 + 灰盒 MVP 一句话 | §6 范围边界"做什么"、§10 阶段裁剪建议 |
| M 清单 | §5 核心机制清单(**M 必须全部出现在清单里**,并在 `来源` 列写 `matrix_id`) |
| S 清单 | §5 机制说明中标注"表现可原创",不进"不做" |
| X 清单 + 替代方案 | §6 范围边界"不做"(写成"不做原作素材/文案/布局的复制,改用:{替代方案}") |
| O3 / E0-E1 盲区 | §9 关键技术风险(标"需实测确认") |
| 合规风险评级 | §9 风险表(法律项)+ §6 不做清单 |
| 商业化判定 | §7 商业化与外部依赖 |
| `docs/NUMERIC_MODEL.csv` | 蓝图只写"数值见 NUMERIC_MODEL.csv",不抄数值表(避免两处口径漂移) |

**三条硬约束**:
1. 蓝图 §1 一句话定义必须包含"**复刻基底 + 原创差异点**"两半(如"复刻{循环结构}的手感,以{差异点}区别原作"),只写"做一个像 XX 的游戏"不合格。
2. §5 机制清单每条末尾标注来源:`(M/原作·{matrix_id})` 或 `(S/原创)` 或 `(X→替代)`;M 项必须带 `matrix_id`,缺失视为未落地。
3. 蓝图**不重写拆解结论**,只引用与收敛;矛盾时以 `TEARDOWN_MATRIX.json` 为准并回问用户。

### 1. 引擎选择
读取 game-forge-master 的引擎决策树,根据"5. 核心机制清单"自动选择,写入"3. 平台与引擎"。

### 2. 核心玩法循环设计
生成"4. 核心玩法循环"前,**先读取 `references/design-principles-overview.md`**:

0. **若需求是"已有题材改编"**(用户给明确题材 / IP / 热点 / 真实数据),先读 `design-principles-narrative-adaptation.md` 做"题材→机制"转化,再继续以下步骤定主品类。
1. 按 overview §二 品类决策树确定**唯一主品类**:
   - ① 即时反馈类(超休闲/混合休闲)→ 读 `design-principles-instant-feedback.md`
   - ② 价值揭示类(赌石/开箱/鉴定)→ 读 `design-principles-value-reveal.md`
   - ③ 思考顿悟类(解谜/逻辑推理)→ 读 `design-principles-puzzle.md`
   - 都不属于 → 按常规玩法设计

2. 按 overview §三 检查是否需叠加**通用原则**:
   - 涉及 F2P/IAA/IAP/通行证 → 叠加读 `design-principles-monetization.md`
   - 涉及属性/资源/货币/成长曲线 → 叠加读 `design-principles-economy.md`

3. 按 overview §四 叠加规则,品类原则指导核心循环,通用原则指导变现与数值。

4. 按各原则文件的"生成蓝图时的应用流程"章节,映射原则到机制,填写核心玩法循环。

### 3. 复杂度评级
按以下表打分,累计定级:

| 维度 | 1 分 | 2 分 | 3 分 | 4 分 | 5 分 |
|---|---|---|---|---|---|
| 场景数 | 1 | 2 | 3-4 | 5-8 | >8 |
| 机制数 | 1-2 | 3-4 | 5-7 | 8-12 | >12 |
| 动画帧数 | <20 | 20-50 | 50-100 | 100-200 | >200 |
| UI 弹窗数 | 0 | 1-3 | 4-7 | 8-15 | >15 |
| 外部依赖 | 0 | 1 | 2 | 3 | >3 |

总分对应:5-8 → ★,9-12 → ★★,13-17 → ★★★,18-22 → ★★★★,23+ → ★★★★★

### 4. 范围边界
"做什么"必须可执行,"不做"必须明确拒绝。常见"不做"项:
- 不做账号系统(用临时 token)
- 不做服务端(纯前端)
- 不做内购(本期)
- 不做多语言
- 不做新手引导(**仅限纯动作类**;机制/解谜/关卡制必须做,且必须提供测试旁路 `skipTutorial()`,见 `game-spec` PRD §1.5)

> **引导不是可选项。** 它会改变输入语义(引导期间点击被门控吞掉),这件事必须在设计阶段就定清楚,否则每个验证脚本都要各自踩一次"点了没反应但断言照过"的静默假绿。首次进入弹一段文字不算引导,状态机 + 可旁路才算。

### 5. 阶段裁剪建议
根据复杂度自动填,见 game-forge-master 第四节"阶段裁剪规则"。

## 四、交互约定

1. 用户输入需求后,**先用 AskUserQuestion 确认 1-2 个关键点**(如引擎、是否需要后端),不要一次问太多
2. 确认后直接产出 `docs/GAME_BLUEPRINT.md`
3. 产出后向用户简报:"蓝图已生成,路径 docs/GAME_BLUEPRINT.md。核心玩法:{},复杂度 {}。下一步可调用 game-spec 生成 PRD 和技术设计"
4. **不要**自行调用下游 skill,让用户决定是否继续

- [ ] 文档无 TODO/占位文字
