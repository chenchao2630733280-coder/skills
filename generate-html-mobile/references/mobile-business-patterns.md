# 移动端业务渲染模式（Business Rendering Patterns）

> 本文件从 App AI UI Design System v2.0-v2.3 的通用业务模式章节蒸馏而来（蒸馏自 App AI UI Design System v2.0-v2.3），定义 generate-html-mobile 从**工件结构**识别出某类业务形态时的 UI 渲染规则。
>
> **定位声明**：本文件**不含业务知识**——业务流程、字段、状态、角色一律以上游 PRD 与 JSON 工件为准（领域建模知识已沉淀于 `generate-system-prd/references/business-domain-patterns.md`）。本文件只回答：**"当工件结构呈现出某类特征时，页面如何渲染"**。

---

## 一、五大通用渲染模式

每个模式 = 触发条件（工件结构特征）+ UI 结构 + 状态展示 + `.m-*` 类名建议。触发条件中的实体名称均为结构特征描述，具体字段以工件为准。

### 1.1 Resource Availability（资源可用性）

**触发条件**：`state-machines.json` / `data-model` 中存在带容量、时段概念的资源实体（号源、名额、房间、时段等——以工件为准），且存在锁定/超时状态。

**UI 结构**（自上而下）：

```text
日期选择（横向日历条）
  ↓
时段分组（上午/下午，按工件字段分组）
  ↓
时段条目（时间 + 剩余容量 + 操作按钮）
```

**状态展示**（每个时段条目按状态渲染，状态不只靠颜色，同时有文字与可操作性差异）：

| 状态 | 渲染 | 类名建议 |
|------|------|---------|
| Available（可选） | 主色边框/文字 + 可点击 | `.m-slot-item.available` |
| Selected（已选） | 主色填充 | `.m-slot-item.selected` |
| Limited（少量） | 主色 + 剩余数强调 | `.m-slot-item.limited` |
| Full / Booked（约满） | 灰色 + 禁用 | `.m-slot-item.full` |
| Expired / Closed（过期/停诊） | 灰色 + 删除线或"已过期" | `.m-slot-item.expired` |
| Locked（锁定中） | 警告色 + 倒计时 | `.m-slot-item.locked` + `.m-countdown` |

**类名建议**：`.m-slot-grid`（时段网格容器）、`.m-slot-item`（时段条目）、`.m-slot-remaining`（剩余数量）、`.m-countdown`（锁定倒计时）。

**规则**：锁定窗口内的倒计时必须醒目（警告色），倒计时结束显示"已释放"状态并提供重新选择入口；剩余容量数字用 `.m-live-value` 风格（等宽、加粗）。

### 1.2 Queue（排队叫号）

**触发条件**：`state-machines.json` 中存在实时位置型状态机（含"当前值/我的值/前方数量"类结构——以工件为准）。

**UI 结构**：

```text
场景化头部（当前场景说明）
  ↓
当前叫号（大字号主数字，18-24px+ 等宽）
  ↓
我的号码 + 前方人数（成对展示）
  ↓
位置提示（如"即将叫到您，请前往 X"——来自工件的提示字段）
```

**状态展示**：排队状态机各态（未开始/等待中/即将到/已叫号/已过号/完成——以工件枚举为准）用 `.m-tag-xxx` 状态标签 + 主数字颜色联动。

**类名建议**：`.m-queue-hero`（当前叫号大数字区，可复用 `.m-realtime-hero`）、`.m-queue-number`（等宽大数字）、`.m-queue-meta`（我的号码/前方人数成对信息）。

**规则**：
1. 大字号当前值是页面第一焦点（`.m-live-value` 风格）。
2. **不伪造精确等待时间**：工件无可靠预计时间时，展示"前方约 N 人"或"正在叫号"，不编造"预计 18 分钟"。
3. 状态更新用 `aria-live` 播报（对齐 SKILL.md §3.6）。

### 1.3 Identity（身份核验）

**触发条件**：数据模型中存在证件类型字段 + 核验/验证类动作（`actions.json` 中有 verify/intent 类动作——以工件为准）。

**UI 结构**：

```text
证件类型显式选择（分段选择器或独立选项，不用普通下拉框）
  ↓
证件号码输入（带格式校验反馈）
  ↓
联系方式（如工件定义）
  ↓
验证状态区（分步展示：正在验证身份 → 验证完成 → 正在查询… → 完成）
```

**状态展示**：
- 验证是多步过程时**分步展示**每一步的状态与完成情况，不合并为一个 loading。
- 每步失败必须给出原因与修改入口（"证件不支持""信息不一致""已绑定其他账户"等，文案来自工件）。

**脱敏规则**（与 `.m-sensitive-value` 对齐）：姓名保留姓+`**`；证件号保留前 3 后 4；手机号保留前 3 后 4；卡号保留后 4。**列表态、摘要态、确认态默认脱敏；编辑态按 `permissions.json` 授权展示明文。**

**类名建议**：`.m-identity-picker`（证件类型选择）、`.m-masked-value`（脱敏值，可复用 `.m-sensitive-value`）、`.m-verify-steps`（分步验证）。

### 1.4 Record（记录）

**触发条件**：数据模型中存在归属人×类型×日期×_status 结构的记录实体（报告、保单、订单、病历等——以工件为准）。

**UI 结构**（统一卡片结构，融入现有原型）：

```text
记录卡
├── 类型/标题（记录名 + 类型标签）
├── 归属人（脱敏姓名 + 关系角色标签，如工件定义了角色）
├── 关键属性行（日期、编号、摘要指标——按工件 display 字段）
├── 状态标签（.m-tag-xxx）
└── 操作（查看详情 / 按工件 actionIds）
```

**状态展示**：记录状态机全枚举（Pending/Available/Abnormal/Archived 等——以工件为准）都必须有对应 `.m-tag-xxx` 样式（对齐 Step 5 校验 3）；Pending 态用骨架或"处理中"标签，不用空态。

**类名建议**：`.m-record-card`（记录卡）、`.m-record-meta`（属性行）、复用 `.m-card`、`.m-tag`。

**规则**：列表页用统一卡片结构保证扫读一致性；"全部/处理中/已完成"类状态 Tab 筛选复用 `.m-local-tabs`。

### 1.5 Appointment（预约确认）

**触发条件**：数据模型中存在参与者×资源×时间的预约实体，流程含确认步骤（`actions.json` 提交类动作——以工件为准）。

**UI 结构**（确认页全要素，一级信息不折叠）：

```text
预约摘要卡（参与者、资源、日期时间、地点——按工件字段全量展示）
  ↓
费用明细（费用结构分项 + 合计，金额用 .m-amount 格式）
  ↓
注意事项（来自工件的提示字段）
  ↓
协议确认（可点击的协议链接，主色文字）
  ↓
锁定倒计时（若工件定义锁定窗口）+ 固定提交操作（.m-sticky-action）
```

**规则**：
1. 确认页要素必须齐全且直接可见，关键数据（费用、地址、时间）不藏在二级页面。
2. 锁定倒计时放在提交按钮上方或吸顶，剩余时间不足时警示。
3. 支付前用户必须知道"购买的是什么"——摘要卡先于操作。
4. 操作人≠预约对象时（工件含关系角色字段），摘要卡第一行显式展示"当前对象：姓名（角色标签）"。

**类名建议**：`.m-appointment-summary`（预约摘要卡）、`.m-fee-breakdown`（费用明细）、复用 `.m-sticky-action`、`.m-countdown`。

## 二、跨领域展示原则

从多领域提炼的通用展示约束，适用于所有命中相应工件结构的页面：

1. **双状态机分离展示**：`state-machines.json` 中存在支付状态机 + 业务状态机并行时（如"支付成功+保单生成中"），页面同时展示两个状态标签，不得合并为一个"成功"。支付态用 `.m-tag-success`/`.m-tag-warning`，业务态独立标签。
2. **敏感数据双态规则**：列表/摘要态默认脱敏（`.m-masked-value`）；编辑态经 `permissions.json` 授权后展示明文；编辑流程为"摘要 → 点击编辑 → 授权/验证 → 编辑 → 重新校验"。
3. **操作人≠对象时角色显式化**：工件存在关系角色字段时，关键步骤（确认页、支付页、结果页）持续展示"当前对象：姓名 + 角色标签"，角色标签用浅色胶囊（`.m-tag` 风格）。
4. **多步验证分步展示**：核验类流程各步骤独立展示状态与失败原因，禁止合并为单一 loading。
5. **结果页失败三问**：失败结果页必须回答——发生了什么 / 为什么 / 下一步怎么办；给出原因与至少一个恢复动作（修改信息/重新提交/联系客服——按工件 actionIds）。

## 三、布局变体

按工件内容特征选择的页面级布局变体（叠加在 10 个基础原型之上）：

### 3.1 瀑布流内容（Masonry）

**适用**：内容发现/图文列表页中，工件内容项为不等高图文（图片比例不一、标题长短不一——以工件为准）。

```css
.m-masonry { columns: 2; column-gap: 8px; }
.m-masonry .m-media-card { break-inside: avoid; margin-bottom: 8px; }
```

卡片结构：图 → 标题 → 可选元信息；**不设固定高度**，自然形成瀑布流。

### 3.2 保障矩阵（表格型数据）

**适用**：工件存在"项目×数值"二维对照结构（保障项×保额、收费项×金额——以工件为准）。

结构：模块标题 + 表格式两列（项目名 / 数值），数值右对齐、等宽数字、加粗；重要行可用 `.m-card` 包裹强调。原则：**信息比装饰重要**——此变体不加大图和插画。

**类名建议**：`.m-matrix-table`（两列对照表）。

### 3.3 Care Mode（关怀模式）

**适用**：工件或用户需求声明了适老化/无障碍场景。

不是简单放大字号，而是整组 Token 覆盖 + 信息密度重算：

```css
.care-mode {
  --m-text-primary-scale: 1.25;   /* 正文 14px → 17-18px */
  --m-primary-action-height: 52px; /* 按钮 48px → 52px */
  --m-card-padding: 20px;
  --m-section-gap: 20px;
  --m-touch-target: 52px;
}
```

同时减少：装饰元素、同屏信息量、复杂操作步骤；增强：文字对比度、点击区域。原则从"效率优先"切换为"可理解性优先"。

**类名建议**：`.care-mode`（挂到 `body` 或页面根元素的 Token 覆盖组）。

## 四、结果页（result）原型规则

补齐 SKILL.md §3.5 原型表缺口。结果页是流程终点页，四态结构（状态枚举以工件为准）：

### 4.1 Success（成功）

```text
[成功图标（SVG）]
结论标题（动词+对象，如工件定义）
关键凭证（编号/摘要，脱敏）
[查看详情] [返回首页]
```

### 4.2 Processing（处理中）

```text
[进度图标/动画]
"处理中"结论 + 说明文案（正在发生什么，文案来自工件）
[查看进度]
```

规则：异步流程（支付完成但业务对象生成中）用 Processing 态，**不用 Success 态**，并按双状态机分离展示。

### 4.3 Failed（失败）

```text
[失败图标]
结论标题
原因（必须给可解释原因，来自工件）
[失败三问恢复动作：修改信息 / 重新提交]
```

### 4.4 Cancelled / Expired（已取消/已过期）

```text
[中性图标]
结论标题 + 说明（含影响说明，如信用规则——文案来自工件）
[可恢复动作：重新预约等]
```

**通用规则**：
1. 结论文案用"动词+对象"（如"预约挂号""确认退号"），不用孤立的"确定/提交"。
2. 结果页不用底部主导航（属于流程终点二级页）。
3. 凭证编号脱敏展示；关键数字用 `.m-live-value` 风格。
4. 状态图标用统一 SVG 图标体系，禁止 Emoji。

**类名建议**：`.m-result-hero`（图标+结论区）、`.m-result-reason`（原因说明）、`.m-result-actions`（操作组）。
