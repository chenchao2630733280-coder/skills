# 状态建模纪律（拆"对象—容器—场景"三套状态）

> 这一份解决一个具体问题：**为什么很多复刻"规则拆对了，代码一跑就崩"**。
> 结论：不是规则错，是状态被塞进一个字段、被动画驱动、被副本污染。

本文件与 `teardown-dimensions.md` 维度 3 / 6 / 8 配合使用；对应 SKILL.md §九。

---

## 一、先分三套状态机

任何有"操作 → 收集 → 清除"结构的游戏，至少有三层状态，**不能合成一个**：

| 层 | 管什么 | 螺丝解谜的例子 | 塔防的例子 | 卡牌的例子 |
|---|---|---|---|---|
| **对象态** | 单个可操作物 | 螺丝：固定/选中/移动中/已收集 | 单位：待机/移动/攻击/死亡 | 卡：在手/已打出/进墓地 |
| **容器态** | 收集器/槽位/队列 | 颜色盒（开/满/关）、暂存槽 | 资源池、人口上限 | 手牌上限、牌库、弃牌堆 |
| **场景态** | 关卡整体 | 进行中/胜/负 | 波次进行/失败/通关 | 回合/对局结束 |

**跨层因果走事件，不走直接引用**：`对象态变化 → 事件 → 容器态更新 → 事件 → 场景态判定`。
否则会出现"容器说装了、场景说没装""重开时容器残留上一局"这类事故。

**拆解要求**：报告 §8 必须画出这三套状态机与它们之间的事件箭头；只有一套状态机的设计，基本可以判定为"没拆到状态层"。

## 二、四个概念不许合并成一个字段

这是最高频的错误。以"层级（layer / depth / zIndex）"为例，它经常被拿来同时表达四件事：

| 概念 | 回答的问题 | 正确用法 | 被误用后的症状 |
|---|---|---|---|
| **归属 belongsTo** | 它挂在谁身上 | 外键：`screw.boardId` | 板件移除后螺丝仍"活着"，计数错乱 |
| **渲染层 renderOrder** | 谁画在上面 | 纯视觉排序，可随时重排 | 用 zIndex 判断可点击 → 换皮就崩 |
| **遮挡 blocksWhat** | 它挡住谁的什么 | 规则属性：`blocksScrews` / `blocksBoards` / `blocksInput` 分开 | 透明板件被当成"不遮挡"，玩法直接变简单 |
| **可交互 removable/usable** | 现在能不能点 | **派生值**，每次从权威状态重算 | 看得见但点不了时无处表达 |

### 判定基准也必须写明

"被遮挡"是个结论，不是规则。规则里必须写清**用哪个几何/逻辑基准**判定：

| 基准 | 行为差异 | 适用 |
|---|---|---|
| 中心点落入多边形 | 露出边缘也算被挡 | 简单、稳定，多数休闲解谜 |
| 碰撞区（半径） | 半露可点 | 手感更宽松 |
| 整块多边形相交 | 大面积重叠才算挡 | 容易误判 |
| 人工配置可点状态 | 完全可控但产能低 | 特殊机制/演出关 |

**不同基准直接改变难度与手感**——这是"像不像"的隐藏变量，必须作为拆解结论写出来（并进 `value_or_range`）。

## 三、可见 ≠ 可交互（用实例证伪，不要用直觉）

拆解时找一个"**看得见但点不了**"的实例，就证明了至少存在两个独立状态。找不到实例，才允许先合并（标 E0）。

常见证据形态：
- 同一屏内既有可点螺丝又有被压住的螺丝（外观几乎一致）
- 半透明覆盖物下的对象可见但不可点
- 已消耗的槽位仍显示轮廓但不可再用

**反向也要检查**：有没有"看不见但能点"的？（隐藏可点区、判定区大于视觉）——有则说明判定与渲染彻底解耦。

## 四、残留态：消失之后留下了什么

**凡是"消失"的地方，追问一句：消失了什么，留下了什么？**

| 操作 | 消失 | 留下的残留态（常见） |
|---|---|---|
| 移除一颗螺丝 | 螺丝 | 板件上的**空孔**（仍占视觉位置，仍算板件一部分） |
| 移除板件所有螺丝 | 板件固定 | 板件本体仍在原位，直到播放掉落动画结束 |
| 盒子装满 | 盒子空间 | 盒子关闭动画/空位，等下一盒补位 |
| 使用道具 | 道具次数 | 道具槽位（灰化/冷却）仍占 UI 位 |
| 敌人被击杀 | 敌人单位 | 尸体/坑/掉落物（可能仍参与碰撞或遮挡） |

**建模要求**：残留态是**独立字段**（`holeVisible`、`slotUsed`、`corpseBlocks`），不能靠"对象删除"隐式表达。
否则"板件还在但有 3 个空孔"这种状态无处存放，最后只能写进渲染层，一重开就丢。

## 五、权威状态 vs 派生状态

| 类别 | 规则 | 例 |
|---|---|---|
| **权威（存储）** | 只能由操作事务写入 | 螺丝的 `collected`、容器里的 id 列表、关卡进度事件 |
| **派生（计算）** | 每次读取时重算，**禁止存副本** | 剩余螺丝数、可交互螺丝列表、进度百分比、盒子是否满、胜负 |

副本一定会漂移，尤其在：动画未结束、快速连点、断线重连、中途重开。

**代码判据**：任何写了两次的同一个量，第二次就是 bug 的来源。搜索"赋值同一语义字段"的地方，是最快的找 bug 方式。

## 六、逻辑与表现分离（四条硬约束）

1. **一次操作 = 一个事务**：校验 → 改权威状态 → 发事件 → 由事件驱动动画/音效/UI 刷新。事务内不许 await 动画。
2. **动画只读状态，不写规则**：动画结束时只上报"表现完成"，不得决定"是否移除"。
3. **表现参数可随机，逻辑结果必须确定**：抖动幅度、掉落旋转、粒子数可以随机；掉落**判定**与**顺序**不能随机。
4. **打断必须可预测**：动画播到一半点击、连续快速点击、切后台再回来，结果都要等于"按最终状态重算"。

**事故形态**（都会导致"同一关重置十次结果不同"）：
- 用 `onAnimationComplete` 里改规则
- 事件监听重复绑定，一次点击触发两次收集
- 视觉对象删除后，逻辑仍在引用（或反之）
- 用 `setTimeout` 串联状态，而不是事务

## 七、状态迁移表（拆解时直接抄这个结构）

对每个对象，写出**状态 × 触发 × 副作用**，缺一格就是没拆清：

```markdown
| 当前状态 | 触发条件 | 下一状态 | 副作用（谁跟着变） | 证据 |
|---|---|---|---|---|
| FIXED | 点击且未被遮挡 | SELECTED | 无 | E2 帧 00:03 |
| SELECTED | 有同色开放容器 | (容器态) 计数+1 | 对象→COLLECTED；板件剩余数-1 | E2 |
| SELECTED | 无同色容器且槽位有空 | (容器态) 槽位-1 | 对象→COLLECTED；板件剩余数-1 | E2 |
| SELECTED | 无同色容器且槽位已满 | 场景态→FAIL | 触发失败界面 | E1 待验证 |
| 板件 剩余数=0 | 事务提交 | UNLOCKED | 播放下落动画；动画结束→REMOVED；重算遮挡与可交互 | E2 |
```

**"副作用"列是最容易漏的一列**：一次操作往往同时改三处（对象、容器、场景）。只写"下一状态"而不写副作用，等于只拆了 1/3。

## 八、检查清单（产出前逐条过）

- [ ] 三套状态机（对象/容器/场景）都画了，且有事件箭头
- [ ] 归属、渲染层、遮挡、可交互是四个独立字段（有合并的已写明理由与风险）
- [ ] 遮挡的判定基准已写明（中心点/碰撞区/多边形/人工）
- [ ] "可见 ≠ 可交互"有实例证据，或明确标"未找到反例，暂合并"
- [ ] 每个"消失"都追问了"留下什么"，残留态有字段承载
- [ ] 权威状态与派生状态已分开，派生量没有存副本
- [ ] 状态迁移表含"副作用"列，且副作用覆盖对象/容器/场景三层
- [ ] 逻辑与表现分离的四条约束都已落到设计上
- [ ] 确定性验收写法明确：重置 ≥10 次状态哈希一致
