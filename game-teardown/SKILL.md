# Game Teardown — 游戏复刻拆解

本 skill 是 AI 游戏生成流水线的**阶段 0.5（复刻专线）**。当用户的需求不是"从 0 想一个游戏"，而是"**照着某款游戏做**"时，先经本阶段把参考游戏拆成**产品系统**，再交给 `game-blueprint`。

**一句话原则**：先拆「循环—规则—数值—内容—交互」，再拆「表现—技术—运营」；先做可玩核心，再换高保真表现；**只学结构与参数，不搬素材与表达**。

**本 skill 的成败判据不是"拆得全"，而是"拆得能被推翻"**——一次就对的拆解，通常说明拆得不够深（见 §六）。

**与相邻 skill 的边界**：

| skill | 职责 | 不做 |
|---|---|---|
| `game-topic-brainstorm` | 从 0 找选题（无参考对象） | 不拆具体游戏 |
| **本 skill** | 把**已有游戏**拆成可复刻的系统与参数 | 不产出蓝图、不写代码、不判断"好不好玩" |
| `game-blueprint` | 把拆解结论收敛成一页纸蓝图 | 不做拆解 |

---

## 一、何时调用

**调用**（满足任一）：
- 用户点名一款参考游戏，要"复刻/对标/仿制/做成一样的/换皮"
- 用户给录屏、截图、试玩描述，要求"按这个做"
- 用户要"拆解竞品，做差异化版本"
- `game-forge-master` 识别到需求含参考对象并路由到本阶段

**不调用**：
- 从 0 脑暴选题 → `game-topic-brainstorm`
- 用户已有明确玩法、无需参考 → 直接 `game-blueprint`
- 只想听"这游戏值不值得玩/好不好玩" → 对话回答即可
- 要改已有工程代码 → 直接 Edit/Write

---

## 二、输入与输出

**输入**：
- 必需：参考游戏标识（名称 / 录屏 / 截图 / 试玩记录，至少一种）
- 可选：复刻档位（T0~T3）、目标平台、工期预算、必须保留的原作特征、必须改掉的差异方向
- 可选：**用户自带的拆解稿 / 复盘记录**（多份笔记、文档、分析）——此时走"审计路径"，见下

**审计路径（已有拆解稿时）**：不重写全文，只做四件事，产出仍是 3 份固定产物：
1. **提级**：把文稿里的"观察/推断/建议"打上 `kind` 与 `E` 等级，矛盾处标红
2. **补缺**：用 12 维清单找缺口（常见缺：状态建模、瓶颈资源、解空间、确定性）
3. **证伪**：给每条关键假设补 `falsifier`，能推翻的立刻推翻并记入修正史
4. **补测**：把 E0/E1 结论转成待验证清单（方法 + 成本），并给出"先补哪三条最划算"

**输出**（固定路径，3 份，缺一不可）：

| 产物 | 路径 | 读者 | 作用 |
|---|---|---|---|
| 拆解报告 | `docs/GAME_TEARDOWN.md` | 人 + 下游 skill | 12 维结论、循环图、修正史、判定依据 |
| 复刻矩阵 | `docs/TEARDOWN_MATRIX.json` | 机读 + 质量门 | 每条结论的三色/证据/陈述类型/敏感度/MVP 归属 |
| 数值模型 | `docs/NUMERIC_MODEL.csv` | Excel/Sheets + `game-spec` | 参数、区间、公式、证据等级、来源 |

**材料不足时的处理**：用 AskUserQuestion 只问 1 轮（档位 + 材料补齐方式）；仍不足则按 **T1 + 结构级拆解** 执行，并在报告 §14 明确列出盲区与证据覆盖率，**不得虚构数值**。

## 三、第一原则：复刻不是复制（三色判定）

拆解结论的每一条都必须打上三色标签，否则视为未拆完。

| 标签 | 含义 | 判定问句（任一命中即归此类） | 处理 |
|---|---|---|---|
| **M / Must** | 必须复刻的核心 | "去掉它，玩家还会说这像 XX 吗？" → 不会 | 进 MVP，按原版参数尽量贴 |
| **S / Swap** | 可替换的表现 | "它决定这是'XX 的什么皮'，而不是'这是不是 XX'" | 可原创，是差异化的主战场 |
| **X / Cannot** | 禁止复制的表达 | 属于受保护表达：具体美术/音频/代码/文本/角色名/商标/关卡地图排布 | **必须写出替代方案**，否则 Gate 直接 FAIL |

**硬规则**：
1. 每个维度至少 1 条 **M**——只有 S 说明没拆到核心。
2. 每个 **X** 必须有 `replacement` 字段（合法替代手法），空即 FAIL。
3. **M/S/X 与"重要程度"无关**：X 项可能极其重要（如核心 UI 布局），但它仍然不能抄，只能"换一种方式达到同样效果"。
4. 复刻档位只改 M 的数量与深度，**不改变 X 的边界**（任何档位都不能抄素材）。

## 四、复刻档位 × 拆解深度（先定档，再决定拆多深）

不区分档位就全维度拆到公式级，是最常见的浪费。

| 档位 | 定义 | 拆解深度 | 交付判据 |
|---|---|---|---|
| **T0 学习原型** | 只复刻核心玩法循环 | 循环 L2，规则 L1，数值 L1（仅区间），表现全 S | 能跑通"一次完整循环" |
| **T1 玩法克隆** | 规则/系统/数值接近，表现原创 | 循环 L2，规则 L2，数值 L2，内容 L1 | 老玩家上手能认出同一玩法 |
| **T2 高保真复刻** | 连交互节奏、关卡节奏、UI 信息结构都接近 | 全部 L2，关键项 L3，交互 L3 | 前 5 分钟体验节奏与原作同构 |
| **T3 商业产品** | 追加商业化/运营/合规 | T2 + 经济与付费 L2~L3 + 运营节奏 L1 | 有可运营的数值与付费结构 |

**深度分级**：

- **L1 结构级**：有哪些模块、先后顺序、界面层级、存在与否
- **L2 区间级**：数值范围、时长、频率、概率量级、难度节奏
- **L3 公式级**：曲线形状、伤害/成长公式、掉落权重分布、经济闭环平衡点

**两条约束**：
1. **深度上限由可观测性决定**（见 §八），不可观测的维度拆到 L3 就是编造。
2. **只有高敏感项才值得 L3**（见 §十一）。给玩家感知不到的参数做 L3 是自嗨。

**T2/T3 额外要求**：状态建模（§九）与解空间分析（§十）必做；T0/T1 至少做"瓶颈资源识别"。

## 五、12 维拆解流程（4 个 Pass）

按"可玩核心优先"排序，**不允许先拆表现层**。

### Pass A — 循环与规则（维度 2、3）

| 拆什么 | 方法 | 产出 |
|---|---|---|
| 玩家目标、30 秒/5 分钟/1 小时各做什么 | 录屏按时间轴切片，标"操作—反馈—奖励" | 三时间尺度表 + 循环图（Mermaid） |
| 输入→反馈→奖励→成长→新挑战闭环 | 画闭环，找断点（哪里会让玩家想退出） | 循环图 + 断点清单 |
| 失败与重试成本 | 计时：死亡到重开几步/几秒/损失什么 | 重试成本表（决定留存下限） |
| **失败压力的来源：瓶颈资源是什么** | 问"玩家因什么而失败/紧张"：空间/步数/时间/次数/费用/血量 | 瓶颈资源表（容量、单次占用、释放条件、扩容闸门） |
| 核心乐趣排序 | 操作 / 策略 / 成长 / 收集 / 社交 / 叙事 | 乐趣权重（决定 M 项取舍） |
| 系统模块（属性/战斗/建造/AI/成长/多人） | 每系统填"输入、状态、规则、输出、边界" | 系统表（6 字段不得缺） |

**产出物要求**：核心循环图 + 一次循环的时长与步数（可被 `game-spec` 直接换算成关卡节奏）。

### Pass B — 数值与内容（维度 4、5）

- 属性/伤害/命中/暴击/护甲公式族，成长与经验曲线，掉落权重与保底
- 资源产出/消耗闭环、货币层级、体力与冷却
- 关卡结构、波次、敌人/物件配置、难度峰值位置、教学关设计
- **解空间**：分支因子分布、死路率、最优解长度、解的数量（见 §十）
- **只学"节奏与结构"**：关卡的具体地图排布、剧情文本、角色设定属 X

方法：录屏逐帧统计 → 控制变量实测 → 公式族反解 → 拟合 → 建 CSV 模型 → 敏感度分析。
详见 `references/numeric-reverse-engineering.md`。

### Pass C — 交互与表现（维度 6、7）

- 屏幕信息层级（HUD/菜单/背包/地图/结算）、操作路径长度（点到目标几步）
- **可交互状态**：哪些对象"看得见但点不了"（证明存在独立判定层，见 §九）
- 反馈密度：打击感（顿帧/位移/闪白）、飘字、音效触发点、震动、动画时长
- 引导流程、错误提示、加载与存档、失败反馈
- 美术风格坐标系（色相/明度/饱和度范围、比例、线宽、镜头）、动画节奏、叙事结构

**拆法**：逐屏截图 → 页面流程图 + 交互状态机（每个界面的"进入/空/满/错误/退出"五态）。
表现层**全部默认 S**，只把"反馈密度与节奏"当 M（这是玩家觉得"手感像不像"的真正来源）。

### Pass D — 工程与商业（维度 1、8、9、10、11、12）

- 引擎/客户端架构/数据驱动/存档/联机/服务器/性能指标（多为不可观测，见 §八）
- 配置表结构、编辑器需求、埋点、构建与热更、调试命令
- **内容产能来源**：手工配置 / 参数化生成 / 求解器筛选 —— 决定你的成本结构（见 §十）
- 测试与调优：功能边界、平衡、可玩性、性能、**确定性**、回归
- 合规与伦理（硬门，见 §十二）
- 运营与商业化：付费点、活动节奏、留存/转化指标（仅 T3）

**原则**：技术维度**不复刻原实现**，只保证"行为等效"；能观测到的只有表现与节奏，架构一律标 O3。

## 六、拆解是收敛过程：假设 → 反例 → 修正

**首轮拆解产出的是假设集，不是结论集。** 任何一次成型报告都必须留出修正回合，否则你交付的是"看起来严密的猜测"。

### 6.1 三条修正触发器

| 触发器 | 表现 | 动作 |
|---|---|---|
| **反例** | 某帧/某局观测与假设矛盾（如"螺丝直接进盒"却被看到暂存槽里已有螺丝） | 假设作废，重写机制，并追查受影响的下游结论 |
| **走不通** | 按假设写不出可玩规则 / 画出无解 / 无法用同一套规则跑通 | 说明规则缺隐藏条件，回查边界与判定基准 |
| **交叉源冲突** | 竞品资料、攻略、官方帮助与自己的观测不一致 | 以**自己的观测**为准，冲突写入待验证清单，标"可能是版本差异" |

### 6.2 每条假设必须带"可推翻它的观测"

写结论时同时写 `falsifier`：**什么观测能证明我错了**。
- 不合格：`螺丝移除后板件消失`
- 合格：`螺丝移除后板件消失（若观察到"同一板件移除一颗螺丝后仍留在原位且出现空孔"，则本结论作废）`

**没有 falsifier 的结论 = 不可验证 = 不许进报告**（只能进"猜想"附注）。

### 6.3 修正记录（报告的必备章节）

保留修订史，**不删旧版本**：

```markdown
## 修正史
| 版本 | 原假设 | 被什么推翻（帧号/样本/来源） | 修正为 | 连带影响 |
|---|---|---|---|---|
| v1→v2 | 螺丝点击后直接进入同色盒子 | 第 1 秒画面：暂存槽已存 2 颗橙螺丝，而同色盒子未开放 | 开放盒子队列 + 暂存区两级去向 | 维度 3、4、5、12 全部重估；失败条件改为"暂存满且无合法操作" |
```

**典型修正形态**（经验库，命中即优先检查）：
- "A 直接进 B" → 实际中间有**缓冲层**（暂存/队列/冷却）
- "对象消失" → 实际留有**残留态**（空孔、坑、已解锁槽位）
- "层级决定一切" → 实际是**多个正交维度**（归属/渲染/遮挡/可交互，见 §九）
- "一次操作只改一个东西" → 实际触发**连锁更新**（容器 → 场景 → 可用性）

## 七、可复刻性三问（每条 M 结论的闸门）

一条结论只有同时通过三问，才算"拆清了"：

| # | 问题 | 不过关意味着 | 必须补什么 |
|---|---|---|---|
| 1 | **能写成伪代码吗？**（输入/状态/规则/输出/边界） | 规则还停在形容词层 | 补边界条件（满/空/同时触发/上限/重复操作） |
| 2 | **能写成断言吗？**（可自动验证的用例：前置状态 → 操作 → 期望结果） | 无法验收 = 等于没定义 | 拆出一条测试用例，写进报告 §10 |
| 3 | **能算出解吗？**（用同一套规则跑通一遍模拟/求解） | 规则有隐藏依赖或不可判定 | 补判定基准、补缺失状态（见 §九） |

- 三问全过 → 可复刻，进 MVP
- 过 2 问 → 标"需补"，进 MVP 但列为风险
- 过 1 问及以下 → 只是"感觉像"，**不得进 MVP**，进待验证清单

**硬约束**：求解器/模拟器**必须调用与游戏相同的规则函数**。另写一套"求解器版规则"必然自洽但永远和游戏不一致，是最隐蔽的返工源。

## 八、证据分级与可观测性（防编造）

AI 做逆向拆解最大的失败不是拆不全，而是**把推断写成事实**。

### 8.1 证据等级（每条数值/结论必带）

| 等级 | 定义 | 举例 |
|---|---|---|
| **E3** | 实测或可交叉验证的公开数据 | 自己控制变量试 20 局取分布；官方wiki/帮助中心公式；补丁说明 |
| **E2** | 采样统计 | 录屏 10 局，逐帧统计单局时长/敌人数/掉落频率 |
| **E1** | 合理推断 | 同类游戏公式族 + 参数反解，能解释已观测现象 |
| **E0** | 猜测 | "应该是这样"、没有样本、无法解释反例 |

### 8.2 判定细则（四条）

结论类型→证据形态（错配即降级）、样本覆盖矩阵（缺格即盲区）、三类陈述必须分离（`【观察】/【推断】/【设计】`）、
置信度按属性拆分（禁止给对象一个笼统置信度）——四条细则见 `references/evidence-grading.md`。

**一句话记住**：单帧只能证明"此刻"，证明不了"顺序"；只看过前 2 关就断言后期难度曲线，是本 skill 最常见的越界。


### 8.3 硬规则（违反即 Gate FAIL）

1. **进蓝图的数值必须 ≥E2**；E0/E1 只能进报告 §14「待验证清单」，并写清验证方法与成本。
2. **O3 维度只写"行为等效设计"**，禁止写"原作是如何实现的"。句式：`原作效果可观测为 X → 复刻采用 Y 达到等效`。
3. 每条数值必须带 `source`：帧号区间 / 样本局数 / 链接 / 实测次数。**没有来源的数字不许进 CSV。**
4. 不确定就写**区间**（`0.8~1.2s`），不写单点精确值（`0.97s`）。
5. 禁止"看起来差不多"作为证据；禁止用"业界惯例"替代观测。
6. 证据覆盖率（达到 E2 及以上的维度数 / 12）必须写进报告 §0 摘要，**低于 60% 要在报告首行标红提示**。

## 九、状态建模纪律（复刻能不能跑起来的分水岭）

> 详细清单与模板见 `references/state-modeling.md`。这一维做错，后面所有规则都会在动画、异步、重置时崩。

### 9.1 四个概念不许合并成一个字段

| 概念 | 回答的问题 | 常见错误 |
|---|---|---|
| **归属**（belongsTo） | 它挂在谁身上 | 用 `layer` 代替父子关系 |
| **渲染层**（renderOrder） | 谁画在上面 | 用 `zIndex` 推可交互性 |
| **遮挡**（blocksWhat） | 它挡住谁的什么 | 透明 ≠ 不遮挡（透明是视觉，遮挡是规则） |
| **可交互**（removable/usable） | 现在能不能点 | 用 `visible` 代替 `removable` |

一条硬判据：**能找到"看得见但点不了"的实例，就证明至少存在两个独立维度。** 找不到实例时，才允许先合并并标 E0。

### 9.2 残留态必须建模

操作后对象可能留下痕迹：空孔、坑、已解锁槽位、已消耗容器位。
"移除螺丝"和"移除板件"是两个事件；"容器已满"与"容器已关闭"也是两个状态。
**凡是"消失"的地方，先问一句：消失了什么，留下了什么？**

### 9.3 能算的不要存

`remainingScrews`、`可交互螺丝列表`、`进度百分比` 都是**派生状态**：每次从权威状态重算。
存了副本就一定会不同步（尤其在动画、异步、重开时）。

### 9.4 逻辑与表现分离（硬约束）

- 一次操作在**一个事务里**改完所有权威状态，再发事件；动画只读状态，**不得决定规则**
- 禁止"等动画播完才判定移除"——这是状态漂移与重开不一致的第一大来源
- 表现参数（抖动幅度、掉落旋转、粒子数量）可随机，**但不得影响逻辑结果**

### 9.5 坐标与参照系

记录**参照分辨率 + 归一化方式**（如 `512×1152 → 0..1`）。没有参照系的坐标不可复用，也无法换算成别的机型。

## 十、解空间与难度（比加权评分可靠）

> 方法、指标定义与求解器要求见 `references/solvability-and-difficulty.md`。

### 10.1 先找瓶颈资源

休闲解谜的失败压力 90% 来自"容器容量"，不是"敌人强度"。拆解时先回答：

| 问题 | 例（螺丝解谜） |
|---|---|
| 因什么而失败？ | 暂存槽塞满且无合法操作 |
| 上限多少？ | 5 格 |
| 单次占用 | 1 格/螺丝；同色满 3 颗释放 3 格 |
| 释放条件 | 凑齐同色 / 用道具 / 新盒开放 |
| 扩容闸门 | 广告或内购解锁额外盒子/孔位 |

**找不到瓶颈资源 = 没找到失败压力 = 难度无法复刻。**

### 10.2 四个解空间指标（难度用它们表达，不用等权公式）

| 指标 | 含义 | 判读 |
|---|---|---|
| **分支因子分布** | 每步合法操作数 | 全为 1 = 机械；恒 >8 = 无方向；理想是"多数 2~4，关键节点出现 1 或 ≥5" |
| **死路率** | 随机走 N 步后无解的比例 | 太高=挫败，太低=无压力 |
| **最优解长度 / 对象数** | 步数冗余度 | 接近 1 = 线性流程；远大于 1 = 有真实规划空间 |
| **解的数量** | 唯一解 / 少解 / 多解 | 唯一解需防呆提示；多解要检查是否"随便点都过" |

**口径纪律**：等权加权分（如 `0.2C+0.2O+...`）只作排序占位，**不作难度绝对值**；归一化基准一变，绝对值就不可跨版本比较。

### 10.3 求解器是拆解的一部分，不是开发的附加项

- DFS/BFS + 状态哈希 + 记忆化；输出 `solvable / solution / steps / deadEnds / 分支因子统计`
- **必须复用游戏规则函数**（见 §七）
- 用途不止验关：批量**反推难度曲线**（解数、死路率随关卡变化的形状），比人工试玩可靠

### 10.4 内容产能决定成本结构

判断原作的内容来自哪里：
- **手工配置**（每关手摆）→ 你要建编辑器，否则产能封顶
- **参数化生成**（模板 + 参数）→ 你要建生成器 + 校验
- **求解器筛选**（生成后自动验解、评分、淘汰）→ 这是最高杠杆，也是这类品类的真壁垒

**能自动化的绝不手工堆**：先做"生成 → 求解 → 评分 → 筛选"的管线，再谈内容量。

## 十一、敏感度排序（决定"像不像"的真旋钮）

拆完 12 维不等于每项都值得复刻。必须再收一刀：

1. 从所有 **M** 项里挑 **3~5 个**"决定辨识度"的变量（去掉它就不像了）。
2. 每个打 `sensitivity: high / mid / low`，写一句"为什么高"。
3. 规则：
   - **high** → MVP 必做，参数贴原作（E2+）
   - **mid** → MVP 做简化版
   - **low** → 允许大改，**同时构成差异化锚点**
4. 复刻必须有**至少 1 个原创差异点**（题材/叙事/一个新机制/一个新反馈层），写进矩阵 `differentiation`。这既防"换皮混淆"，也防做出来只是个廉价复制品。

典型高敏感项（按品类参考，需实测确认）：操作响应延迟、单局时长、反馈密度（每秒事件数）、失败惩罚力度、成长可见速度、随机性的可解释度、**瓶颈资源的容量**。

## 十三、灰盒 MVP 裁剪规则

复刻的返工大头是"先做表现、后发现循环不对"。裁剪顺序固定：

| 类别 | 处理 |
|---|---|
| M 且 high 敏感 | **必进 MVP**，灰盒实现（几何/色块/文字），参数贴原作 |
| M 且 mid/low 敏感 | 进 MVP 但简化（少关卡、少单位、少特效） |
| S 表现层 | 全部**占位**（纯色块 + 文字标签 + 静音） |
| X 禁止项 | 用原创替代方案，MVP 期可用更简陋的替代 |
| O3 不可观测 | 用"行为等效"最小实现（如本地伪匹配、固定掉落表） |

**MVP 三件套**（缺一不可）：
1. **逻辑内核**：规则可脱离画面单独跑单测
2. **单关灰盒**：验证遮挡、解除、连锁更新（挑"最有结构"的一关，不是第一关）
3. **关卡数据文件**：轮廓/坐标/归属/层级/初始遮挡/容器配置，可被程序读取

**MVP 一句话定义模板**：`能验证「{核心循环}」的最小可玩切片：{1 个关卡/1 种单位/1 条成长线}，其余全部占位。`

**确定性验收（硬指标）**：
- 同一关重置 **≥10 次**，初始状态哈希一致
- 随机参数只影响表现，不影响逻辑结果
- 动画未播完时点击、连续快速点击、中途重开，结果都必须可预测

**验收**：MVP 必须能连续玩 3 分钟不出现"卡住/空白/无反馈"，且 3~5 个高敏感项可被肉眼辨认出与原作同构。

## 十八、反模式（出现即返工）

1. **只拆画面和玩法**：跳过数值与节奏，做出来"看着像，玩着不像"。
2. **把推断写成事实**：没有样本也给出精确公式，后续数值全歪。
3. **把"复刻"当"复制"**：直接搬素材/文案/地图 → 法律风险 + 平台下架。
4. **先做表现层**：美术做完了才发现循环不对，返工成本最高。
5. **平均用力**：12 维都拆到 L3，却没有敏感度排序，MVP 里塞满低价值系统。
6. **忽略失败成本**：只拆成功路径，重试太贵导致留存崩。
7. **忽略三时间尺度**：只写"一局怎么玩"，没写"玩一小时后还剩什么"。
8. **无差异点**：100% 照搬 = 换皮混淆高风险，且没有存在理由。
9. **状态维度合并**：一个 `layer` 同时承载归属/渲染/遮挡/可交互，动画一上就全线漂移。
10. **一稿定稿**：没有修正史、没有 falsifier，看似完整实则全是未验证假设。
11. **难度靠加权分**：等权系数凑出来的"难度 0.62"不可复现，也不可迁移；要解空间指标。
12. **求解器另写一套规则**：验证通过但和游戏不一致，等于没验。
