# 三策略求解器：伪代码、判定表与死局分类

> 求解器不是"AI 玩家"，是**测量仪器**。它的唯一职责是让"这内容需不需要动脑"变成可复现的结论。

---

## 一、共同骨架

```
state = load(content)          # 与产品共用同一份数据
legal = state.legal_actions()  # 判定层：可交互集合（含"能碰但推不动"）
while not state.finished():
    a = strategy(legal, state)
    if a is None: break        # 无动作可做
    state.apply(a)
    legal = state.legal_actions()
record(state)
```

三条纪律：

1. **共用数据与规则**。求解器里不许重写一套"简化规则"，否则测的不是同一个东西。
2. **动作必须经过真正的合法性判定**，包括"能碰但推不动"这种半合法状态 —— 这是陷阱测量的来源。
3. **记录现场，不只记录胜负**。死局时的快照比胜率有用十倍。

## 二、三种策略

### naive —— 看到就点

```
def naive(legal, state):
    return legal[0] if legal else None
```

- 语义：永远点列表第一个（**不判断推不推得动**）。
- 期望：**必输**，且死得很快（通常 = 并发位数）。
- 如果它赢了 ⇒ 该单元没有决策。

### human —— 会看但会算

```
def human(legal, state):
    advancing = [a for a in legal if state.can_advance(a)]   # 真的有供给
    fresh = [a for a in advancing if state.category(a) not in state.occupied_categories()]
    if fresh: return fresh[0]        # 优先"该类还没占并发位"
    if advancing: return advancing[0] # 没有新的就消耗已有的
    return None                       # 一根都没有 ⇒ 等，绝不硬凑
```

- 语义：会看"推不推得动"，且**同类不重复占并发位**。
- 期望：**必赢**。
- 它输了 ⇒ 要么内容有死局，要么策略还缺一条常识（见 §四）。

### greedy —— 手快不做计划

```
def greedy(legal, state):
    ok = [a for a in legal if state.can_advance(a)]
    return ok[0] if ok else None
```

- 语义：只按"此刻能不能推进"排序，**同类照叠**。
- 期望：**只作参考**。它输是常态 —— 把并发位填成一组"此后都不再前沿"的同类，自己把自己锁死。
- **不能**用它判断内容是否有解。

## 三、判定表

| naive | greedy | human | 结论 | 动作 |
|---|---|---|---|---|
| 输 | 任意 | 赢 | **合格的难度内容** | 收 |
| 赢 | 任意 | 赢 | 无决策（走过场） | 加并发压力或加陷阱，重测 |
| 输 | 任意 | 输 | 疑似死局 **或策略太笨** | 先补策略常识（§四）重跑；仍输才是死局 |
| 输 | 赢 | 赢 | 决策来自"陷阱辨识"而非"节奏" | 正常，记录难度载体 |

**难度有两个独立载体**，判定时要说清是哪一种：

| 载体 | 玩家在决定什么 | 症状 |
|---|---|---|
| 陷阱辨识 | "亮的里面哪个真能推进" | 开局可点集合 ≫ 可推进集合（T 高） |
| 节奏规划 | "这一类点几个、按什么顺序" | 待处理单元数 ≫ 并发位（C 高） |

> 反直觉但实测成立：**陷阱率 0 不等于零决策**。有的内容开局"可点集合 == 可推进集合"，
> 但待处理单元数是并发位的 10 倍以上，naive 照样点 4 下就死。

## 四、human 策略的常识补充（按需）

拟真策略输了，先按顺序试这几条，每条都是一个"真人一定会的常识"：

1. **同类不重复占并发位**（最常见的一条，解决 80% 的假死局）
2. 优先推进"只剩最后一格"的单元（收尾优先）
3. 避免把并发位交给"此后不再前沿"的类别（前瞻一步）
4. 供给紧张的类别优先用掉（稀缺优先）

补完还是输，才判定内容无解。**每次补常识都要记录：哪条常识让败局翻盘** —— 那就是玩家必须学会的策略，也是内容的真实难度来源。

## 五、死局分类（写进报告时用）

| 类型 | 现场特征 | 病根 |
|---|---|---|
| **同类叠满** | 并发位里全是同一类，而该类的供给一次只够喂一个 | 拆分过细 / 玩家重复点同类 |
| **供给断流** | 并发位里的类，之后再也不出现在前沿 | 组合陷阱：先占满 4 个"此后不前沿"的类 |
| **陷阱塞满** | 并发位里全是"能碰但推不动"的 | 陷阱密度过高，人手会误点 |
| **规则级锁死** | 所有动作都非法，且不是玩家操作造成 | 内容本身有缺陷（生成期就该拦住） |

前三类是**设计问题**（可调），第四类是**数据缺陷**（必须修）。

## 六、sweep 骨架

```bash
# 全内容 × 全策略，只取机器可读行
for id in $(seq 1 $N); do
  for s in naive greedy human; do
    node scripts/_bot_play.mjs "$id" "$s" 3 | grep RESULT
  done
done
```

RESULT 至少包含：

```json
{"id":13,"strategy":"naive","win":false,"clicks":4,"ratio":0,"idlePicks":4,
 "slotMax":4,"deadlock":{"occupied":["A","A","A","A"],"front":["B","C"],"left":46}}
```

- `idlePicks` = 点了"推不动"的次数；等于并发位时基本就是秒死。
- `deadlock` 是死局现场，报告里直接引用它，比"胜率 0%"有说服力。

## 七、已知的假失败

- **无头浏览器帧率极低**（软件渲染常见 8–12fps）：等待必须用"等真实条件"，不能用固定 `sleep`；动画结束事件可能永远不触发。
- 一个校验脚本偶发 1/3 概率失败、重跑就过 ⇒ 先怀疑帧率，不要急着改内容（但要在文档里标注"已知假失败"）。
- 批量跑时把每条用例的超时设成单条上限，卡住即判失败，不要无限等。
