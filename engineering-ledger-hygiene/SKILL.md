# 工程记忆与约定账本的自维护 (engineering-ledger-hygiene)

## 一、定位与职责

长周期多轮项目里，真正会拖垮后续轮次的不是代码，而是**知识腐烂**：半年后没人知道「当前口径到底是什么」「哪条约定是为了避免哪个坑」「上周那个决定还作不作数」。

本 skill 管这套知识的**养护**（生命周期），不管它的**存储实现**。它解决四类腐烂：

| 腐烂形态 | 症状 | 后果 |
|---|---|---|
| **截断** | canonical 主档写太长，超注入上限被截掉 | 关键口径静默丢失，下一轮按旧口径做 |
| **计数过期** | 约定文件里自述的「N 条断言 / M 页」改脚本后没回头改 | 权威值失真，越查越错 |
| **决策反复** | 用户说「保持 X」，下一轮又被当成「待办」重新提一遍 | 反复返工、信任损耗 |
| **日志膨胀** | 逐轮日志无限累积，检索成本爆炸 | 想找的东西找不到 |

**适用**：跨多轮、多会话、有「当前权威口径」概念的项目（原型工程、文档工程、长期演进的产品/平台）。
**不适用**：一次性任务、单会话脚本。

**与 `project-knowledge-base` 的关系**：那个 skill 解决「**查**」（query / add / update / list，按分类存取）；本 skill 解决「**养**」（何时重写、谁下沉、计数怎么保鲜、决策怎么钉死）。二者互补：本 skill 定义生命周期与卫生协议，存储可落在文件（参考实现）或 PKB 之上。

**核心原则**：**账本不是档案馆，是操作仪表盘。** 同一份知识只应有一个「当前权威」位置，其余位置要么派生、要么标注为历史。

## 二、三层结构（缺一层都会烂）

| 层 | 文件（参考实现） | 性质 | 写入纪律 | 体量 |
|---|---|---|---|---|
| ① **canonical 主档** | `MEMORY.md` | **当前权威口径** + 不可丢的产品契约 | **原地重写**（非追加） | **有注入上限，超限被截断** ⚠ |
| ② **规则账本** | `ENGINEERING_RULES.md` | **改任何文件前必读**的工程约定（踩过的坑转成的前置约束） | 原地增改 | 随轮次增长 |
| ③ **流水日志** | `memory/YYYY-MM-DD.md` | 逐轮做了什么 | **append-only，绝不重写** | 无限累积（到期下沉） |

**分工口诀**：
- **能算出来的口径** → 主档（但要标权威源，如「权威值取 `build_report.py`」）。
- **「如果不写下来我下次一定会再踩」的** → 规则账本。
- **「这一轮具体做了什么」** → 日志。

**最关键的不变式**：**主档只放当前口径**（历史口径要么移入「已推翻的旧口径」小节并标日期，要么删除）。主档一旦混入历史，下一轮就会把旧口径当现行。

## 三、六条自维护机制

### M1 注入上限驱动重写（被动告警 → 主动重排）

**触发信号**：主档写入后**超出注入上限**（表现为被宿主截断、或注入内容末尾缺失、或工具提示超限）。

**处置流程（重写，不是追加）**：
1. **判定**：对比主档长度上限，确认确已超限。
2. **扁平化**：把长段落压成表格 / 短句（保留判据，删推导过程）。
3. **下沉**：把「推导过程、历史分支、细节参数」下沉到规则账本或**伴生明细文件**（如 `DETAILS.md`，按主题分节、主档只留指针），主档只留结论 + 指针。**明细外置比无限压缩正文更可持续** —— 压缩到一定程度后可执行判据会被压丢。
4. **清旧**：把被后续轮次推翻的口径移入「已推翻的旧口径」小节并**标注日期**（或直接删）。
5. **复检**：重写后再量一次长度，确认留有余量（不贴上限写）。

> 要点：**主档的长度上限是硬约束，不是建议。** 靠「少写点」维持不了，必须靠「重排 + 下沉」。

### M2 决策显式固化（阻止同一决定被反复推翻）

**触发信号**：用户说出**任何**「就这样 / 保持 / 不要改 / 以这个为准」式的决定 —— 哪怕只有一句话。

**处置**：
1. **立即**写进规则账本（不是只记在心里、不是只留在当轮对话）。
2. 在主档对应条目**标注**：`（用户 YYYY-MM-DD 决定，勿改）`。
3. 若该决定是「**保留某个看起来不统一的东西**」，必须同时写清**为什么保留**（否则下一轮会被当成「不一致待修」）。典型：动态标签、归档页的例外层级、刻意的列宽不齐。

**反模式**：把决定只写进当轮日志 ⇒ 下一轮读主档/规则时看不到 ⇒ 又提一遍。

### M3 计数即测即写（防腐烂协议）

**问题**：规则账本里大量自述计数（「N 条断言」「M 页」「K 个文件」），改脚本后没人回头改注释 ⇒ **大面积过期**，且**越权威越误导**（因为它自称权威）。

**协议**：
1. **同一步骤内刷新**：任何门禁 / 脚本的数字改动，**在改该脚本的同一轮**里刷新自述行，别攒着。
2. **权威值一律现跑现取**：主档里凡涉及计数，必须写明「**以某某脚本现跑输出为准**」，并把该脚本路径写出来。
3. **定期体检**：每若干轮跑一次「自述计数 vs 实测」比对，把过期项一次性刷新（并记录在日志）。
4. **宁可写指针，不写数字**：能指向权威源的，就不要在主档复制数字。

### M4 账本即改前门禁（把坑转成前置约束）

规则账本的第一用途不是「查」，是「**改前必读**」。因此：

- 账本顶部写明：**「凡涉及 X / Y / Z 的改动，先读本文件」**。
- 每条约定写成**可执行判据**，不是「小心点」：
  - 反例：「注意行尾问题」
  - 正例：「判 CRLF 用 `crlf > 0 and crlf >= lf * 0.9`（纯 CRLF 时两计数恒相等）」
- 一条约定 = 「**一个已证实的坑 + 一条可执行判据 + （可选）来源轮次**」。来源轮次让后来者能追溯为什么。

### M5 日日志 append-only + 到期下沉

- 日志**只追加**，不重写（重写会破坏「当时到底怎么想」的记录）。
- 日志**不记**瞬态信息（临时路径、工具报错、搜索结果）—— 那些没有跨会话价值。
- **超过沉淀阈值的老日志**（如 30 天）→ 按主题**蒸馏**进主档或规则账本，再删除原文件。蒸馏时只留「仍然成立」的结论。

### M6 并发会话的红项归属判定（基线复现法）

**触发信号**：多个会话/窗口并行推进同一项目，收工前跑门禁出现**与本轮改动看似无关的红项**。

**协议**：
1. **先在起点基线复现**：把本轮起点快照（回滚点 / `current.prev.zip`）解包到**临时目录**（勿污染工作区），在基线树上复跑该门禁。
   - **基线上同样红** ⇒ 既有陈旧门禁，**非本线引入** —— 不修（属在建轮次的收口范围），日志记一句「仍红：他线在建轮次，非本轮引入」。
   - 基线上是绿的 ⇒ 本线（或并发写入）引入，必须处理。
2. **日志记并发窗口**：每轮日志记一句「本窗口（HH:MM–HH:MM）他线未写入 / 有写入」，给后续归属判定留时序证据。
3. **勿顺手修他线红项**（除非用户指派）：中途接手他线的半成品门禁，容易与其轮次收口互相踩。

> 真实形态：同一项目连续 4 个轮次里两条门禁红着（菜单重分类 117/22、订单冒烟 TypeError），每轮日志都靠基线复现确认为「他会话在建轮次」，直到该轮收口才由其修复。**没有基线复现，这些红项要么被盲目「顺手修」，要么被误判为本线事故。**

## 四、每轮收工仪式（把养护嵌进日常）

```
1 落盘/验证完成后：
2   ├─ 本轮有新「坑」？        → 写一条可执行判据进【规则账本】
3   ├─ 本轮有用户决策？        → 【规则账本】+ 【主档】标「用户 YYYY-MM-DD 决定」
4   ├─ 本轮改了门禁/脚本计数？  → 同轮刷新【规则账本】自述行（M3）
5   ├─ 有与本轮无关的红项？    → 基线复现定归属（M6），勿盲目修；日志记并发窗口
6   └─ 本轮做了什么？          → 追加一行进【当日日志】（append-only）
6 量【主档】长度：超限？        → 触发 M1 重写 + 下沉
7 若本轮推翻了旧口径：         → 【主档】旧口径移入「已推翻」并标日期
```

## 五、主档重写流程（M1 展开）

```
A 备份：先复制当前主档（重写唯一回滚）
B 盘点：逐条问「这条现在是权威口径吗？」
      现行 → 保留（压缩为表格/短句）
      被推翻 → 移入「已推翻的旧口径」+ 日期，或删除
      可派生 → 删数字，留权威源指针
C 分层：详情/推导 → 下沉到规则账本或专题文件；主档留结论+指针
D 重写：平地重排（按主题分节，不按时间）
E 复检：长度留余量；关键契约（不可丢的东西）逐条核对仍在
F 记录：日志里记一句「主档重写：压缩 X → Y，下沉 Z」
```

**「不可丢的产品契约」清单**（重写时逐条核对，别压缩掉）：
- 当前唯一的权威计数与它的权威源
- 各端 / 各角色 的职责边界
- 命名与标识的「不统一」约定（哪些刻意不统一）
- 现役状态机 / 口径的 canonical 定义
- 快照 / 基线档位

## 六、产出契约

| 产出 | 说明 |
|---|---|
| `MEMORY.md`（或等价主档） | 当前权威口径，长度受控，含「已推翻旧口径」小节 |
| `ENGINEERING_RULES.md`（或等价账本） | 可执行判据清单 + 顶部「改前必读」声明 + 权威源指针 |
| `memory/YYYY-MM-DD.md` | append-only 日日志 |
| `hygiene-report.md`（按需） | 本轮养护动作：新增约定 / 固化决策 / 刷新计数 / 主档重写前后长度 |

## 七、质量检查清单

- [ ] **主档未超注入上限**，且未贴着上限写（留余量）。
- [ ] 主档里**没有历史口径**（被推翻的已移入「已推翻」小节并标日期，或已删）。
- [ ] 主档里每个计数都写了**权威源**（「以 X 脚本现跑为准」），没有裸数字。
- [ ] 本轮用户的每个「保持/不变」决定都已写进**规则账本** + 主档标注日期。
- [ ] 本轮改动的门禁/脚本计数，其自述行已**同轮刷新**。
- [ ] 规则账本里每条约定都是**可执行判据**（不是「小心点」），且标了来源轮次。
- [ ] 规则账本顶部有**「改前必读」声明**，指明了涉及哪些改动要先读。
- [ ] 当日日志**只追加**、未重写；未记录瞬态信息。
- [ ] （并发）无关红项已用**基线复现法**定归属；日志已记并发窗口观察。
- [ ] 「不可丢的产品契约」在重写后**逐条仍在**。
- [ ] 老日志（超阈值）已蒸馏下沉，原文件已删。
