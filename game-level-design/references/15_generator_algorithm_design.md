# 15 生成路径的算法选型（从游戏事实推出"要哪些算法"）

> 本文回答：**给定这个游戏的类型、机制、设定、玩法，关卡生成路径需要哪几个工位、每个工位用什么算法、什么情况下不用。**
> 它不回答"怎么写拼豆生成器"——那是具体实现，见 §7「不可搬运清单」。
>
> 与 `references/14` 的分工：**14 定"解从哪来"**（手调 / 生成器 / 导入；生成器内部再分「反向构造 vs 正向筛选」），**15 定"路怎么走"**（工位与算法）。
> 先有 14 的路线，才轮到 15 的工位。走"手工"路线的项目不需要读本文。

---

## 0 一句话

生成路径 = **五个工位**（内容量化 → 资源分配 → 布局与依赖 → 可解性验证 → 难度打分）。
不是每个游戏都要五个：**每个工位都要用"游戏事实"换，换不到就砍掉**，砍掉一个工位省一份实现和一份永远调不好的参数。

---

## 1 判定链：先决定要几个工位

按顺序回答五个问题，每个"否"砍掉一个工位。答案要写进 `docs/LEVEL_GENERATOR_SPEC.md` §2，**写下来才算数**。

| # | 问题 | 答"是"→ 开哪个工位 | 答"否"→ 怎么办 |
|---|---|---|---|
| Q1 | 局面离散、可枚举、可序列化？ | 全部可能（同 `references/14` §1） | **不做生成器**，回 14 走手调 |
| Q2 | 关卡内容来自图像/画稿？ | 工位 A 量化 | 砍掉 A，内容由参数直接给出 |
| Q3 | 有"资源容器"（库存/线轴/手牌/预算/血量）？ | 工位 B 分配 | 砍掉 B，资源由用户规则决定 |
| Q4 | 有空间依赖（遮挡/邻接/可及性/路径）？ | 工位 C 布局与依赖 | 砍掉 C，布局退化为"无约束摆放" |
| Q5 | 规则可编码 **且** 状态空间能在预算内搜完？ | 工位 D 验证 | **保留生成器但降级**：只生成候选，可解性靠人工抽查并标注 |

**Q5 答"否"是常态，不是失败**。此时生成器的定位从"保证可解"变成"提高候选命中率"，
必须在 `LEVEL_GENERATOR_SPEC` 里写明"可解性未经机器验证"，否则下游会把它当已验证数据用——
这是本流水线里最容易传染的一种假绿。

工位 E（打分）默认都要开，除非关卡数 < 30（那时人工挑更快）。

## 2 五工位算法选型

每行都给了"什么时候不用这个算法"——**选型的一半价值在排除**。

### A 内容量化（输入是图时）

| 算法 | 适用 | 别用它的情形 | 典型失败 |
|---|---|---|---|
| K-means / 中位切分 | 画稿颜色多、要自动收敛到 N 色 | **颜色是机制旋钮**（颜色数直接改难度）时别用——K-means 给的颜色数不可控、不可复现 | 同一张图两次量化出不同色数，关卡难度漂移 |
| 固定调色板（最近邻映射） | 颜色数由设计定死 | 画稿本身色域跨度过大 | 大片区域被压成一块，形体丢失 |
| 有序抖动 / 误差扩散 | 要保细节、可接受噪点 | 下游有"同色连通块数"约束时 | 碎块暴涨，关卡碎度失控 |

**量化后必须算一个指标**：`同色连通块数 / 该色像素数`。
它直接决定关卡碎度与操作步数——量化完不看这个数就进工位 B，等于把难度交给了图片本身。

### B 资源分配（有容器时）

| 算法 | 适用 | 别用它的情形 |
|---|---|---|
| 贪心装箱（按容量降序首次适配） | 容量种类少、需求大 | 要求"容量分布有设计感"时（贪心会堆出大量同规格） |
| 最大余数法 | 需要精确凑总和不产生零头 | 容量有下限约束 |
| 整数规划 / CP-SAT | 关数少、约束多（如"每关必须有 1 个极小容器"） | 批量生成时——求解时间不可预测 |

**硬约束是守恒式，不是不等式**（见 §3 I1）。材料里"总容量 ≥ 需求，留 10–20% 容错"这条要改：
多出来的容量如果没有合法去处，那根容器**永远消耗不掉**，正向玩到最后必卡死。

> 反过来还要留神一个反直觉结论：**精确分割会让托盘压力恒等于 0**（证明见 `references/16` §7.1）。
> 也就是说"容量库怎么调都不会有压力"是正常现象——压力只能来自余量、干扰项或跨色顺序约束。
> 照抄容量库却发现关卡全都轻松通过时，先看这条，不要去调容量分布。

### C 布局与依赖（有空间关系时）

| 算法 | 适用 | 别用它的情形 |
|---|---|---|
| 随机撒 + 事后查冲突 | 无遮挡、只要求不重叠 | 有遮挡层级时——随机撒几乎不可能满足可达序 |
| 分层拓扑（先生成依赖图，再按拓扑序自底向上摆） | 有遮挡/解锁链 | 依赖图本身有环（说明机制设计有问题，先改机制） |
| 生成树 / 连通性约束 | 要求全图可达 | 允许孤立区域是设计意图时 |

**布局的第一约束不是"好不好看"，是"需求序 ⊑ 可达序"**（见 §3 I2）。

### D 可解性验证（最关键、最容易做错）

| 算法 | 适用 | 代价 |
|---|---|---|
| DFS + 记忆化 | 状态空间中等、规则简单 | 完备但会爆；必须配剪枝与状态哈希 |
| A*（可采纳启发） | 需要"最短步数"而不只是"能不能" | 启发函数写错就不完备，会把有解判成无解 |
| 双向 BFS | 目标态唯一且可描述 | 只适合终局唯一的游戏 |
| 迭代加深 | 解通常很短（≤15 步） | 深解场景退化成 DFS |

剪枝三件套（**缺一条就会在批量生成里超时**）：

1. **死锁判据**：所有容器已满 且 没有任何一次操作能释放容量 → 判死锁，立即回退
2. **容量上界**：某色 `need[c]` > 该色**全部存活容器的剩余容量之和** → 该色永远凑不齐
   （**不是"可达/可见容量"**：被压住的容器在取走上层后同样可用，按可见求和会把可解局面判死、静默丢好关，见 `references/16` §4 剪枝 2）
3. **状态记忆化**：`(剩余需求, 可见对象集合, 容器状态)` 哈希后查表；命中直接返回

另外两条工程手段（不是算法，但决定能不能跑完一批）：

- **状态压缩**：把"每种颜色的剩余量 + 容器占用"压成整数位段，用位运算代替对象比较
- **多进程**：关卡之间独立，天然可并行；单进程跑一夜的量，多进程一小时

### E 难度打分

| 做法 | 适用 | 陷阱 |
|---|---|---|
| 蒙特卡洛随机策略跑 N 次 | 只看"能不能通" | **随机策略通过率 ≠ 难度**：随机走法在简单关也常失败 |
| 两种极端策略对跑（naive / strict） | 判"有没有决策" | 需要两套策略，见 `templates/LEVEL_AUTHORING_template.md` §7 四格表 |
| 真人样本校准 | 上线前定标 | 贵；样本 <30 次/关不下结论 |

打分只解决"排序"，不解决"这关好不好玩"。好玩与否必须回到 `tools/design_review.py` 的八维量尺，
且先过第 0 节体检——**量尺坏了，生成器的打分再精细也是噪声**。

## 3 四条不变量（漏一条就会批量产出废关）

这四条是"生成一万关全都能玩"和"生成一万关里九千九百关卡死"的分界线。每条都给反例和验法。

### I1 容量守恒
**Σ容器容量 = 需求总量 + 允许剩余**，且"允许剩余"必须在规则里**有明确去处**（可弃置 / 可结算 / 可带出）。

- 反例：需求 300，给了 350 的容量，多出的 50 无处安放 → 玩家拿满托盘也消不掉那根 → 必输
- 验法：`assert Σcap - need == 可弃置数量`，不允许"大约"

### I2 需求序 ⊑ 可达序
第 k 步需要的对象，不能被第 k+1 步才解锁的东西压住。遮挡关系的拓扑序必须与消耗序一致。

- 反例：画布还要 3 个红，红全被"只有消完蓝才能拿"的层压着，而蓝的需求已经满足 → 死锁
- 验法：对每条依赖边 `u → v`（u 压着 v），断言 `need_time(u) ≤ need_time(v)`
  —— 先取走压在上面的 u，才轮得到 v 被需要。**方向写反会把正确关卡全判成违规**，
  这个断言也就失去了作用；`references/16` §3 用层号 `<` 直接保证这一条，不必事后查。

### I3 干扰项可处置
画布不需要的对象，必须有"消耗后能丢弃/换出"的路径。

- 反例：塞了 30% 干扰项、放在底层，玩家刨出来后托盘塞满、既不能消也不能丢 → 必输
- 验法：干扰项数量 ≤ 容器的"可临时占用 + 可弃置"总量

### I4 托盘压力上界
存在**至少一条**不超容的消耗序（不是"平均压力低"）。

- 反例：逆向时"托盘快满就补一个匹配色"——补完之后托盘仍然是满的，只是这一手能走，下一手继续满
- 验法：验证器输出"峰值占用 / 容量"这一比值；峰值 = 容量 说明零容错，玩家一步都不能错，
  这通常不是"地狱难度"，是"设计失误"

> I4 是对材料里"强制收敛托盘"那条的修正：**补一个匹配色只能救一手，救不了整局**。
> 正确做法是让构造阶段维护"当前压力 ≤ 上限"，而不是事后打补丁。

## 4 反向生成 vs 正向生成 + 筛选

成本模型很简单：

- 正向：单次验证成本 `c`，一次通过率 `p` → 期望成本 `c / p`
- 反向：构造成本 + 少量验证

**当 `c / p > 构造成本` 时选反向**。死锁率 99% 的场景（材料里提到的）确实该走反向。

但反向有个必须写进文档的前提：**它保证的只是"存在性"，不保证解路数、不保证节奏、不保证难度分布。**

"反向生成无需验证"是错的。反向之后仍要跑验证器，只是验证目的变了：

| 路线 | 验证器回答的问题 |
|---|---|
| 正向 | 有解吗？（存在性） |
| 反向 | 解有多少条？最短解多长？峰值压力多少？（P2/P3/I4） |

省掉这一步，产物就是"一定能通关，但只有一条路、走完全程都在挤托盘"的关卡——
数据上通过率 100%，体验上是"照着唯一路径点完"。见 `references/14` §3 P2、§4.1。

## 5 工程约束：什么时候才需要 C++/Rust

材料建议"生成与验证用 C++/Rust 编译成 DLL"。这个建议在**特定规模**下成立，但有前提：

| 判据 | 阈值 | 结论 |
|---|---|---|
| 单关验证耗时 | < 200ms | Python 足够，多进程即可 |
| 单关验证耗时 | 200ms–2s | 先做状态压缩 + 记忆化，别急着换语言 |
| 单关验证耗时 | > 2s 且批量 ≥ 1000 关 | 才考虑原生扩展 |

> 这三个门槛是**经验起点，不是行业标准**。用你自己项目的实测值替换它们，并把替换后的数字写进 `LEVEL_GENERATOR_SPEC` §8 的耗时表。

**反例**：一开始就用 C++ 写，规则一改就要重编译、重调接口，迭代速度才是真瓶颈。
生成器的规则在前期几乎每周变，先把算法跑对，再考虑换语言——这是"过早优化"在关卡生成上的典型形态。

真正决定性能的是这三件事，语言排在后面：**状态压缩、记忆化命中率、剪枝强度**。

## 6 交付物：`docs/LEVEL_GENERATOR_SPEC.md`

走"生成器"或"导入"路线时必产。九节，模板见 `templates/LEVEL_GENERATOR_SPEC_template.md`：

① 生成目标与规模（关数/时长/验收口径）② 工位开关（§1 五个问题的答案）③ 每工位算法与参数 ④ 四条不变量的裁决
⑤ 验证器规格（状态定义/剪枝/预算）⑥ 失败回流策略（回哪个工位、重试上限）⑦ 已知限制 ⑧ 批量运行方式与耗时 ⑨ 变更记录

**②④ 是硬性内容**：没有"工位开关"，读的人不知道你为什么不上验证器；没有"不变量裁决"，读的人不知道这些关为什么不会卡死。

## 7 工位适用性检查表 & 不可搬运清单

> 这张表问的是"**五个工位还成不成立**"。问"三条路线还能不能走"的是另一张表，见 `references/14` §6。

换游戏时逐条问（任一"否"就调整设计，别硬套）：

| # | 问题 |
|---|---|
| 1 | 把"线轴/画布/托盘"换成我这游戏的对应物后，五个工位还成立吗？ |
| 2 | 我的"需求"是可计数的量吗？（若需求是"达成某个状态"，工位 B 可能整个不存在） |
| 3 | 我的"容器"有容量上限吗？没有上限就没有 I1/I4，压力类难度也就不存在 |
| 4 | 我的空间依赖是遮挡还是邻接？邻接类（路径/连通）用生成树，不用分层拓扑 |
| 5 | 干扰项在我的规则里能丢弃吗？不能就限制它的数量（I3） |

**不可搬运**（属"拼豆-线轴"本作参数，换游戏即失效）：

| 项 | 为什么 |
|---|---|
| 7×6 = 42 格盘面 | 本作 UI 尺寸 |
| 容量库 `[1, 10, 25, 35, 50]` | 本作数值设计，直接决定难度手感 |
| 托盘 6 格 | 本作难度旋钮 |
| "干扰项 0% / 10% / 30%" 分档 | 分档值不可搬，但"分档"这个做法可搬 |
| 反向填盘的具体拓扑构造 | 依赖本作几何，抽象层见 `references/14` §2 |
