# 12｜评审门禁、验收与上线治理

## 1. 门禁规则

`design_review.py` 每次运行都会给出 `PASS / FAIL`：

- **FAIL**：存在任一 HIGH 级诊断，**或**任一「结构性必赢」命中（`TRIVIAL_BY_CONSTRUCTION`）。
- **PASS**：只有 WARN / INFO。
- 加 `--strict` 时 FAIL 会以非 0 退出码结束，可直接用于 CI / 提测卡口。

门禁只看"是否阻断"，不评价"做得好不好"。质量高低靠下面的验收清单。

> 结构性必赢为什么也阻断：它不是"这一关偏难/偏易"，而是"这一关的难度分描述了一个不可能发生的事件"。
> 允许它通过，等于允许下游拿一个无效数字去做决策。

## 2. 报告验收清单

一份可交付的评审报告必须能回答这 6 个问题，缺一项就算未完成：

- [ ] 目标是什么（阶段、形状、目标首通率区间）？
- [ ] 现在预测成什么样（逐关预测 + 与目标偏差）？
- [ ] 不同水平玩家会怎么表现（分层首通/终通/尝试/道具/种子波动）？
- [ ] 哪里有问题、证据是什么（类型 + 数值 + 主因维度）？
- [ ] 建议动哪个参数、预期变成多少、副作用是什么？
- [ ] 哪些是假设、下一步怎么验证、失败怎么回滚？

另外检查：

- [ ] `data_source` 写清是否真实数据；未接入时报告必须显式声明"纯模型预测"。
- [ ] 样本量 < 30 的关卡没有任何调参结论。
- [ ] 预测与实际背离的关卡，结论是"先查模型"而不是"先改关卡"。
- [ ] 推荐值都在合法范围内，且不超过 `max_delta`。

## 3. 模型卡（最小版）

每个上线的难度模型（评分权重 + 映射 + 推荐敏感度）都要有一张卡片，
模板见 `templates/model_card.md`，至少包含：

| 字段 | 说明 |
|---|---|
| 版本号 | 与 campaign.json 的 `version` 对齐 |
| 适用品类/模式 | 换品类必须换权重，不能沿用 |
| 特征定义与口径 | 8 个维度各自的取值来源与归一化方式 |
| 参数与权重 | 权重、`spread`、θ、`per_unit` 的具体值 |
| 训练/校准数据窗口 | 时间范围、版本范围、玩家范围 |
| 评估结果 | AUC / LogLoss / Brier、分群误差 |
| 已知偏差 | 例如"对高随机性关卡低估难度" |
| 回滚版本 | 上一个可用版本号 |

## 4. 上线节奏

1. **离线回放**：拿历史关卡 + 历史通关数据跑一遍，看预测排序与实际是否一致（Spearman 相关优于绝对值误差）。
2. **Shadow**：线上实时算但不影响玩家，记录"如果按建议调会怎样"。
3. **小流量实验**：单变量、1–2 个关卡、玩家级随机化。
4. **扩量**：护栏稳定后扩到同阶段。
5. **长期监控**：模型漂移（预测与实际差值的移动平均）、不可解率、道具消耗、继续率。

## 5. 阈值变更纪律

阈值（`jump_winrate`、`band_tolerance`、`unstable_sd` 等）允许改，但必须留痕：

1. 写明**为什么**改（例：真实数据显示 8pt 的跳变并未引起流失上升）。
2. 写明**影响范围**（哪些关卡从 FAIL 变 PASS、哪些从漏报变检出）。
3. 用**历史数据回归**验证：改完后重跑 3 个以上已上线战役，确认不会集体变绿。
4. 记录在案：谁批准、生效版本、复核日期。

**禁止**为了让报告变绿而调宽阈值。判据是尺子，改尺子不等于把东西做对。

## 6. 与团队分工的接口

| 角色 | 用报告里的什么 |
|---|---|
| 关卡策划 | 第 2、4、6 段：目标/跳变/建议；按单变量方案改配置 |
| 数据分析 | 第 3、7 段：分层模拟与预测-实际对比；负责校准 `spread`/θ/`per_unit` |
| 主策/制作人 | 第 1、8、9 段：结论、假设、下一步；决定是否放行 |
| QA | `diagnosis.csv` 里的 NEAR_UNWINNABLE / BLOCKER：优先构造可解性用例 |
