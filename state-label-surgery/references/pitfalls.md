# 状态 / 标签 / 链路手术 —— 坑与判据速查

> 来源：真实项目多轮状态变更（7 态子单、标签正名、删整条链路、部分回退）中**已证实**的问题。每条给「现象 → 判据 → 修法」。

## S1 改名被当成改状态机（改动面失控）
- **现象**：用户说「把这两个状态名改一下」，按「重构状态机」的思路动手，补了数据样本、改了渲染分支、动了一堆断言。
- **判据**：把用户链条与实现链条**逐态比对**，若位次与数量一致、只差文案 ⇒ 是纯改名。
- **修法**：先判拓扑。纯改名收敛为纯文本替换，改动面直降。

## S2 只改了可见文案，函数名/元素 id/键名没改（半截旧码）
- **现象**：按钮文案从「改名」改为「编辑」，但 `openRename` / `renameDlg` / `rnName` / `renamingId` 等旧命名还在。
- **判据**：全仓 grep 旧词根，看是否只剩「文案层」命中。
- **修法**：中文标签 + 表单字段 + 函数名 + 元素 id + 键名 + 二次确认文案 + 成功提示**成套改**。

## S3 标签→码缩表没同步 ⇒ 一致性检查静默跳过
- **现象**：标签改了，校验脚本的「标签→码」缩表没改。检查仍然全绿 —— 因为它按新标签找不到匹配，直接跳过了。
- **判据**：看扫描器是否打印「已比对 N 项」；若 N 骤降或为 0，即空转。
- **修法**：清点缩放表**全部副本**，逐处同步 + 加等价断言。

## S4 投影缺样本 ⇒ 渲染分支永不可见
- **现象**：页面按状态分支渲染操作按钮，但该端的投影数据里没有这个状态的样本，用户永远看不到这个分支。
- **判据**：覆盖扫描器求「代码引用状态 − 投影实含状态」，非空即有缺口。
- **修法**：补样本（跨端共享块两处同改、逐字节相同）+ 补渲染处置 + 固化为常设门禁。

## S5 同词不同义被一把梭
- **现象**：改「商家开票」时，把「局办审核 > 商家开票 > 打款」里的动作短语也一起改了；或改「改名」时把「节点改名」也动了。
- **判据**：逐处判断该命中是「状态标签 / 步骤条节点名」（要改）还是「业务动作短语 / 无关同形词」（不改）。
- **修法**：逐处判语义再决定，禁止全局一把梭。

## S6 部分回退连带清掉不该动的
- **现象**：用户只要求把 A 改回原名，全局替换式回退顺手把 B 的新改动也清了。
- **判据**：回退后断言「B 的新标签仍在位」「B 的映射表双向在位」「共享块逐字节相同」。
- **修法**：定向回退（只反向替换 A 的串 + 手工修 A 专属处）；留 A 改名前的基线快照做逐字节黄金校验。

## S7 删整条链路留下半截
- **现象**：删一条链路只删了手动入口，命令码/字段/标签/相邻规则里的同形用法还在；或被禁词表的合法术语（如 `fiscal supervised account`）被误伤。
- **判据**：分级侦查是否覆盖「入口/命令码/字段/标签/他处同形」；终检是否排除子串误伤（`voucherStatusOf` 含 `voucherStatus`）。
- **修法**：六件套（侦查 → 失配批量收集 → 禁词表带引号 → 按文件放宽护栏 → 子串防误伤 → 同步验证器旧断言）。

## S8 EOL 归一化被误判为内容膨胀
- **现象**：CRLF 文件改完，字节数「涨了 N 字节」，被误以为内容变多。
- **判据**：`load()` 归一到 LF 后 `n0` 是 LF 长度、`nb` 是**还原后**长度 ⇒ CRLF 文件涨的字节**恰等于行数**。
- **修法**：判 CRLF 用 `crlf > 0 and crlf >= lf * 0.9`（纯 CRLF 时 `\r\n` 与 `\n` 计数恒相等，直接比较会误判）。

## S9 派生件用文本变换比对
- **现象**：含内容 hash 的派生件（构建报告）被纳入「改前快照 + 预期变换」比对，永远对不上。
- **判据**：该文件是否含需要重算的 hash。
- **修法**：派生件单列判据 —— hash 变化集合恰等于预期集合 + 全量 hash 与磁盘实算一致。

## S10 动态标签被「统一」
- **现象**：一个标签的值随上下文变化（如确认方随发起方变），有人想把它统一成单一文案。
- **判据**：该标签是否依赖上下文参数。
- **修法**：保持动态；三处实现（PC 共享表 / 共享标签函数 / 移动端内联三元）必须一致；静态漂移自检里**刻意排除**动态项（写进去会恒失败）。

## S11 概念退役删成「半下线」（最重的事故形态）
- **现象**：领域概念（如「推送渠道」）退役时，页面删了列、共享库却留着常量与函数族；或样本留了运行期 remap —— 门禁全线红，且没人知道该以哪边为准。
- **判据**：旧概念的标识符（常量名/函数名/字段名）全仓 grep 是否 = 0；是否留有 remap；门禁断言是「同步数字」还是「按新口径重写」。
- **修法**：走八件套 —— 影响面盘点（含共享库**函数族**）→ **先接替代源**再删旧概念 → 样本改型不留 remap → 同批删完 → 门禁断言重写 + 负向断言（旧概念 = 0）→ 作废 BR 登记 → 收口 grep → 快照反向 diff。
- **真实案例**：渠道下线轮删 `CHANNELS`/`channelUsable` 等 11 个共享库函数、BR-603/610 作废、密钥页整页改应用维度（信息取自应用授权页共享库）—— 因坚持整批完成 + 断言重写，356 断言一次转绿。
