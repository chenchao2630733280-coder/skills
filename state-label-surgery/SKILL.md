# 状态机 / 标签 / 链路手术 (state-label-surgery)

## 一、定位与职责

本 skill 专职**业务状态及其显示标签、流转链路的变更手术**。它处理的是批量文本改写里**最危险的那一类** —— 因为一个状态不只活在「一处文案」里，它同时活在：

- **数据**（样本 / 种子 / 总账里的状态码）
- **渲染**（按状态分支的操作列、标签色、按钮）
- **门禁**（硬断言、钉样本断言、标签→码缩表）
- **文档**（标签表、流程图、口径说明）
- **跨端副本**（多端共享块、移动端内联）

改一处漏一处，轻则显示不一致，**重则下游校验器仍认旧词 ⇒ 检查静默跳过、永远绿、永远没查**。

**适用**：改状态名 / 拆状态 / 合并状态 / 删除一条流转链路 / 回退某次改名 / 新增一个状态。
**不适用**：纯术语统一（走 `batch-rewrite-surgery`）；改代码结构（走 `refactor`）。

**与 `batch-rewrite-surgery` 的分工**：那个负责「**怎么把 N 个文件里的 X 一次改对**」（机制）；本 skill 负责「**改状态时到底有哪些地方必须一起改**」（覆盖面）。两者串联使用：本 skill 出**改动面清单**，`batch-rewrite-surgery` 出**落盘脚本与逐字节校验**。

---

## 二、第 0 步（最关键）：先判拓扑是否也变

**动手前唯一必须做的事**：把用户口述的「状态链条」与**现有实现的链条逐态比对**。

| 比对结论 | 改动面 | 风险 |
|---|---|---|
| **拓扑完全一致，只差显示标签** | 收敛为**纯文本替换** | 低（走 `batch-rewrite-surgery`） |
| 拓扑有增 / 删 / 拆 / 合 | 必须走**三件套**或**六件套** | 高 |
| **要下线的是贯穿多页的领域概念本身** | 必须走**概念退役八件套**（第五节） | 最高（半下线 = 门禁全红且口径失去权威） |

> 实战结论：多数「改状态」的需求，逐态比对后发现**拓扑根本没变，只是两个标签的字面不同**。这一步能把改动面砍掉 80%，直接避免按「改状态机」的错误假设动手。
>
> **反面：若跳过这一步**，会把「纯文本替换」当成「状态机重构」来做，平白引入数据补样本、渲染分支、断言更新等一大堆风险动作。

**怎么比对**：把用户给的链条写成 `A > B > C > D`，再 grep 现有实现里的状态枚举，排成同样的形式，逐位对齐。差异只在文案就收敛，差异在位次/数量就升级流程。

---

## 三、三件套：状态增删改必须同步「数据 + 渲染 + 门禁」

改任一状态（新增 / 改标签 / 拆语义）时，按此顺序：

### ① 先扫覆盖（找缺口）

页面按状态分支渲染，但**投影里缺样本时，该分支永远不可见**。写一个覆盖扫描器，逐页求：

```
缺口清单 = 「代码引用的状态」 − 「该页投影实际含有的状态」
```

缺口非空 ⇒ 先补数据。**不要凭印象补，一定先跑扫描器**（历史上查出过「局办端缺 `PENDING_INVOICE`、商家端缺 `REJECTED`」这类隐形缺口）。

### ② 补 mock 样本

缺口所在端补一条该状态的记录。**若数据是跨端共享块（两处副本），必须两处同改、逐字节相同**（见 `delivery-consistency-gate`）。

### ③ 补渲染分支

新状态在该页的操作列 / 行内按钮**必须有明确处置**（只读提示 或 具体按钮），否则该行只显示「详情」，用户看不到可做的动作。

### ④ 连带更新硬断言

- 行数 / 金额 / 各端计数类断言（`9→10` / `4200→5400` / `17→19`…）
- 「钉样本唯一」类断言：样本由 1 条变 2 条即失效 ⇒ 改成「两端各一」

### ⑤ 固化为门禁

把「三端投影各含全 N 态」写成**常设断言**，而不是本次人工核对一遍就完。否则下次加状态又会漏。

### ⑥ 文案联动

同一语义的中文标签，在 **HTML 与《说明文档》两处同改**（还有门户镜像 / 移动端内联等副本）。

---

## 四、六件套：删「整条链路」

删一条流转链路（如「标记财政打回」整条链）比改状态更危险，因为**同一语义散落在入口、命令码、字段、标签、相邻规则**里。按六步：

| # | 步骤 | 要点 |
|---|---|---|
| 1 | **分级侦查** | 按「手动入口 / 命令码 / 字段 / 标签 / 他处同形失败」逐级找全。**别漏「同词不同义」的邻近用法**（例：`作废重开` 在凭证与发票下是两回事；`FAILED` 在凭证与用户实名核验下是两回事）⇒ 该改词根就改（发票侧改「发票号更正后重新开票」） |
| 2 | **按文件分组 + 失配批量收集** | 编辑清单按文件组织；`assert c == 1` 改成收集 `MISS`、循环后统一报出并 `SystemExit`（详见 `batch-rewrite-surgery`） |
| 3 | **禁词表避合法术语** | 删除用的锚点串要**带引号**（如写 `"'fiscal'"`），否则误伤 `fiscal supervised account` |
| 4 | **按文件放宽缩减护栏** | 整块删除会触发 `save()` 的 10% 缩减护栏 ⇒ `MIN_RATIO = {...}` 按文件放宽（先确认不是 EOL 归一化误报） |
| 5 | **终检防子串误伤** | `voucherStatusOf` 含子串 `voucherStatus` ⇒ 先剔函数名再断言 |
| 6 | **同步验证器里的旧口径断言** | 删完后，门禁脚本里针对旧链路的断言必须一并删/改，否则它不是失败就是空转 |

---

## 五、概念整体退役（删一个领域概念，八件套）

比删链路更大的手术：把一个**贯穿多页 + 共享库 + 规则 + 文档**的领域概念（如「推送渠道」）整体下线。它不是链路删除的简单放大，有两点本质不同：**下游门禁的断言不是「同步」而是「重写」**；且常伴随**替代源迁移**（数据改从别处来）。

| # | 步骤 | 要点 |
|---|---|---|
| 1 | **影响面盘点** | 概念的全部载体：UI 段/列/筛选、共享库常量 + **函数族**（含派生 helper，一个概念常拖出 5~10 个函数）、BR 规则、样本字段、文档口径、门禁断言 |
| 2 | **先接通替代源** | 概念退役常伴随「信息改从另一处取」（如密钥信息改取应用管理页的共享库）⇒ **先接通替代源再删旧概念**，顺序反了会出现真空态 |
| 3 | **样本改型，不留 remap** | 被下线枚举的样本（如人群类型 TAG）**直接改成新形态**，不做运行期映射 —— 留 remap = 留下半下线状态 |
| 4 | **整批完成纪律** | **同批内必须删完**：页面删了概念列而共享库还留着常量 ⇒ 半下线，门禁全线红且无人知道该以哪边为准 |
| 5 | **门禁断言重写** | 旧概念的断言不是改数字，是**按新口径重写整段**（含负向断言「旧概念标识 = 0」）；重写后跑负向自检证明新断言有牙齿 |
| 6 | **BR / 文档作废登记** | 作废的 BR 号进「已作废」清单（**勿删号**，防编号被误复用）；文档同步新口径 |
| 7 | **收口 grep** | 旧概念的标识符（常量名、函数名、字段名、文案）全仓 = 0；同形词逐处判语义后放行（见六节改名纪律） |
| 8 | **快照 + 反向 diff** | 交 `batch-rewrite-surgery` 落盘、`snapshot-guard` 快照与逐字节比对，常规链 |

> 实战样本：某项目「推送渠道」退役 —— 共享库删 `CHANNELS`/`channelUsable` 等 11 个函数、BR-603/610 作废、密钥页整页重写为应用维度（信息取自应用授权页共享库）、3 条人群样本改型、推送记录 11 列改 8 列、门禁整段重写后 356 断言全绿。

## 六、改名 ≠ 改状态

**先判拓扑（第二节），再决定改动面。** 若结论是「只改显示标签」，则：

1. **先把「非标签」的同词挑出来**：同一个中文词可能既是标签又是动作短语。
   - **要改**：状态标签、步骤条**节点名**、下拉选项。
   - **不改**：业务动作短语（如「局办审核 > 商家开票 > 打款」里的「商家开票」）、与本次无关的同形词（如「节点改名」里的「改名」）。
   - **逐处判语义**，不要全局一把梭。

2. **纯文本替换会漏的四个地方，要定向补**：
   - **冗余括注**（`待发票审核（待局办审核）`）
   - **markdown 表格单元格对齐**（改标签长度后补/减空格保列宽）
   - **标签→码 缩表**（见第六节，漏了 = 校验静默跳过）
   - **抽取/镜像脚本**（如 `_sidebar_extract.js` 这类镜像参照，必须同步）

3. **活文件集**同 `batch-rewrite-surgery`：当前交付物 + 活动门禁脚本白名单 ✅；归档目录 ❌；历史落盘脚本 ❌（是运行记录，含旧词属正常）。

## 七、标签 → 码 映射表必须同步（静默失效头号来源）

若下游扫描器 / 校验器靠一张「**中文标签 → 状态码**」的缩表来认状态，**改标签却不同步该表**，则：

```
扫描器按新标签找不到匹配 ⇒ 该项被跳过 ⇒ N=0 ⇒ 全绿，但根本没查
```

这与 `delivery-consistency-gate` 的「扫描器必须有牙齿」是同一根问题。**处置**：
- 清点该映射表的**全部副本**（可能散在多处，含跨端共享块）
- 逐处同步扩容
- 每个副本加一条**等价断言**（断言「标签集合 == 码集合的映射完备」）
- 若映射表有「动态项」（值随上下文变化的标签），**刻意排除**在静态自检之外（写进去会恒失败）

> 同类：动态标签（如确认方随发起方变化的「待X确认」）**禁止统一成单一文案**，且三处实现（PC 共享表 / 共享 label 函数 / 移动端内联三元）必须一致，由专门的确认方门禁守住。

## 八、部分回退：必须单列「未回退项仍在位」的断言

用户只说「把 A 改回原名」时，**B 项的新改动必须原样保留**。全局替换式回退极易连带清掉不该动的。

**做法**：
1. **定向回退脚本**：只反向替换 A 的串 + 手工修正 A 专属的几处（步骤条节点名、文档表格列宽）。
2. **显式断言**：
   - 「B 的新标签仍在位」✅
   - 「B 的映射表双向在位」✅
   - 「共享块逐字节相同」✅
3. **黄金校验（回退专用）**：留着 **A 改名前的基线快照**，断言「当前磁盘 == 基线 + 仅 B 的改名」，**逐字节相同**。
4. **派生件单列判据**：含内容 hash 的派生件（构建报告等）**不能用文本变换比对** ⇒ 另立判据：① hash 变化页集合**恰等于**预期集合；② 全量 hash 与磁盘实算一致。

## 九、标准流程

```
0 拓扑判定：用户链条 vs 现有实现，逐态比对          → 结论：纯改名 / 拓扑变更 / 概念退役
  （概念退役 ⇒ 转第五节八件套：盘点 → 替代源 → 改型 → 整批 → 门禁重写 → 作废登记 → 收口 → 快照）
1 侦查：全仓 grep 状态码 + 标签 + 同形词，逐处判语义；定活文件集
2 覆盖扫描：求「代码引用状态 − 投影实含状态」= 缺口清单
3 清单：数据(补样本) / 渲染(补分支) / 门禁(改硬断言+钉样本+常设断言) / 文档 / 跨端副本
4 落盘：交 batch-rewrite-surgery 生成脚本（dry×N → 落盘 → 反向 diff）
5 校验：六查 —— 旧标签 0 / 新标签到位 / 未涉及项在位 / 映射表同步 / 门禁全绿 / 派生件 hash 判据
6 快照：交 snapshot-guard（改前刷、改后比对）
7 复述：状态码 / 标签 / 改动文件数 / 语义判定理由
```

## 十一、质量检查清单

- [ ] **已做拓扑判定**，并明确本次是「纯改名」还是「拓扑变更」。
- [ ] 已跑**覆盖扫描器**求缺口，数据缺口已补、两端副本逐字节相同。
- [ ] 新状态在页面上有**明确处置**（不是只显示「详情」）。
- [ ] 硬断言（行数/金额/端计数）与「钉样本」断言已同步更新。
- [ ] 「全 N 态覆盖」已**固化为常设门禁**，不是本次人工核对。
- [ ] 标签→码 映射表的**全部副本**已同步；每副本有等价断言；动态项已排除。
- [ ] 同形词逐处判过语义（标签改、动作短语不改、无关词不动）。
- [ ] 删链路走了**六件套**（侦查/失配收集/禁词表/护栏/子串误伤/验证器断言）。
- [ ] 概念退役走了**八件套**：替代源已先接通、样本改型无 remap、同批删完（无半下线）、门禁断言按新口径重写且负向自检有牙齿、作废 BR 已登记。
- [ ] 部分回退有**单列断言**证明未回退项仍在位；派生件走 hash 判据。
- [ ] 反向 diff 逐字节校验通过；快照已刷并双向比对。
