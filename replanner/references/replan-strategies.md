# 重规划策略 (replanner)

本文件定义 replanner 的 **5 种核心调整策略 + 1 种兜底(人工接管)**。
脚本 `replan.py` 的 `suggest_strategy` 给出框架性建议,实际策略选择与任务改写由 AI 在 SKILL.md 引导下完成。

## 策略总览

| 策略 | 适用场景 | 操作 | 风险 | 优先级 |
|------|---------|------|------|--------|
| 重排 | 失败任务非关键路径,可后置 | 调整执行顺序,先做其他任务 | 低 | 1(优先) |
| 跳过 | 失败任务为可选阶段(P1/P2) | 从 tasks 移除,清理下游引用并标注 | 中 | 2 |
| 拆分 | 失败任务过大/根因不明 | 拆为多个更小子任务重试 | 中 | 3 |
| 合并 | 多个小任务频繁失败 | 合并为一个较大任务统一处理 | 中 | 4 |
| 降级 | 失败任务可用降级方案替代 | 换用 `skill-runtime` 降级策略,产物降级 | 高(需用户确认) | 5 |
| 人工接管 | 同一失败链路重规划达 3 轮 | 停止自动重规划,转人工审查 | —(兜底) | 兜底 |

**选择原则**:优先选对规划扰动最小的策略;降级需用户确认;人工接管是硬兜底,第 3 轮后必须触发。

---

## 一、重排(reorder)

- **触发条件**:失败任务不在关键路径上(影响分级为"降级"或"无影响"),且其下游有可独立执行的其他任务。
- **适用场景**:某任务瞬时失败但非阻塞,可先推进其他无依赖任务,把失败任务后置重试。
- **操作步骤**:
  1. 确认失败任务的下游是否有不依赖它的可并行任务。
  2. 调整 `depends_on`/`parallel_with`,把可先做的任务提前。
  3. 失败任务保留在 tasks 中,标注稍后重试(在 `replan-report.md` 变更说明里记录)。
  4. 不删除任何任务,不改变任务内容。
- **风险**:低。仅改顺序,不改任务本身。
- **示例**:T-003(创建接口)失败,T-006(部署环境,无依赖)可先做 → 把 T-006 提前,T-003 后置。

## 二、跳过(skip)

- **触发条件**:失败任务为可选阶段(priority=P1/P2),且其下游任务能容忍该产物缺失(或有兜底)。
- **适用场景**:非核心功能(如评论、统计)失败,不影响主流程交付。
- **操作步骤**:
  1. 确认失败任务 priority 非 P0(阻断级不可跳过)。
  2. 从 `tasks` 数组移除失败任务。
  3. 清理下游任务的 `depends_on`/`parallel_with` 中对该 id 的引用。
  4. 在 `replan-report.md` 标注:跳过了哪些任务、下游受何影响、是否需后续补做。
- **风险**:中。下游可能缺少该产物,需确认下游能容忍或走兜底。
- **示例**:T-005(评论功能,P2)失败且无下游依赖 → 直接跳过,主流程(文章/接口/列表)照常交付。

## 三、拆分(split)

- **触发条件**:失败任务过大(est_complexity ★★★★+)、根因不明确,或一次 skill 调用无法完成。
- **适用场景**:任务粒度超出"1 次 skill 调用可完成"红线,失败可能因局部复杂度过高。
- **操作步骤**:
  1. 分析失败任务的内部结构,按子步骤拆为 2~N 个更小子任务。
  2. 新任务 id 沿用原 id 加后缀(如 `T-003` → `T-003a`/`T-003b`/`T-003c`),便于追溯。
  3. 子任务间按数据/控制依赖设 `depends_on`;原任务的下游改指向最后一个子任务。
  4. 重新估算每个子任务的 `est_complexity`(应低于原任务)。
  5. 保留原任务在 `replan-report.md` 的变更说明里记录(被拆分),从 tasks 中移除原任务。
- **风险**:中。需重新估复杂度与依赖;拆得过细会增加调度开销。
- **示例**:T-003(实现创建文章接口)失败 → 拆为 T-003a(定义接口契约)+ T-003b(实现 handler)+ T-003c(写单测)。

## 四、合并(merge)

- **触发条件**:多个相邻小任务频繁失败(各自单独执行都不稳),合并后可一次性处理。
- **适用场景**:几个强耦合的小任务拆得过细,反复失败,合并为整体重试更稳。
- **操作步骤**:
  1. 识别频繁失败的相邻小任务(通常有直接依赖关系)。
  2. 合并为一个任务,id 可用原 id 列表组合(如 `T-004+T-005`)或取主 id。
  3. 合并后任务的 `depends_on` 取各原任务依赖的并集(去重),`assigned_skill` 取主任务或重新指定。
  4. `est_complexity` 按合并后整体重估。
  5. 在 `replan-report.md` 记录被合并的原 id 列表。
- **风险**:中。并行度降低;合并后任务复杂度上升,可能再次失败(此时考虑拆分或降级)。
- **示例**:T-004(列表页)+ T-005(详情页)都失败且强耦合 → 合并为 T-004M(实现列表+详情页)。

## 五、降级(degrade)

- **触发条件**:失败任务有可接受的降级方案(如换用更简单技术栈、减少功能、用占位实现)。
- **适用场景**:关键路径任务(P0)无法在轮次内修复,但可用降级方案让流程继续,事后补强。
- **操作步骤**:
  1. 查阅 `skill-runtime` 的降级模式(degrade-patterns),确认是否有对应降级方案。
  2. **必须用户确认**:降级涉及质量折损,未经确认不写入降级方案。
  3. 修改失败任务的 `title`/`assigned_skill` 为降级方案,或在 tasks 中新增一个降级任务替代。
  4. 在 `replan-report.md` 明确记录:降级前后的差异、质量折损点、后续补强计划。
  5. 下游任务的 `depends_on` 指向降级任务。
- **风险**:高。产物质量下降,可能影响下游期望;需用户知情同意。
- **示例**:T-003(实现完整搜索接口)失败 → 降级为 T-003D(实现简单 LIKE 搜索),后续迭代再升级。

## 六、人工接管(manual)

- **触发条件**:同一失败链路重规划达 **3 轮**仍失败,或影响分级为"阻断"但所有自动策略均不适用。
- **适用场景**:自动重规划已无法收敛,需人工判断需求范围/技术可行性。
- **操作步骤**:
  1. 脚本 `replan.py` 在 `round >= 3` 时强制把策略置为"人工接管",并在报告生成"人工接管提示"章节。
  2. 停止自动重规划,**不再产出新的 task-tree.v2**(或产出但标注"待人工审查")。
  3. `replan-report.md` 汇总:历次失败信息、影响范围、已尝试策略、当前阻塞点。
  4. 转交人工:人工决定是否调整需求范围、换用降级方案、或终止任务。
- **风险**:—(兜底机制,避免无限重规划消耗资源)。
- **示例**:T-001(表结构设计)经 3 轮拆分/降级仍失败 → 转人工,人工审查是否需求本身存在矛盾。

## 策略与影响分级的对应

| 影响分级 | 可选策略(按优先级) | 禁用策略 |
|---------|-------------------|---------|
| 阻断 | 拆分 → 降级 → 人工接管 | 跳过(P0 不可跳) |
| 降级 | 重排 → 跳过 → 合并 → 拆分 | — |
| 无影响 | 重排 / 不调整 | —(通常无需重规划) |

> 详见 `references/impact-analysis.md` 的分级定义与 `replan.py` 的 `suggest_strategy` 实现。
