# 依赖识别规则 (task-planner)

本文件定义 task-planner 在"标注依赖"阶段使用的三类依赖识别规则。
正确识别依赖是拓扑排序与并行度计算的前提;漏标会导致执行乱序,错标会降低并行度。

## 一、数据依赖

- **定义**:任务 B 需要任务 A 的产物作为输入。A 不完成,B 无法开始或无意义。
- **识别方法**:
  1. 列出 B 的输入(数据、文件、接口契约、配置)。
  2. 追溯每个输入的产出方:若来自 A,则 B `depends_on` A。
  3. 数据依赖是最常见的依赖类型,优先识别。
- **示例**:
  - 后端接口任务依赖数据层表设计任务(需要表结构才能写接口)。
  - 前端页面任务依赖后端接口契约任务(需要 API 定义才能对接)。
- **标注**:在 task-tree.json 的 `depends_on` 数组中加入 A 的 id。
- **注意**:若 B 只需要 A 的"契约/约定"而非"实现",可让 A 拆出一个"产出契约"的子任务,B 依赖该子任务,从而提前并行。

## 二、控制依赖

- **定义**:任务 B 必须在任务 A 完成后才能开始,但不是因为数据,而是流程/质量约束。
- **识别方法**:
  1. 检查是否存在质量门、评审、验收节点卡在 A 与 B 之间。
  2. 检查是否存在"必须先确认 A 的结果才决定 B 怎么做"的决策依赖。
  3. 检查是否存在环境/状态前置(如 A 完成才能解锁 B 所需环境)。
- **示例**:
  - 集成测试任务必须在所有单元测试通过后开始(质量门)。
  - 上线部署任务必须在验收报告签出后执行(流程门)。
  - 数据迁移任务必须在评估报告确认后执行(决策门)。
- **标注**:在 task-tree.json 的 `depends_on` 数组中加入 A 的 id。
- **注意**:控制依赖往往降低并行度,能拆成数据依赖(提前给契约)就不要用控制依赖硬卡。

## 三、资源依赖

- **定义**:任务 B 和任务 A 不能并行执行,因为共用同一独占资源(同一文件、同一服务、同一环境)。
- **识别方法**:
  1. 列出 B 涉及的资源(文件、服务、数据库、部署环境、外部账号)。
  2. 若 A 也写/占用同一资源,二者存在资源依赖。
  3. 资源依赖不一定是"谁先谁后",但必须串行。
- **示例**:
  - 两个任务都改同一份数据库迁移文件(写冲突)。
  - 两个任务都占用唯一的测试环境(环境冲突)。
  - 两个任务都调用有并发限制的外部 API(限流冲突)。
- **标注**:
  - 若有明确先后,标入 `depends_on`。
  - 若只需串行、先后无所谓,在 `parallel_with` 中**移除**对方(默认不在 parallel_with 即串行),或在备注中说明资源冲突。
- **注意**:资源依赖可通过"拆资源"(分文件、分库、分时段)消除,从而恢复并行。

## 四、依赖识别流程

```
对每个任务 B:
  1. 列出 B 的输入 → 追溯产出方 → 标数据依赖(depends_on)
  2. 检查 B 前是否有质量门/决策门 → 标控制依赖(depends_on)
  3. 检查 B 涉及的独占资源 → 标资源依赖(depends_on 或移出 parallel_with)
  4. 未命中任何依赖 → B 可与同层任务并行(纳入 parallel_with)
```

## 五、常见错误

| 错误 | 后果 | 纠正 |
|------|------|------|
| 漏标数据依赖 | B 在 A 未完成时启动,拿到空/错数据 | 必须追溯每个输入的来源 |
| 过度标控制依赖 | 并行度被压到 1,执行变慢 | 能拆成数据依赖(给契约)就不要硬卡 |
| 把可并行任务标成依赖 | 浪费并行窗口 | 区分"需要数据"和"刚好同时做" |
| 环状依赖 | 拓扑排序失败,无法排出执行顺序 | 拆出共享前置任务打破环 |

> 拓扑排序若报"存在环",回到本规则逐对检查,拆出公共前置任务解除环。
