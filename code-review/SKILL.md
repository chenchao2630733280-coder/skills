# 代码审查 (code-review)

## 一、定位与职责

本 skill 是**只读不写**的代码审查工具:
- **只读**:不直接修改被审查代码,不写补丁,不创建 PR。所有发现以报告形式产出。
- **复用 skill-auditor 的报告模式**:Markdown(人读)+ JSON(机读)双产出,便于编排总纲或下游工具消费。

核心职责:
1. 接收 PR、diff、commit 范围或单文件变更。
2. 按"正确性 / 安全性 / 性能 / 可维护性"四个维度逐项检查。
3. 标注每个问题的严重级别(blocker / warning / suggestion)。
4. 产出审查报告 + 修复建议,交付给调用方(人 or 编排总纲)决定是否合并。

**不做什么**:
- 不替代自动化测试(不跑测试用例,不验证运行时行为)。
- 不替代 lint / type-check(假定这些已通过)。
- 不重写代码,只给建议。

## 二、四个审查维度

### 1. 正确性 (correctness)
检查代码逻辑是否符合预期,关注:
- 逻辑错误(条件反转、off-by-one、错误运算符)
- 边界条件(空集合、首末元素、最大/最小值、负数、零)
- 异常处理(吞异常、catch 过宽、未传播、finally 副作用)
- 空指针 / None / undefined 解引用
- 资源泄漏(未关闭的文件/连接/锁、未释放的内存)
- 并发正确性(竞态、死锁、可见性、非原子复合操作)
- 类型混淆、隐式转换陷阱
- 返回值忽略(尤其错误码)

### 2. 安全性 (security)
- SQL 注入(字符串拼接 SQL、未参数化)
- XSS(未转义的用户输入回显、innerHTML / dangerouslySetInnerHTML / v-html)
- 命令注入(os.system / exec 拼接用户输入)
- 硬编码密钥 / Token / 密码 / API Key
- 权限绕过(缺失鉴权、越权访问、IDOR)
- 敏感数据明文(日志、响应体、错误信息、数据库)
- 不安全的反序列化、路径穿越(../)
- 弱加密 / 弱哈希(MD5、SHA1 用于密码)、弱随机数
- CSRF、开放重定向、SSRF

### 3. 性能 (performance)
- N+1 查询(循环内查询 DB / 调用外部 API)
- 不必要的循环 / 嵌套循环(可优化为哈希 / 排序合并)
- 大对象拷贝(应传引用 / 指针的地方传值)
- 缺失数据库索引(高频查询字段无索引)
- 内存泄漏(闭包持有、缓存无上限、事件监听未移除)
- 同步阻塞 IO 在热路径 / 异步上下文里调同步
- 重复计算、未缓存可复用结果
- 大列表全量加载(应分页 / 流式)
- 不必要的序列化 / 反序列化

### 4. 可维护性 (maintainability)
- 命名不清(单字母、误导名、与作用不符)
- 函数过长(>80 行)、参数过多(>5 个)、嵌套过深(>4 层)
- 重复代码(应抽函数 / 基类 / 工具)
- 缺注释(复杂逻辑、业务规则、魔法数字未说明)
- 高耦合(直接依赖实现而非接口、全局状态、循环依赖)
- 单一职责违反(一个类 / 函数做太多事)
- 魔法数字 / 硬编码常量(应抽常量 / 枚举)
- 错误信息不可定位(无堆栈、无上下文)
- 死代码、注释掉的代码、TODO / FIXME 未跟踪

## 三、审查流程

```
接收输入(diff/PR/commit 范围)
   ↓
1. 解析变更:识别改动文件、新增/删除/修改行
   ↓
2. 上下文还原:对每个改动点,读取必要上下文(同文件邻近代码、被调用函数签名)
   ↓
3. 四维度扫描(对每个变更点依次过 correctness → security → performance → maintainability)
   ↓
4. 严重级别标注(对每个发现按"四"的定义定级)
   ↓
5. 去重与合并(同一根因的多个症状合并为一条)
   ↓
6. 产出报告(Markdown + JSON)
   ↓
7. 给出合并建议:有 blocker → 阻断合并;仅 warning/suggestion → 可合并但建议跟进
```

**输入形式**:
- git diff 输出(unified diff)
- PR 链接 + diff(若编排总纲已抓取)
- commit 范围(如 `a1b2c3..d4e5f6`)
- 单文件 / 多文件路径列表

**上下文边界**:只审查"变更行 + 其直接影响的上下文",不审查未改动的旧代码(除非变更使其暴露新风险)。

## 四、严重级别定义

| 级别 | 含义 | 合并影响 | 示例 |
|------|------|----------|------|
| **blocker** | 必须修复才能合并。会导致错误、安全漏洞、数据损坏或严重性能问题 | 阻断合并 | SQL 注入、空指针崩溃、硬编码生产密钥、数据丢失 |
| **warning** | 建议修复。不影响功能正确性,但影响健壮性 / 可维护性 / 长期质量 | 可合并,但应在后续迭代修复 | 缺失边界检查但当前无触发路径、函数过长、命名不清 |
| **suggestion** | 可选改进。属于最佳实践或风格优化 | 可合并,可忽略 | 可用更地道的语法、可加注释、可抽常量 |

定级原则:
- 当不确定时,**降一级**(宁可放过,不误伤)。
- 同一问题若横跨多维度,按最高相关维度定级,在 description 中注明其他维度影响。
- 安全问题默认不低于 warning;涉及鉴权 / 注入 / 密钥的默认 blocker。

## 五、产出契约

每次审查产出两个文件,放在调用方指定目录(默认当前工作目录):

### 1. `code-review-report.md`(人读)
结构:
- 标题 + 元信息(被审查范围、审查时间、审查者 = code-review skill)
- 总览表(total / blocker / warning / suggestion 计数 + 合并建议)
- 问题清单表(按严重级别降序,字段:ID / 维度 / 文件:行 / 描述 / 建议)
- 修复建议详表(对每条问题给出具体修复方案,含代码片段示例)
- 通过项摘要(明确指出哪些维度 / 文件未发现问题,避免"沉默通过")

模板见 `references/review-report-template.md`，审查清单见 `references/review-checklist.md`。

### 2. `code-review-report.json`(机读)
```json
{
  "issues": [
    {
      "id": "CR-001",
      "dimension": "security",
      "severity": "blocker",
      "file": "src/auth/login.ts",
      "line": 42,
      "description": "硬编码 API Key",
      "suggestion": "从环境变量读取,见修复建议"
    }
  ],
  "summary": {
    "total": 12,
    "blocker": 2,
    "warning": 6,
    "suggestion": 4
  },
  "timestamp": "2026-08-06T10:30:00+08:00"
}
```

字段约束:
- `id`:格式 `CR-NNN`,三位数字,从 001 起。
- `dimension`:枚举 `correctness | security | performance | maintainability`。
- `severity`:枚举 `blocker | warning | suggestion`。
- `file`:相对仓库根的路径。
- `line`:变更中能定位到的具体行号;若为跨行问题,取起始行。
- `description`:一句话说明问题。
- `suggestion`:一句话修复方向(详细方案在 md 中)。

## 六、与编排总纲的接入

### 被 product-pipeline-master 调用
- **接入点**:在 `implement-frontend` / `implement-backend` / `implement-data-layer` / `integrate-system` 阶段**之后**调用本 skill,作为合并前的质量门。
- **输入**:编排总纲传入 diff(本次实现产生的变更)或 PR。
- **输出**:报告回传编排总纲;若 `summary.blocker > 0`,编排总纲应阻断后续阶段并触发修复循环。

### 与 guardrail / diff-reviewer 配合
- **分工**:
  - `guardrail` / `diff-reviewer`:看**变更风险**(改了什么、影响面多大、是否触碰敏感模块)。
  - `code-review`(本 skill):看**代码质量**(写得对不对、安全不安全、好不好维护)。
- 两者**互补不重叠**:前者回答"这次变更危险吗",后者回答"这次变更写得好吗"。
- 编排总纲可并行调用两者,综合判断是否放行。

### 独立调用
用户也可直接调用本 skill 审查任意 diff / PR,无需编排总纲。

## 七、质量检查清单

审查报告产出前,自检以下项,确保报告本身质量:

- [ ] 每条 issue 的 `file:line` 能定位到具体代码(非空泛指)
- [ ] 每条 issue 同时有 description 和 suggestion(不只指出问题)
- [ ] 严重级别符合"四"的定义,无高估 / 低估
- [ ] 同一根因的多个症状已合并,无重复 issue
- [ ] 总览表的计数与 issues 数组一致
- [ ] JSON 字段类型与枚举值符合"五"的约束
- [ ] 通过项摘要已明确写出(不能"什么都没说"就视为通过)
- [ ] 修复建议可执行(不是"请优化"、"请改进"这类空话)
- [ ] 未审查未改动代码(除非变更使其暴露新风险)
- [ ] 报告语言为中文(除非调用方指定英文)
