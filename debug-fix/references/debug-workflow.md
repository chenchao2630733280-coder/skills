# 调试工作流详解

按 **复现 → 定位 → 假设 → 验证 → 修复 → 验证** 六步闭环执行。每步给出输入 / 输出 / 工具 / 判断标准。

---

## 步骤 1:复现

**目标:** 确认错误可稳定复现,并记录复现条件。

| 项 | 内容 |
|---|---|
| **输入** | 用户提供的错误日志、堆栈、复现步骤、环境信息 |
| **输出** | 可重复的复现步骤、明确的环境与触发条件 |
| **工具** | Read(读日志文件)、RunCommand(跑复现脚本)、tool-monitor-ops(查线上 trace) |
| **判断标准** | 能按记录的步骤稳定触发同一错误;若无法复现,需说明并请求更多信息 |

**要点:**
- 记录:操作系统、语言/运行时版本、依赖版本、配置、数据状态
- 无法复现时:不要凭空假设,转而向用户索取更多上下文(完整日志、trace、数据样本)
- 间歇性错误:优先怀疑并发、时序、资源竞争类问题

---

## 步骤 2:定位

**目标:** 找到与错误相关的代码位置。

| 项 | 内容 |
|---|---|
| **输入** | 复现步骤、堆栈跟踪、错误信息 |
| **输出** | 相关代码文件与行号、调用链上下文 |
| **工具** | SearchCodebase(按语义找代码)、Grep(按符号/文本找)、Read(读上下文)、Glob(找文件) |
| **判断标准** | 已找到错误抛出点及其上下游调用;能解释错误发生在哪一层 |

**要点:**
- 从堆栈最顶层用户代码开始,而非框架内部
- 用 SearchCodebase 按行为/意图搜索,而非只匹配符号
- 读完相关函数全貌,不要只看报错行
- 追溯数据流:错误值从哪里来

---

## 步骤 3:假设

**目标:** 基于代码与日志分析,形成可验证的根因假设。

| 项 | 内容 |
|---|---|
| **输入** | 相关代码、错误现象、日志/trace |
| **输出** | 一条明确的根因假设("因为 X,导致 Y") |
| **工具** | 逻辑推理、对照 `debug-patterns.md` 模式匹配 |
| **判断标准** | 假设能解释所有已知现象(错误信息、触发条件、影响范围) |

**要点:**
- 优先对照 8 类常见 Bug 模式匹配,加速定位
- 假设要具体、可证伪:写明"若假设成立,则应观察到 Z"
- 多个候选假设时,按"能解释最多现象"与"最易验证"排序
- 避免:未读代码就猜测、只解释部分现象就下结论

---

## 步骤 4:验证

**目标:** 确认假设是否成立,排除其他可能性。

| 项 | 内容 |
|---|---|
| **输入** | 根因假设、相关代码 |
| **输出** | 假设成立 / 不成立的结论,附代码或日志证据 |
| **工具** | Read(读佐证代码)、Grep(找同类调用点)、tool-monitor-ops(查日志/trace 佐证)、RunCommand(跑最小复现) |
| **判断标准** | 有直接代码/日志证据支持假设;假设的预测与观察一致 |

**要点:**
- 找反例:是否存在与假设矛盾的现象?若有,假设需修正
- 检查同类调用点:同样的 Bug 是否存在于其他地方
- 假设不成立:回到步骤 2 重新定位,不要强行修复
- 记录验证证据,作为调试报告的根因依据

---

## 步骤 5:修复

**目标:** 修改代码消除根因(修复前需用户确认)。

| 项 | 内容 |
|---|---|
| **输入** | 已验证的根因、相关代码 |
| **输出** | 修复方案、修复 diff、修改的文件列表 |
| **工具** | Edit(改代码) |
| **判断标准** | 用户已确认方案;修改针对根因而非表象;未引入新风险 |

**要点:**
- **修复前必须向用户展示方案并获得确认**(安全约束)
- 修复根因,不要只消除报错信息(如吞异常、try-catch 掩盖)
- 最小化改动:只改与根因相关的代码,不顺手重构
- 检查同类调用点是否需要一并修复
- 不直接修改生产环境代码,需在分支上验证

**重试规则:**
- 修复后若验证失败,可重试,但最多 3 轮
- 每轮重试需说明上一轮失败原因与本次调整
- 3 轮失败后转人工,输出已尝试方案清单

---

## 步骤 6:验证(修复后)

**目标:** 确认修复有效且未引入回归。

| 项 | 内容 |
|---|---|
| **输入** | 修复后的代码、修复 diff |
| **输出** | 验证结果(通过/失败)、测试建议 |
| **工具** | RunCommand(跑测试)、联动 `test-and-harden-system` |
| **判断标准** | 原复现步骤不再触发错误;相关测试通过;无新增失败 |

**要点:**
- 先按原复现步骤确认错误已消除
- 建议跑相关单元测试 / 集成测试
- 联动 `test-and-harden-system` 做更完整的回归验证
- 若验证失败,回到步骤 5 重试(计入重试轮次)
- 验证通过后产出 debug-report.md / debug-report.json

---

## 工作流闭环示意

```
复现 → 定位 → 假设 → 验证 ──成立──→ 修复 → 验证(修复后) → 产出报告
                       │              │              │
                       └─不成立─→ 回定位   └─失败─→ 重试(≤3轮)→ 转人工
```
