# 调试修复 (debug-fix)

## 一、定位与职责

本 skill 专门用于软件缺陷的定位与修复。

**核心职责:**
- 接收错误信息(错误日志、堆栈跟踪、复现步骤、异常截图等)作为输入
- 通过代码搜索与逻辑分析定位 Bug 根因
- 产出修复方案并直接修改代码完成修复
- 输出调试报告(debug-report.md / debug-report.json)供追溯

**不负责:**
- 性能优化、新功能开发、代码重构(除非修复所必需)

## 二、调试工作流

按以下六步闭环执行,详见 `references/debug-workflow.md`:

1. **复现**:确认错误可稳定复现,记录复现步骤与环境信息
2. **定位**:用 SearchCodebase / Grep 找到相关代码,用 Read 读取上下文
3. **假设**:基于代码与日志分析根因,形成可验证的假设
4. **验证**:确认假设是否成立(读相关代码、查日志、逻辑推理)
5. **修复**:修改代码(修复前需用户确认)
6. **验证**:建议跑测试,联动 `test-and-harden-system` 验证修复有效性

## 三、常见 Bug 模式

详见 `references/debug-patterns.md`,共 8 类:

- 空指针 / None 引用
- 边界条件(off-by-one)
- 并发竞争
- 资源泄漏(未关闭)
- 类型不匹配
- 异步时序
- 配置缺失
- 依赖版本冲突

定位 Bug 时优先对照上述模式匹配,加速根因分析。

## 四、与 tool-monitor-ops 的联动

- 可调用 `tool-monitor-ops` 查询日志 / trace 辅助定位
- 查到的日志信息作为调试输入,纳入根因分析
- 适用场景:
  - 线上错误、难以本地复现的问题
  - 需要分布式 trace 链路的问题
  - 需要历史日志佐证假设的问题

## 五、安全约束

- **修复前确认**:任何代码修改前需向用户展示修复方案并获得确认
- **重试上限**:最多执行 3 次(含 2 次重试,与 runtime.yaml `retry.max=2` 精确对应),用尽后转人工并说明已尝试方案
- **降级处理**:重试用尽后按 runtime.yaml `degrade` 策略"标记未修复并记录原因"降级,转为人工处理(转人工)
- **测试联动**:修复后建议跑测试(联动 `test-and-harden-system`)
- **生产环境保护**:不直接修复生产环境代码,需先在分支验证后再合并

## 六、产出契约

每次调试产出两份报告:

### 1. debug-report.md
- 根因分析
- 修复方案
- 修复 diff
- 验证建议

### 2. debug-report.json
```json
{
  "bugSummary": "Bug 摘要",
  "rootCause": "根因",
  "fixFiles": ["修改的文件路径列表"],
  "fixDiff": "修复 diff",
  "verified": false,
  "retryCount": 0,
  "timestamp": "ISO 8601 时间戳"
}
```

## 七、质量检查清单

- [ ] 复现步骤已记录
- [ ] 根因已定位并有代码证据
- [ ] 修复方案已获用户确认
- [ ] 修复 diff 已生成
- [ ] 测试建议已提供
- [ ] debug-report.md / .json 已产出
- [ ] 重试次数 ≤ 3
- [ ] 未直接修改生产环境代码
