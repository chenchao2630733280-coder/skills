# PRD Review Checklist

## 证据规则

- 每个 `Complete` 至少引用一个可定位的原文证据，格式优先使用“文件 > 章节/标题 > 最短必要摘录”。
- 一个证据可以支持多个维度，但每个维度必须解释证据为何足够。
- 找不到内容时记录已检查的位置，不得生成不存在的引用。
- 行业惯例、历史经验和合理推断只能用于提出问题，不能作为 `Complete` 的证据。

## Full Review

| 分类 | 维度 | 完整的最低证据 |
|---|---|---|
| 产品清晰度 | 目标与问题 | 说明为什么做、解决什么问题及预期价值 |
| 产品清晰度 | 目标用户与角色 | 明确主要用户、相关角色及各自目标 |
| 产品清晰度 | 范围边界与优先级 | 明确本期包含、不包含、延期项、沿用现状、外部责任边界和 P0/P1 或等价优先级中适用的部分 |
| 用户与流程 | 核心场景 | 说明用户触发条件、主路径和完成结果 |
| 用户与流程 | 首次与空状态 | 新用户、无数据或首次配置有明确处理 |
| 用户与流程 | 异常与逆向 | 取消、失败、超时、驳回、退款等适用路径有原则 |
| 业务完整性 | 核心业务对象 | 对象含义、产品行为依赖的关键属性、关系和唯一性可识别 |
| 业务完整性 | 业务规则 | 创建、修改、失效、约束、计算和关联影响明确 |
| 业务完整性 | 状态与生命周期 | 状态、触发条件、终态、回退和超时完整 |
| 业务完整性 | 角色与权限 | 关键角色对关键操作的允许、禁止和数据范围明确 |
| 业务完整性 | 边界与冲突 | 重复提交、并发、上下限和规则冲突有处理原则 |
| 验收与度量 | 结构化验收标准 | P0 功能至少明确前置条件、触发或操作、预期结果；适用时包含失败结果和关键边界值 |
| 验收与度量 | 需求追踪完整性 | P0 和高风险 P1 可追踪到目标或问题、用户场景、功能或需求、关键规则和验收标准 |
| 验收与度量 | 成功指标 | 定义业务或用户效果指标；不适用时说明原因 |
| 验收与度量 | 数据可观测性 | 指标所需事件或数据来源可识别 |
| 交付准备度 | 依赖与约束 | 外部系统、政策、内容、数据或前置能力明确 |
| 交付准备度 | 非功能要求 | 性能、安全、隐私、兼容性等适用约束明确 |
| 交付准备度 | 风险与待确认 | 重大风险有负责人或决策方式，待确认项可追踪 |
| 交付准备度 | 术语一致性 | 同一对象、角色、状态和指标使用一致名称 |
| 交付准备度 | 跨章节一致性 | 范围、功能清单、流程、规则、状态、权限、验收和指标之间无影响产品行为的冲突或悬空引用 |

## Quick Review

只检查以下高风险维度：

1. 目标用户、产品目标、本期范围及关键排除项。
2. 核心场景与主流程闭合性。
3. 核心业务对象和关键规则。
4. 状态终态、逆向路径和异常处理。
5. 角色权限和敏感操作。
6. P0 追踪链、结构化验收标准和重大待确认项。

## 适用性判断

- 没有状态变化的需求可将“状态与生命周期”标为不适用。
- 纯内部工具仍需检查角色和数据范围，但成功指标可以简化。
- 探索性原型可降低非功能细节要求，但不得省略目标、范围、主流程和验收意图。
- 页面清单、接口、数据库字段和技术架构默认不是产品质量门禁项；只有产品行为或目标下游阶段依赖它们时才检查。
- 合规、安全、支付、实名和风控相关需求应提高异常、权限和约束问题的优先级。
- 数据、内容或 AI 功能应检查输入来源、失败回退、人工介入、可解释性或合规边界中实际适用的部分。
