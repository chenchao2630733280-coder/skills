# PRD Quality Checker

## 定位声明

本 skill 是**修改类审查 skill**（非只读）：在 Improve 模式下会修改 PRD 文档以完善缺陷；在 Audit 模式下只读不写。与 guardrail/code-review/diff-reviewer/skill-auditor 等只读审查 skill 不同，本 skill 具有 PRD 修改能力。

目标：在下游工作开始前，基于可定位的文档证据发现会造成范围误解、规则冲突、无法验收或返工的产品问题，并给出可复核的质量门禁结论。

## 双层架构

### 产品配置层

面向产品经理，只接收自然语言、表格或选项。按 [references/product-configuration.md](references/product-configuration.md) 获取：

- 审核目的和目标下游阶段。
- `Audit` 或 `Improve` 运行方式。
- `Full`、`Quick` 或 `Incremental` 审核范围。
- 项目画像和特殊风险。
- 团队自定义的通过、阻塞或忽略条件。
- 输出格式及是否需要 AI 开发准备度。

产品经理不需要编写 JSON Schema、状态机、数据库模型或评分代码。未提供自定义配置时使用本技能默认规则。

### 执行引擎层

面向模型或未来自动化系统，负责：

- 将自然语言配置规范化为运行配置。
- 识别评审画像并选择适用规则。
- 按 `Audit / Improve` 状态流执行审核。
- 建立证据、追踪和一致性结果。
- 计算评分与门禁。
- 输出 Markdown 报告及可选 JSON。
- 在报告中记录规则版本。

具体协议见 [references/execution-contract.md](references/execution-contract.md) 和 [references/structured-output.md](references/structured-output.md)。

## 定位

- 从产品目标和业务规则出发，不替代技术方案评审。
- 默认评审已有 PRD；如果只有想法或零散材料，先完成需求澄清，再执行本技能。
- 不依赖固定文件名、章节模板或行业。可读取 Markdown、纯文本、办公文档提取文本或当前项目中的需求材料。
- 与实现型 PRD 检查分开：本技能负责架构前的产品质量门禁；页面、路由、UI Token 和具体实现覆盖由项目自己的实现评审流程负责。
- 产品质量门禁与 AI 开发准备度分开。不得用 AI Ready 分数替代 `READY / CONDITIONAL / NOT_READY`。

## 输入

优先获取：

1. 主 PRD 或需求基线。
2. 关联的功能清单、流程、规则或历史评审报告。
3. 产品配置：运行方式、审核范围和目标下游阶段。
4. 可选上下文：项目类型、行业、合规级别、特殊风险、自定义规则及是否需要 JSON 或 AI 开发准备度附录。

输入不足时不要假装已验证。明确列出已读材料和未提供材料。

## 工作流程

### 1. 规范化产品配置

读取 [references/product-configuration.md](references/product-configuration.md)，将用户自然语言转换为内部运行配置。不要要求用户补充技术字段；缺失项使用默认值，并在报告中声明。

### 2. 建立评审画像

至少判断：

- `change_type`：新产品 / 存量迭代 / 修复或合规变更。
- `product_type`：用户产品 / 内部工具 / 平台能力 / 数据或 AI 产品。
- `risk_level`：普通 / 高风险。
- `downstream_stage`：方案设计 / 排期 / 开发 / 验收。
- `delivery_target`：人工开发 / AI 辅助 / AI 代码生成。

画像只决定规则适用性和风险优先级，不替代 PRD 证据。

### 3. 确定审核范围

- `Full`：首次评审或需求大改，检查全部维度。
- `Quick`：时间有限时，只检查阻塞项和高风险维度。
- `Incremental`：有上次报告和可比较的当前 PRD 时，只复查变化及受影响维度。

用户未指定时：

- 有可信的历史报告和当前版本时使用 `Incremental`。
- 否则使用 `Full`。

增量复审必须有可核对的历史证据。仅有一句“上次已通过”不能作为跳过依据。具体规则见 [references/incremental-review.md](references/incremental-review.md)。

`Quick` 是有限范围风险扫描，不等同于完整门禁。未检查维度标记为 `Not Reviewed`，不得标为 `N/A` 或据此宣称完整通过。

### 4. 选择运行方式

- `Audit`：完成扫描、评分和门禁后一次性输出报告。默认使用此方式。
- `Improve`：先完成全量预扫描，再仅针对影响结论的问题逐题确认；每次只问一个问题，最多连续追问 5 个。

按 [references/execution-contract.md](references/execution-contract.md) 执行状态转换。`Improve` 不是降低标准，所有用户回答都必须标为“用户确认”，不能伪装成原 PRD 证据。

### 5. 建立证据表

阅读材料后，按 [references/checklist.md](references/checklist.md) 检查适用维度。每项记录：

- `Evidence`：文件、章节或标题，加一段最短必要的原文摘录或忠实摘要。
- `Finding`：完整、部分、缺失、不适用或冲突。
- `Impact`：该问题可能影响的用户、范围或下游工作。
- `Confidence`：高、中、低。

证据纪律：

- `Complete` 必须有可定位的正向证据；没有证据不得判为完整。
- `Missing` 应记录已检查的相关章节，避免把“未找到”伪装成文档事实。
- `N/A` 必须说明为什么不适用。
- 同一规则在不同章节冲突时，同时引用双方证据。
- 不要仅凭行业常识把缺失内容判定为已确认。推断必须标记为“建议”或“待确认”。

PRD 明确属于电商、审批、内容、交易或其他高规则密度领域时，可按需读取 [references/domain-risk-prompts.md](references/domain-risk-prompts.md)。这些提示只用于发现应核对的问题，不是默认业务规则，也不能作为评分证据。

### 6. 检查追踪与一致性

按 [references/traceability-and-consistency.md](references/traceability-and-consistency.md) 执行：

1. 为 P0 和高风险 P1 建立最小追踪链：`目标/问题 → 用户场景 → 功能或需求 → 业务规则 → 验收标准`。
2. 扫描范围、功能清单、流程、状态、权限、规则、验收和指标之间的冲突或悬空引用。
3. 检查范围边界是否说明包含、不包含、延期、沿用现状和外部责任边界中适用的部分。
4. 检查关键验收标准是否包含前置条件、触发或操作、预期结果，并在适用时覆盖失败结果和边界值。

不要要求 PRD 使用固定编号或模板。没有需求 ID 时，可用章节、功能名或用户故事作为追踪键。

### 7. 识别阻塞项

以下任一情况默认阻止自动进入下游流程：

- 产品目标或目标用户无法确定。
- 核心范围、主流程或关键业务对象无法确定。
- 关键规则、状态终态、角色权限存在冲突或重大空缺。
- 高风险异常流程没有处理原则。
- P0 功能没有可测试的验收标准。
- P0 需求无法追踪到目标、场景或验收标准。
- 范围、流程、规则、状态、权限或验收之间存在会改变产品行为的未解决冲突。
- 仍有会显著改变架构、端类型、页面规模或核心流程的待确认项。

不要把措辞、排版、低风险埋点遗漏当作阻塞项。

### 8. 进行最少必要追问

先完成文档扫描，再提问。只询问无法从材料推断且会改变结论的问题。

- 默认每次问一个问题。
- 优先处理阻塞项，再处理高优先级问题。
- 每个问题提供基于证据的推荐答案和备选项。
- 默认最多连续追问 5 个问题；仍未解决时，生成带待确认项的报告，而不是无限对话。
- 用户明确要求一次性审查时，不强制逐题问答。

提问时先说明证据缺口和影响，再给出推荐选项。不要诱导用户接受行业惯例，也不要把开发可自行决定的实现细节升级为产品决策。

### 9. 评分与门禁

使用 [references/scoring.md](references/scoring.md) 的固定评分方法。不得凭整体印象随意给分。

门禁结论只有三种：

- `READY`：可以进入下游流程。
- `CONDITIONAL`：不存在阻塞项，但需带着明确的非阻塞事项继续。
- `NOT_READY`：存在阻塞项或质量不足，先补充 PRD。

评分不是唯一依据；阻塞项优先于总分。

### 10. 输出结果

按 [references/report-template.md](references/report-template.md) 输出报告，至少包含：

- 输入材料和评审范围。
- 门禁结论、总分和各分类得分。
- 阻塞项和高优先级问题。
- 已确认结论、合理假设和待确认项。
- P0 和高风险 P1 的追踪矩阵，以及跨章节不一致项。
- 对 PRD 的具体补充建议。
- 下游流程是否可以继续，以及继续时必须携带的约束。

默认展示 Markdown 报告。用户要求系统集成、自动化处理或机器可读结果时，同时按 [references/structured-output.md](references/structured-output.md) 输出 JSON。报告和 JSON 必须记录同一个规则版本，当前版本见 [references/rule-version.md](references/rule-version.md)。

只有在用户要求或项目工作流明确指定路径时才写入文件。

### 11. 可选 AI 开发准备度

仅在以下任一条件满足时读取 [references/ai-readiness.md](references/ai-readiness.md)：

- 用户明确要求评估 AI 生成代码、自动开发或开发代理的输入准备度。
- PRD 明确将直接交给代码生成流程。
- 项目工作流将 AI Ready 评估指定为独立交付物。

AI Ready 结果作为报告附录，不改变产品质量总分和门禁。页面清单、接口契约、字段级模型等内容可能适合放在设计或技术文档中；如果下游尚未要求这些材料，应标记为“下游输入缺口”，而不是直接判定 PRD 产品质量不合格。

### 12. 修订与复审

需要修改 PRD 时：

1. 先说明拟修改的文件和章节。
2. 保留原有意图，不替产品经理擅自确定重大业务决策。
3. 将未确认内容标为待确认或合理假设。
4. 修改后重新检查受影响维度并更新报告。

项目工作流把本技能作为前置门禁时：

- `READY`：继续后续流程。
- `CONDITIONAL`：向用户展示遗留项；用户确认接受后继续。
- `NOT_READY`：暂停架构、详细设计或开发，先完成补充并复审。

## 输出纪律

- 每个通过项、冲突项和高优先级问题都必须引用可定位证据，避免泛泛而谈。
- 优先报告会造成返工的问题，不用大量低价值措辞建议淹没关键风险。
- 不要求 PRD 包含技术实现细节，除非产品行为依赖这些约束。
- 不把“AI 可生成代码”等同于“产品需求质量合格”。
- 不向 PRD 末尾追加大段历史状态；评审历史应保存在独立报告中，避免污染需求正文。
