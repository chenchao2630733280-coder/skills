# 维度 4:扩展性审查规则

> 审查新能力接入成本和四位一体模板覆盖。本维度关注 skill "未来扩展的友好度"。

---

## 4.1 四位一体覆盖

**检查项**:
编排总纲(如 game-forge-master)对每个支持的引擎/端类型,四个位置是否同步覆盖:

| 位置 | 职责 | 示例(Unity) |
|---|---|---|
| 决策树 | 何时选该引擎 | "3D 复杂游戏/需 Unity 生态 → Unity" |
| 模板索引 | 该引擎的模板文件清单 | unity/ 目录下的 .cs.tpl 文件 |
| 产物路径表 | 该引擎产出物路径 | Assets/Scripts/Runtime/**/*.cs |
| 集成分支 | 该引擎的构建/校验流程 | §2.8 Unity 构建流程 |

**检查方法**:
```
1. 从决策树提取所有支持的引擎/端类型 → 集合 E
2. 对每个 e ∈ E,检查:
   a. 模板索引中有 e 的模板条目?
   b. 产物路径表中有 e 的产物行?
   c. 集成阶段有 e 的构建分支?
3. 任意一项缺失 → 四位一体不完整
```

**严重级别**:
- 决策树有但其他位置缺 → CRITICAL(选了引擎但无法生成/构建)
- 模板索引有但决策树无 → WARNING(有模板但不会被选中)

## 4.2 新引擎/端类型接入成本评估

**评估方法**:
假设要新增一个引擎/端类型(如 "Unreal Engine 5" 或 "小程序端"),需要改几个文件?

| 改动位置 | 改动内容 | 成本 |
|---|---|---|
| 编排总纲 决策树 | 加 1 个分支 | 低(1 行) |
| 编排总纲 模板索引 | 加 1 个目录条目 | 低(几行) |
| 编排总纲 产物路径表 | 加 N 行产物 | 低 |
| 编排总纲 集成分支 | 加 1 个构建流程章节 | 中(需研究 CLI) |
| code-forge references | 新建 engine-{name}-template.md | 高(需写完整模板) |
| code-forge SKILL.md | 加索引块 + 生成规则补充 | 低 |
| integrate SKILL.md | 加构建流程 + 失败回退 | 中 |

**成本评级**:
| 总改动文件数 | 评级 |
|---|---|
| ≤3 | ✅ 低成本(四位一体设计良好) |
| 4-6 | ⚠️ 中成本(可接受) |
| >6 | ❌ 高成本(扩展性差,需重构) |

**检查方法**:
```
1. 列举最近一次新增引擎/端类型的实际改动(从 topics.md 或 git log)
2. 统计改动文件数
3. 评估是否有可复用的扩展模板
```

**严重级别**:
- 接入需改 >6 文件 → WARNING
- 接入需改动核心调度逻辑 → CRITICAL(应只加不改)

---

## 4.3 决策树完备度

**检查项**:
1. 决策树覆盖所有声明支持的引擎/端类型
2. 有"用户明确指定 → 尊重用户选择"兜底分支
3. 决策树分支无重叠(一个输入只匹配一个分支)
4. 决策细则表与决策树一致

**检查方法**:
```
1. 提取决策树的所有分支条件
2. 检查是否有遗漏场景(如 3D 游戏但未指定引擎,走哪个分支?)
3. 检查分支条件是否互斥(如 "2D 游戏" 和 "复杂物理" 可能重叠)
4. 对照决策细则表,验证每条细则对应决策树的一个分支
```

**示例问题**:
```
决策树:
├─ 2D 跑酷/平台 → Phaser
├─ 3D 游戏 → Godot 4
├─ 3D 复杂/Unity 生态 → Unity
└─ 用户指定 → 尊重

问题:"2D + 需 exe" 走哪个分支?(决策树无此组合)
解决:决策树应有"2D 桌面游戏(需 exe)→ Godot 4"分支
```

**严重级别**:
- 决策树有遗漏场景 → WARNING
- 分支条件重叠 → INFO
- 无兜底分支 → WARNING

---

## 4.4 模板索引与产物路径表同步

**检查项**:
1. 模板索引中列出的模板文件,对应产物会出现在产物路径表中
2. 产物路径表中的产物,都能追溯到模板索引中的模板
3. 新增模板时,产物路径表同步更新

**检查方法**:
```
1. 从模板索引提取所有模板 → 预期产物类型集合 A
2. 从产物路径表提取所有产物类型 → 集合 B
3. A - B = 有模板但无产物路径(WARNING)
4. B - A = 有产物路径但无模板(CRITICAL,无法生成)
```

**严重级别**:
- 产物无对应模板 → CRITICAL
- 模板无对应产物路径 → WARNING

---

## 4.5 阶段裁剪规则完备

**检查项**(仅流水线审查):
1. 有阶段裁剪规则表(按复杂度裁剪)
2. 裁剪后仍产出占位文档(不跳过产出)
3. 可选阶段(如 polish)有独立裁剪判断
4. 裁剪结果写入蓝图(可追溯)

**标准裁剪规则结构**:
| 复杂度 | 特征 | 裁剪 |
|---|---|---|
| ★ 极简 | ... | 跳过 X |
| ★★ 简单 | ... | 跳过 Y |
| ... | ... | ... |

**检查方法**:
```
1. 搜索"裁剪"关键词
2. 验证有裁剪规则表
3. 验证裁剪后有占位产出说明
4. 验证可选阶段有独立判断
```

**严重级别**:
- 无裁剪规则 → WARNING(简单游戏走全流程浪费)
- 裁剪后无占位产出 → CRITICAL(下游读不到产物)

## 4.6 扩展点显式化

**检查项**:
1. skill 明确标注"可扩展点"(如"此处可新增引擎分支")
2. 扩展点有模板/示例(如四位一体的扩展模板)
3. 扩展不破坏现有流程(向后兼容)

**优质扩展点示例**:
```markdown
### 决策结果写入
引擎选择结果写入 docs/GAME_BLUEPRINT.md 的"3. 平台与引擎"章节,格式:
平台:{平台}
引擎:{引擎名}
依赖:{依赖列表}
理由:{一句话}
```
→ 新增引擎时,按此格式填入即可,无需改流程。

**检查方法**:
```
1. 搜索"扩展"/"新增"/"可添加"关键词
2. 验证扩展点有模板示例
3. 评估扩展是否需要改核心流程(应只加不改)
```

**严重级别**:
- 无扩展点标注 → INFO
- 扩展需改核心流程 → WARNING
