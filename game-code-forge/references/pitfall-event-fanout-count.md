# 一次事件扇出 N 个下游,先规定「按事件计」还是「按对象计」

## 现象

一次操作改动了 N 个对象（消除一片、批处理一批、结算一组），随后 N 个对象各自发出联动：音效、粒子、飘字、计分、埋点。此时"发生了几次"有三种答案：

| 口径 | 一次操作涉及 6 个对象时 |
|---|---|
| 按事件计 | 1 次 |
| 按对象计 | 6 次 |
| 按下游消费者计 | 6 × 4 个通道 = 24 次 |

三种都"说得通"。没规定用哪个，就是 bug 的温床——而且**两边的单元测试都能过**，因为单测通常只喂一个对象。

## 典型后果

- **连击虚高**：一次操作跳 6 连，玩家看到 `x6`，而实际只做了一次决策。
- **音效糊成噪音**：同一帧播 6 个同 ID 音效，超过并发上限，最先播的被打断，听起来像电流声。
- **飘字刷屏**：6 个 `+10` 叠在一起，遮挡战场。
- **埋点虚高**：转化率、操作密度、提示使用率全部乘了 N。

## 判据（写进 TECH_DESIGN，缺一不可）

任何一个事件在下游被多个消费者读取时，必须写清三件事：

1. **计数单位**：事件 / 对象 / 格数 / 通道（四选一，不许含糊）。
2. **去重窗口**：同一 tick / 同一帧 / 100ms / 不去重。
3. **去重责任方**：发事件方还是消费方——**只允许一处负责**，两处都去重会漏计数。

> 判断口诀：**"玩家做了一次动作，还是做了一次动作的 N 分之一？"** 主体是玩家 → 按事件计。

## 正确写法

由**发事件方**提供批次标识，消费方按它去重：

```ts
// 发事件方
const batchId = nextBatchId();
for (const obj of affected) emit('obj:cleared', { id: obj.id, batchId });

// 消费方（音效）
if (lastBatchId === batchId) return;   // 同批只响一次
lastBatchId = batchId;
play('sfx_clear');
```

计分若确实该按对象累加，就明确写"计分按对象、反馈按事件"——**同一事件允许两种口径，但必须各自声明**。

## 反例（都真实发生过）

- 音效逐个对象播 → 糊；改成同批只响一次后，"整批弹起"才听得清。
- 一次操作里 `combo` 按对象累加 → 连击数瞬间 6，与玩家感知不符。
- 埋点按 listener 触发次数记 → 操作密度指标虚高一个数量级，难度模型据此误判。

## 验法

- 构造"一次操作涉及 N 个对象"的局面，断言下游计数 = 1（或 = N，按你规定的口径），并**把口径写进验证清单**。
- 对埋点单独断言：一次操作只产生一条该事件的记录（除非口径就是按对象）。
