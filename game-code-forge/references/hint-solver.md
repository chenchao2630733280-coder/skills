# 提示系统骨架（Hint Solver）

> 给 `game-code-forge` 用。触发条件：PRD §1.5「提示与引导」存在且非"无"。
> 本文与机制无关——只规定**结构**，规则由项目自己填。

---

## 1. 适用与不适用

| 适用 | 不适用 |
|---|---|
| 状态可枚举、存在"合法操作"判定的游戏（解谜、消除、规划、推箱子、卡牌对局） | 纯反应类（跑酷、弹幕），提示只能给"方向感"，用高亮即可，不必上求解器 |
| 单局状态空间可裁剪到可搜索（深度 ≤ 数十步、分支 ≤ 数十） | 状态含连续物理量的游戏（提示应改为"示范录像"而非搜索） |

判据一句话：**能不能写出 `isLegal(state, action)` 和 `apply(state, action) -> state`**。能，就能做求解器；不能，别硬做。

---

## 2. 六条骨架

### ① 规则单一来源

求解器**必须 import 运行时的规则实现**，不得复制一份"求解器专用规则"。

- 反例：求解器自己写一遍"什么算合法操作"，改玩法时只改了运行时 → 提示给出非法解，玩家信任一次就没了。
- 连**遍历顺序**都要一致：若运行时按 A→B 顺序处理，求解器也按 A→B，否则同一局面得出不同结论。
- 验法：`grep` 求解器目录，不应出现第二份 `isLegal` / `apply` 实现；或加一条断言"随机 N 个局面，两边判定的合法操作集合完全相同"。

### ② 输出是"计划"，不是"下一步"

一次搜索产出**整条计划**（动作序列）并缓存；玩家偏离计划（执行了别的动作）才重算。

- 反例：每次点击都重算 → 提示在相邻两步之间跳来跳去（抖动），且玩家回退后提示"换了主意"。
- 计划要有**游标**：`plan[cursor]` 是当前该做的动作；每执行一步 `cursor++`；偏离则整条作废。
- 验法：连点三次提示，三次给出的应是同一计划的第 1/2/3 步，而不是三个互不相干的"下一步"。

### ③ 预算 + `exact` 语义

搜索必须有上限（节点数或毫秒），超限时**降级输出而不是假装成功**。

```
{ exact: true,  plan: [...] }              // 搜到确切解
{ exact: false, hint: "试试把注意力放到左侧", plan: [] }   // 超预算，只给方向
```

- 反例：超预算后返回一条没验证过的路径 → 玩家照着走卡死，比不给提示更糟。
- `exact` 必须透传到 UI 与埋点：`hint_show` 事件里带 `hint_type`（direction / step / answer）与 `exact`。
- 验法：构造一个必然超预算的局面，断言返回 `exact: false` 且 `plan` 为空。

### ④ 强度三档，不许默认给答案

| 档位 | 给什么 | 适用 |
|---|---|---|
| 方向 | 高亮"能动的东西"/ 提示观察区域 | 第一次卡住 |
| 步骤 | 下一手具体操作 | 多次无进展 |
| 答案 | 整条路径逐步高亮 | 明确点了"看答案" |

默认档位由 PRD §1.5 的卡住判定决定（连续 N 次无有效操作 / 停留超时 / 失败 K 次），**不能是"随时可点"**——那会把提示变成作弊器，直接毁掉难度曲线。

### ⑤ 已知限制要写进交付物

求解器的能力边界是**交付物的一部分**，不是内部备注。至少写清：

- 哪类局面搜不出来（状态空间爆炸 / 需要连续操作 / 依赖随机种子）；
- 超预算的典型场景；
- 提示与"最优解"的关系（是"一条可行解"还是"最短解"）。

不写，下游会以为"没提示 = 无解"，而这通常是两件事。

### ⑥ 提示质量进验收

提示给的解**必须能在游戏里走通**。最低要求一条回放断言：

```
取一个真实局面 → 求解器给出 plan → 自动执行 plan → 断言到达胜利条件
```

这条断言能一次拦住"规则分叉""计划过期""游标错位"三类 bug。

## 3. 最小接口

```typescript
/** 由项目实现，必须与运行时共用 */
export interface Rule<S, A> {
  isLegal(state: S, action: A): boolean;
  apply(state: S, action: A): S;        // 纯函数，不得修改入参
  isWin(state: S): boolean;
  isDead(state: S): boolean;            // 无合法操作且未胜
  actions(state: S): A[];               // 顺序须与运行时的遍历顺序一致
}

export interface HintResult<A> {
  exact: boolean;
  plan: A[];                            // exact=false 时为空
  hint?: string;                        // 方向档文案
  nodes: number;                        // 搜索节点数，进埋点
}

export interface HintSolver<A> {
  solve(state: unknown, budgetMs: number): HintResult<A>;
  /** 玩家执行一步后推进游标；返回 false 表示已偏离计划，需重算 */
  advance(action: A): boolean;
  reset(): void;
}
```

实现建议：**迭代加深 DFS + 已访问集合**（状态需可哈希）。`actions()` 的顺序直接决定找到的是哪条可行解，所以顺序是规则的一部分（见骨架 ①）。

## 4. 计划缓存与失效

| 事件 | 处理 |
|---|---|
| 玩家执行了 `plan[cursor]` | `cursor++`；计划走完则清空 |
| 玩家执行了计划外的动作 | 整条计划作废，下次请求重算 |
| 关卡重开 / 读档 | 清空缓存 |
| 状态哈希不匹配 | 作废（防御性检查，宁可多算一次） |

不要做"局部修补"（保留后半段计划）——修补逻辑比重算更容易错，而重算成本已被预算限制住。

---

## 5. 面板怎么读（UI 契约）

提示面板至少三段，与档位一一对应：

1. **看哪**：高亮可操作对象 / 目标区域（不动手）
2. **点哪**：高亮具体对象 + 手势提示（动一次手）
3. **为什么**：一句因果说明（"这个被压住了，先清它"）

第三段是留存关键：只给动作不给理由，玩家第二次遇到同类局面仍然卡住。

## 6. 验收清单

- [ ] 求解器与运行时**只有一份**规则实现（`grep` 无第二份 `isLegal`/`apply`）
- [ ] 随机 N 个局面，两边合法操作集合一致
- [ ] 连续请求三次提示，得到的是同一计划的第 1/2/3 步
- [ ] 必然超预算的局面返回 `exact: false` 且 `plan` 为空
- [ ] 取真实局面回放 `plan`，能到达胜利条件
- [ ] `hint_show` 埋点带 `hint_type` 与 `exact`
- [ ] 引导存在时，`skipTutorial()` / `forceStep(id)` 已实现（否则引导关验证全假绿）
