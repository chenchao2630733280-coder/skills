# 业务领域模式库（Business Domain Patterns）

> 本文件从 App AI UI Design System v2.0-v2.3 的垂直业务章节蒸馏而来，作为 generate-system-prd 生成 PRD 时的**领域检查清单与建模启发式**。
>
> **定位声明**：
> 1. 领域模式是**检查清单与启发式**，不是模板硬套。用户实际需求与模式冲突时以需求为准，差异记入 `decision-log.json`。
> 2. 本文件只定义"业务侧应该存在什么实体/角色/状态/流程"（What），不定义任何页面渲染方式（How）；渲染知识由下游 `generate-html-mobile` / `generate-html-pc-admin` 承担。
> 3. 领域结论最终以 PRD 文档和 `state-machines.json` / `business-rules.json` / `pages.json` 工件为权威载体，本文件不产出项目实例数据。

---

## 一、读取规则（懒加载）

1. 仅当 Step 1 需求收集识别出对应领域时，读取对应章节；**不要预读全文**。
2. 一个项目可能命中多个领域（如"宠物保险"同时命中宠物+保险；"宠物医院预约"同时命中宠物+医疗）。此时多个领域章节都要读取，并注意实体合并建模（例如 Pet 既是宠物档案实体，也是保单被保对象、预约服务对象）。
3. 识别出垂直领域后，Step 2 生成第 3 章（核心领域与数据设计）、第 4 章（关键业务流程）、第 5 章（特殊业务场景）、第 7 章（权限体系）前，应先对照对应领域的"领域检查清单"。
4. Step 3 交叉校验时，对命中的每个领域执行"领域完整性校验"（即各领域末尾的检查清单）。

## 二、领域识别与复杂度评估

### 2.1 六维识别（Step 1 需求收集时执行）

对项目回答以下六个维度：

| 维度 | 取值 | 判断依据 |
|------|------|---------|
| Project Type（项目类型） | Commerce / Finance / Insurance / Healthcare / Government / City / Enterprise / Content / Social / Productivity / Travel / Pet / Other | 需求描述中的业务对象与核心场景 |
| Trust Level（信任等级） | Low / Medium / High / Critical | 是否涉及资金、健康、身份、法律效力 |
| Transaction Level（交易等级） | None / Low / Medium / High | 是否有支付、退款、结算、回查 |
| Form Complexity（表单复杂度） | Low / Medium / High | 是否多步骤、多对象、强校验表单 |
| State Complexity（状态复杂度） | Low / Medium / High | 核心对象是否有长生命周期状态机、是否多状态机并行 |
| Local Service（本地服务） | 无 / 纯数字 / 预约+线下 | 是否依赖线下履约 |

**输出**：领域结论（命中哪些垂直领域）+ 复杂度评级。复杂度评级决定第 3/4/5/10 章的篇幅与颗粒度：High 维度越多，状态机、校验规则、异常场景必须写得越完整。

### 2.2 复杂度矩阵

| 维度 | Low | Medium | High |
|------|-----|--------|------|
| 角色 | 单角色 | 多角色 | 监护/代理（操作人≠操作对象） |
| 状态 | 少 | 中 | 多状态机并行（如业务态≠支付态） |
| 表单 | 简单 | 中等 | 多步骤 |
| 交易 | 无 | 单步 | 支付+核验+回查 |
| 服务 | 数字交付 | 本地服务 | 预约+线下履约 |
| 内容 | 少 | 中 | 内容流 |
| 数据 | 简单对象 | 多对象 | 关系型（实体间监护/归属/授权） |

> 经验结论：视觉轻松的领域业务模型未必简单。宠物项目在本地服务、内容、实体关系三个维度均为 High；医疗项目在角色、状态、表单三个维度均为 High。

## 三、通用领域抽象（跨领域建模启发式）

无论命中哪个垂直领域，第 3 章数据建模时可使用以下统一抽象。这些抽象来自保险、家庭保险、宠物、医疗、城市服务五类真实项目的共性提炼。

### 3.1 实体统一结构

所有复杂业务实体都可以按以下六段结构展开（第 3 章为每个核心实体补齐这六段，不适用的段显式标注"无"）：

```text
Entity
├── Identity     （标识：编号、名称、证件）
├── Status       （状态：生命周期状态机）
├── Metadata     （基础属性）
├── Content      （附件/图文/文档）
├── Actions      （可执行操作）
└── History      （操作与变更历史）
```

示例：保单 = Identity(保单号) + Status(保单状态机) + Metadata(产品/参保人/保障期限) + Content(条款文档) + Actions(退保/理赔/续保) + History(保全记录)。
示例：宠物 = Identity(宠物编号) + Status(健康状态机) + Metadata(品种/性别/生日/体重) + Content(照片) + Actions(编辑档案/预约) + History(疫苗与就诊时间线)。

### 3.2 角色-关系模型（Actor / Role / Relationship）

当"操作人≠被操作对象"时（家长为孩子投保、监护人为患儿挂号、主人为宠物预约），必须显式建模：

```text
Actor          （操作人）
Role           （关系角色）
Relationship   （与操作对象的关系）
Identity       （双方证件信息）
Authorization  （授权状态）
Eligibility    （操作对象的资格）
```

- 关系角色枚举参考：SELF / CHILD / SPOUSE / PARENT / DEPENDENT / OTHER（对应：本人/子女/配偶/父母/其他家属/其他）。
- 关系是业务数据，进入第 3 章数据模型和第 7 章权限矩阵；操作人与对象分离的场景，第 4 章流程中的关键步骤应包含"当前操作对象是谁"。

### 3.3 资源-容量-锁模型

带容量/时段的资源（号源、房间、名额、时段）统一按以下链路建模：

```text
Resource（资源）→ Schedule（排期）→ Capacity（容量）→ Availability（可用性）
→ Reservation（预约）→ Lock（锁定）→ Expiration（超时释放）
```

关键规则：资源被选中到支付/提交确认之间存在**锁定窗口**，超时必须自动释放并回补容量。锁定时长、释放规则写入第 4 章流程，并发冲突写入第 10 章校验规则。

### 3.4 记录模型

业务产出物（保单、报告、订单、病历、检验记录、体检报告）统一结构：

```text
Record
├── Owner        （归属人）
├── Type         （类型）
├── Date         （日期）
├── Status       （状态）
├── Content      （内容/指标）
├── Attachments  （附件）
└── History      （历史）
```

### 3.5 动作分级

所有业务动作统一分为四级，第 4/8 章按此分级描述操作：

```text
Primary      （主行动，每流程一个）
Secondary    （次行动）
Tertiary     （辅助行动）
Destructive  （破坏性/不可逆动作）
```

破坏性动作在第 4 章必须定义冲销/撤销机制或二次确认规则，并在第 10 章配置套校验规则。

## 四、垂直领域模式

### 4.1 保险 / 金融

#### 领域特征

- 信任等级：Critical（资金 + 法律效力）
- 状态复杂度：High（核保态、支付态、保单态并行）
- 角色复杂度：Medium（投保人与被保人可为同一人，也可分离）
- 表单复杂度：High（资格判断 + 长协议）

#### 核心实体与角色

- 实体：产品、参保人、保单、支付单、协议文本（条款/投保须知/服务协议/授权书）
- 角色：投保人（操作人）、被保人（保障对象）、受益人
- 保障内容必须是结构化数据（保障项目×保额矩阵），不是一段营销文案

#### 关键状态机清单

1. **支付状态机与保单/业务状态机是两个独立状态机**，不得合并为一个 success 字段。终态组合"支付成功 + 保单生成中"合法存在，各状态机单独编号（SM-XXX）。
2. 核保状态机（5 态）：Idle / Loading / Success / Failed / Pending
3. 支付回查状态：Payment Unknown / Success / Failed / Cancelled——第三方支付回跳后结果不确定，必须支持回查
4. 保单状态机：处理中 / 生效中 / 已失效（按产品定义扩展）

#### 流程要点

```text
进入专区 → 产品说明 → 选择参保人 → 身份信息 → 资格核验 → 报价
→ 协议确认 → 支付 → 支付结果（含回查）→ 保单
```

- 资格核验（Eligibility）是重要业务结果：符合时列出各通过项；不符合时必须给出可解释原因与修改入口，不能只写"不符合"。
- 核保是异步过程，"预计需要几秒钟"这类过程性反馈属于业务状态而非简单 loading。
- 产品说明属于高解释成本内容，应按"产品是什么→谁可以买→保什么→多少钱→怎么理赔→有哪些限制→如何投保"的信息顺序组织（落第 8 章产品说明页规格）。

#### PRD 章节落点映射

| PRD 章节 | 落点内容 |
|---------|---------|
| 第 3 章 | 参保人/保单/支付单/协议实体 + 双状态机字段 + 保障矩阵数据结构 |
| 第 4 章 | 投保全流程 + 支付回查 + 核保异步 + 资格核验 |
| 第 5 章 | 资格不符、核保失败（原因可解释）、支付结果不确定 |
| 第 7 章 | 代投保时的关系与授权权限 |
| 第 10 章 | 重复支付、超时锁定、资格复核规则 |

#### 领域检查清单

- [ ] 支付状态机与保单状态机是否分离定义？
- [ ] 资格不符时是否给出可解释原因与修改入口？
- [ ] 第三方支付回跳后是否覆盖"结果未知"态与回查机制？
- [ ] 协议是否作为可查阅实体（条款/须知/授权书分别可打开），而非一段合并不分？
- [ ] 保障内容是否为结构化数据（保障项目×保额）？
- [ ] 核保失败是否回答三问：发生了什么/为什么/下一步怎么办？
- [ ] 退保/理赔的入口、状态与到账路径是否定义？

### 4.2 家庭保险 / 儿童保险

#### 领域特征

- 角色复杂度：High（监护关系，操作人≠被保人）
- 表单复杂度：High（多人信息 + 资格判断 + 长协议）
- 信任等级：Critical

#### 核心实体与角色

- 角色模型：投保人/监护人 → 本人 / 子女 / 其他被保人（使用 3.2 的 Actor/Role/Relationship 建模）
- 授权实体：独立授权对象（谁授权、授权时间、授权范围）
- 被保人档案：关系 + 姓名 + 证件 + 手机 + 资格标记，支持新增/编辑/删除
- 家庭保障视图：按成员汇总保障项数、年度保额、保单数

#### 关键状态机清单

1. 授权状态机（5 态）：Not Authorized / Authorizing / Authorized / Authorization Expired / Authorization Failed
2. 验证流程四步分离，各步独立状态与失败原因：身份核验 → 医保核验 → 资格判断 → 核保
3. 被保人档案状态：已存在 / 未授权 / 待验证 / 验证失败 / 信息过期

#### 流程要点

```text
多人选择 → 被保人档案管理（增删改）→ 授权 → 资格核验 → 报价
→ 协议 → 支付 → 保单 → 家庭保障汇总视图
```

- 被保人选择支持单选/多选/编辑/新增/删除，"新增被保人"是一级业务动作。
- 验证四步必须分开定义：每步有独立状态、失败原因与重试入口，不能合并为一个"正在加载"。

#### PRD 章节落点映射

| PRD 章节 | 落点内容 |
|---------|---------|
| 第 3 章 | Actor/Role/Relationship/Authorization/Eligibility 实体 + 授权状态机 |
| 第 4 章 | 被保人增删改流程、授权流程、验证四步流 |
| 第 5 章 | 授权过期、验证失败、信息不一致场景 |
| 第 7 章 | 监护人代操作权限矩阵（谁能为谁投保/查询） |
| 第 8 章 | 被保人选择、家庭保障汇总、成员切换页面规格 |
| 第 10 章 | 敏感信息脱敏与编辑授权规则、被保人唯一性校验 |

#### 领域检查清单

- [ ] "用户"与"被保人"是否显式区分（不默认同一对象）？
- [ ] 关系（本人/子女/配偶…）是否作为显式数据字段？
- [ ] 授权是否有独立状态机（含过期态）？
- [ ] 敏感数据是否定义"列表/摘要态脱敏、编辑态经授权"的双态规则（姓名/证件/手机/保单号脱敏格式）？
- [ ] 验证四步（身份/医保/资格/核保）是否分开定义状态与异常？
- [ ] 家庭保障汇总（按成员）是否在第 8 章有对应页面？

### 4.3 宠物 / 情感陪伴 / 本地宠物服务

#### 领域特征

- 内容复杂度：High（资讯/故事/活动内容流）
- 本地服务：High（预约 + 线下履约）
- 信任等级：Medium（领养场景为 High——高情感高责任）
- 交易等级：Medium

#### 核心实体与角色

- **Pet 是业务实体，不是用户资料里的一个头像字段**。标准档案字段：照片/姓名/品种/性别/年龄/生日/体重/颜色/绝育状态/疫苗状态/驱虫状态/健康状态/所在地；可扩展：血型/芯片/病史/过敏史/合作医院/保险/免疫记录。
- 服务实体：宠物医院/宠物店/洗护/训练/血型检测/领养/救助（含位置/距离/营业时间/联系方式/预约能力）
- 内容实体：文章/活动/救助故事
- 角色关系：主人（操作人）→ 宠物（对象）。多宠物场景必须支持"当前宠物"上下文：切换后健康数据、预约、保险、推荐内容全部跟随切换。

#### 关键状态机清单

1. 宠物健康状态机：Healthy / Attention / Treatment / Recovered / Unknown
2. 疫苗时间状态（不是布尔值）：未接种 / 已接种 / 即将到期 / 已过期
3. 领养申请状态机：Draft → Submitted → Reviewing → Approved → Contacting → Meeting → Adoption Confirmed → Completed；异常：Rejected / Cancelled / Expired
4. 服务预约状态机：Idle → Selecting → Reserved → Confirmed → Completed；异常：Cancelled / Expired / No-show
5. 本地服务营业状态：Open / Closed / Busy / Booking / Full / 24H

#### 流程要点

- **领养不是电商 Checkout**，完整流程：
```text
浏览宠物 → 筛选 → 查看详情 → 填写申请 → 填写调查问卷 → 志愿者审核
→ 沟通 → 视频/照片确认 → 线下领养 → 签订协议 → 完成
```
- 领养申请表属于"高意愿、强责任、半结构化表单"：领养原因/家庭情况/居住情况/养宠经验/是否接受回访/是否接受家访/是否已有其他宠物/是否愿意长期承担医疗费用；开放式问题给明确引导语。
- 领养须展示信任要素：审核流程步骤、预计时间、联系机制、审核标准、责任说明、后续服务。
- 服务预约与内容发现是两条并行业务线（Transaction vs Discovery），信息架构上分开组织。

#### PRD 章节落点映射

| PRD 章节 | 落点内容 |
|---------|---------|
| 第 2 章 | 信息架构区分：首页（当前宠物/快捷服务/活动/资讯）/ 宠物档案 / 服务 / 领养 / 我的 |
| 第 3 章 | 宠物档案/服务/内容/领养申请实体 + 5 组状态机 |
| 第 4 章 | 领养全流程、服务预约流程、宠物档案管理流程、宠物切换逻辑 |
| 第 5 章 | 疫苗过期提醒、预约爽约、领养审核驳回场景 |
| 第 7 章 | 志愿者/审核方角色权限 |
| 第 8 章 | 宠物切换、健康/疫苗时间线、服务目录与筛选、领养筛选与申请页面 |
| 第 10 章 | 多宠物切换一致性、领养申请唯一性、疫苗到期计算规则 |

#### 领域检查清单

- [ ] 宠物是否作为独立实体建模（含完整档案字段），而非用户资料字段？
- [ ] 多宠物场景是否支持"当前宠物"上下文（操作明确对象）？
- [ ] 领养流程是否按"内容+筛选+审核+沟通+线下交付"完整建模，而非简化为下单？
- [ ] 疫苗/驱虫是否用时间状态（即将到期/已过期），而非布尔值？
- [ ] 领养申请是否定义审核方角色（志愿者）与审核标准/流程步骤？
- [ ] 本地服务是否覆盖位置/距离/营业时间/联系方式/预约能力？
- [ ] 领养问卷的开放式问题是否有引导语与字数约束？

### 4.4 医疗公共服务 / 预约挂号

#### 领域特征

- 信任等级：Critical（健康 + 实名）
- 状态复杂度：High（号源/预约/排队/报告多状态机并行）
- 角色复杂度：High（登录人≠就诊人）
- 表单复杂度：High（实名 + 多种证件类型）

#### 核心实体与角色

- **就诊人（Patient）与登录用户分离**。"常用联系人"不是通讯录，而是就诊人档案（本人/儿童/新生儿/家属/其他联系人），含证件类型与实名验证。
- 证件类型是身份模型的一部分，不是普通下拉框：居民身份证/港澳居民居住证/台湾居民居住证/护照/外国人永久居留身份证/新生儿凭证/其他医疗凭证。
- 医疗资源层级：医院（名称/等级/性质/多院区）→ 院区 → 科室（一级/二级）→ 医生（职称/科室/擅长/排班）。**多院区必须显式建模**——院区是预约的核心上下文。
- 排班与号源：Schedule（日期+时段+医生+科室+院区+容量+剩余）→ Slot
- 临床数据：检验报告/检查报告/影像报告/疫苗接种记录
- 排队叫号：当前叫号/我的号码/前方人数/诊室
- 科室公告属于高优先级业务信息（如停诊通知），与普通资讯分开建模。

#### 关键状态机清单

1. 号源状态：Available / Selected / Booked / Full / Expired / Closed / Waiting
2. 预约状态机：Selecting → Selected → Pending Confirmation → Booked → Upcoming → Checked In → Waiting → Completed；异常：Cancelled / Refunded / Missed(爽约) / Expired / No-show
3. 排队状态机：Not Started → Waiting → Almost Ready → Called → Missed / Completed
4. 报告状态：Pending / Available / Abnormal / Archived
5. 就诊人验证：Verified / Unverified

#### 流程要点

- 标准预约挂号全流程：
```text
登录 → 选择就诊人 → 选择医院 → 选择院区 → 选择科室 → 选择门诊类型
→ 选择医生 → 选择日期 → 选择号源 → 锁定号源 → 确认预约 → 支付
→ 预约成功 → 到院 → 签到 → 候诊 → 叫号 → 就诊 → 完成
```
- **号源锁定**：选择到支付之间存在锁定窗口，须定义锁定时长（倒计时）、超时自动释放、释放后容量回补；这是医疗预约区别于普通服务预约的关键。
- 确认页要素（一级信息）：医院/院区/科室/医生/日期/时间/就诊人/费用/就诊方式/注意事项；挂号费用结构（挂号费/诊疗费/合计）要让用户理解为什么付这笔钱。
- 支付区分两个维度：**费用结算方式（医保/自费/医保+自费）**与**支付渠道**，不是同一概念。
- 退号/取消必须说明：是否可退/退款金额/退款路径/截止时间/影响。
- **爽约（Missed）是与"失败"不同的独立状态**，须说明信用影响（如影响后续预约次数）。
- 预约处理中（Pending）不能直接显示为成功。

## 五、跨领域复用提示

1. **主题与业务模式分离**：同一视觉主题可承载不同业务模式（如医疗主题下既有预约模式也有内容模式）；PRD 只关心实体/状态/流程，视觉主题由下游阶段决策。
2. **多领域命中时实体合并**：宠物医院 = Pet 实体 + 医院层级 + 号源锁定 + Record（宠物病历）；医保衔接保险 = 保险流程 + 医保结算维度。合并时以 3.x 通用抽象为桥接。
3. **复杂度决定深度**：六维评级全为 Low 的项目（纯展示官网）不需要本文件大部分内容，仅保留 3.5 动作分级即可。
