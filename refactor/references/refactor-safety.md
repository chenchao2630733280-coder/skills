# 安全重构规则 (refactor-safety)

本文件是 `refactor` skill 的安全准则。重构的前提是"不改变外部行为",任何破坏该前提的做法都属违规。规则按"做事顺序 + 底线约束 + 异常处置"组织。

---

## 1. 小步重构 (Small Steps)

**规则**
- 每次只改一处:一个方法、一个变量、一段提取,不一稿多改。
- 单步改动应小到"几分钟内可审阅完毕"。
- 不在同一小步里并行多项独立重构。

**做法**
- 开始前列出重构步骤清单(对应 `refactor-plan.md`)。
- 每完成一步即提交一次(或打一个检查点),保持可回溯。
- 下一步开始前确认上一步已通过测试。

**反例**
- 一次性重命名 20 个符号 + 提取 3 个方法 + 合并两个类 → 失败时无法定位。

---

## 2. 每步保测试 (Test After Every Step)

**规则**
- 每个小步完成后立即运行相关测试,全绿才进下一步。
- 重构前必须存在可信测试;若测试缺失,先补"特征测试 (characterization test)"锁住现有行为,再重构。
- 测试必须先在"重构前"基线上跑通一遍(确认测试本身有效)。

**做法**
- 记录每步跑的测试命令与结果到 `refactor-report.md`。
- 测试失败时,首选回滚而非就地修(就地修可能掩盖重构引入的问题)。
- 涉及性能重构时,除功能测试外另跑基准对比,确认行为不变且指标改善。

**底线**
- 没有测试且无法补测试的代码,不做风险性重构;仅做最低风险的局部命名/格式类改动,并明确标注风险。

---

## 3. 不混合功能变更 (No Mixed Changes)

**规则**
- 本轮重构期间禁止任何行为变更:不修 bug、不加特性、不改业务规则。
- 发现 bug 时记录到待办,本轮结束后另起流程处理。
- 看到可以"顺手优化"的功能点,克制,不要顺手。

**做法**
- 提交信息只描述重构,不夹带功能描述。
- 若改动必须触及行为才能完成,停止重构,转对应流程(修 bug / 加特性 / 升级)。
- review 时若发现行为变更,该步判为失败,回滚。

**判别**
- 同样的输入,重构后输出/异常/副作用顺序/可观测行为与重构前一致 → 合规。
- 任何差异 → 违规。

---

## 4. 公开 API 不变 (Public API Frozen)

**规则**
- 对外契约保持不变:函数签名、参数顺序、返回值结构、异常类型、可见性、HTTP 接口形状、序列化格式等。
- 重命名/改签名/删参数属破坏性变更,不在本 skill 范围。

**做法**
- 重构前明确"哪些是公开 API"(导出符号、被外部依赖的接口、文档化的契约)。
- 仅改内部实现、私有方法、内部字段组织。
- 若发现公开 API 必须改,停止重构,转为"升级/迁移"流程(需版本号/兼容方案)。

**例外**
- 仅本项目内部、无外部消费者时,跨模块改名仍建议分两步:先加新名委托旧名 → 迁移调用方 → 删旧名,每步可测可回滚。

---

## 5. 原逻辑保留 (Keep Original as Comment)

**规则**
- 复杂或易错的改动,保留旧实现作为注释,直到测试与人工验证通过后再删除。
- 不要在验证通过前就清理"看起来多余"的旧代码。

**做法**
- 注释格式建议 `// OLD:` 或 `/* 原实现:` 块,简短标注。
- 验证通过后,在同一小步或紧接的下一步删除该注释,避免长期堆积死代码。
- 仅对"改写算法/改控制流/改边界条件"这类高风险改动保留;纯命名/格式类无需保留。

**反例**
- 一边大改算法一边删旧实现,测试红时已无对照,无法判断是改错还是测试错。

---

## 6. 可回滚 (Rollback Strategy)

**规则**
- 每一步独立可提交、可回滚。
- 失败时立即回滚到上一个绿色状态,而非"再改一点试试"。

**做法**
- 每步一个 commit(或一个 patch/stash),消息描述该步重构内容。
- 回滚优先级:git revert/checkout 单步 > 整体重置到基线。
- 回滚后重新评估该步:是方法错了还是顺序错了,调整 plan 再试,不盲目重试同样操作。

**底线**
- 连续两步都无法通过测试时,回滚到基线,停止本轮重构,在 `refactor-report.md` 记录阻塞点,交回上游决策。

---

## 附:安全重构速查表

| 维度 | 必做 | 禁止 |
|------|------|------|
| 步幅 | 每步一处,小而独立 | 一稿多改、批量并发 |
| 测试 | 每步跑、先建基线 | 无测试就大改、就地修红测 |
| 范围 | 只改结构/实现 | 夹带功能/bug 修复 |
| API | 公开契约冻结 | 改签名/改返回值/删导出 |
| 旧码 | 高风险处保留注释对照 | 验证前删旧实现 |
| 回滚 | 每步可独立 revert | 失败后继续叠加改动 |

---

## 附:典型风险信号(出现即暂停)

- 测试在重构后变红且无法快速定位 → 回滚。
- 改动不得不触及公开 API → 停止,转升级流程。
- 一段代码没有任何测试覆盖且难以补测 → 仅做最低风险改动或先补测试。
- 重构后性能不升反降且无法解释 → 回滚并复核假设。
- 发现隐藏的多态/反射依赖 → 重新评估该步是否安全,通常需更小步幅。
