# 代码重构 (refactor)

## 一、定位与职责

本 skill 专职**代码重构**:在不改变代码外部行为(功能)的前提下,改善代码的内部结构、可读性、性能或现代化程度。

**核心原则:重构 ≠ 功能变更。**

- 重构:行为不变,结构变好。可验证手段是重构前后测试用例全部通过且输出一致。
- 功能变更:行为改变(新增/修改/删除功能)。
- **强制约束:重构与功能变更必须分两次独立提交。** 不允许在一次改动中既重构又改功能,否则一旦出错无法定位根因。

职责边界:
- ✅ 负责:命名优化、提取方法/类、消除重复、算法替换、API 升级、结构调整。
- ❌ 不负责:修 bug、加特性、改业务逻辑(这些应走对应流程,完成后另起重构)。

## 二、重构目标类型

重构按目标分为四类,启动时需明确本次属于哪一类(可多选,但同一轮小步重构只针对一类)。

| 类型 | 目标 | 典型手段 |
|------|------|----------|
| 可读性 | 让代码更易读、易理解 | 重命名、提取方法、消除魔法数、简化条件表达式 |
| 性能 | 降低时间/空间复杂度或减少冗余开销 | 算法优化、缓存、懒加载、批量化、短路求值 |
| 结构 | 降低耦合、提升内聚、消除重复 | 拆大类、提取接口、提取类、移动方法、合并相似代码 |
| 现代 | 使用更当前的语法/API/库 | 升级废弃 API、用新语法替代样板代码、迁移至标准库 |

选择建议:优先做"可读性"和"结构",它们降低后续重构难度;"性能"需有度量依据(勿过早优化);"现代"需评估升级成本与收益。

## 三、重构模式

详见 `references/refactor-patterns.md`。常用 8 种:

1. **提取方法 (Extract Method)**:把长方法中意图独立的片段抽成新方法。
2. **内联方法 (Inline Method)**:方法体简单到不如直接读,将其调用替换为方法体。
3. **移动方法 (Move Method)**:把方法移到更常用的类,降低跨类耦合。
4. **重命名 (Rename)**:让名字准确表达意图(变量/方法/类/文件)。
5. **提取类 (Extract Class)**:一个类承担过多职责时拆分。
6. **内联类 (Inline Class)**:类已无独立存在价值时合并入另一类。
7. **提取接口 (Extract Interface)**:把多处需要的契约抽为接口,便于解耦与替换。
8. **合并相似代码 (Consolidate Duplicate)**:消除重复分支/相似函数,统一为单一实现。

## 四、安全重构规则

详见 `references/refactor-safety.md`。要点:

- **小步重构**:每次只改一点(一个方法/一个变量),不批量并发改动。
- **每步后跑测试**:每个小步完成后立即运行测试,绿了再进下一步。
- **不混合功能变更**:本轮重构期间禁止任何行为变更。
- **保持公开 API 不变**:对外契约(函数签名/类接口/返回值)保持不变;若必须变,停止重构,转升级流程。
- **保留原逻辑作为注释**:复杂处保留旧实现注释,直到测试与人工验证通过后再删除。
- **可回滚**:每步独立可提交/可回滚;失败立即回滚到上一个绿色状态。

## 五、与 code-review 的联动

重构完成后**强烈建议**过一遍 code-review(若环境中有该 skill):

- 检查是否在"不改功能"的名义下意外引入行为变更。
- 检查命名是否真正准确、抽象是否合理、是否过度设计。
- 检查测试覆盖是否仍充分(重构不应削弱测试)。
- 检查是否引入新的耦合或循环依赖。

联动约定:refactor 产出 `refactor-report.md` 后,可将其作为输入交给 code-review skill 复核;code-review 发现的问题回流为新一轮重构任务。

## 六、产出契约

每轮重构产出以下三件(命名固定,机器可读字段用 JSON):

### 1. `refactor-plan.md` — 重构方案
- 目标类型(可读性/性能/结构/现代)。
- 涉及文件与范围。
- **变更前后对比**:对每个关键改动给出"前/后"代码片段或结构示意。
- 风险点与回滚预案。

### 2. `refactor-report.md` — 执行结果
- 变更文件清单(路径 + 改动类型)。
- diff 摘要(新增/删除/修改行数,关键 hunk)。
- 测试结果(命令 + 通过/失败数 + 耗时)。
- 与 plan 的偏差说明。

### 3. `refactor-report.json` — 机器可读结果
```json
{
  "target": "string, 重构目标文件或模块",
  "goal": "string, 目标类型 readability|performance|structure|modernization",
  "changes": [
    { "file": "string", "type": "modified|added|deleted|renamed", "summary": "string" }
  ],
  "testResult": {
    "passed": 0,
    "failed": 0,
    "command": "string",
    "durationMs": 0
  },
  "timestamp": "ISO 8601 string"
}
```

## 七、质量检查清单

完成重构前逐项确认(全部为 ✅ 方可交付):

- [ ] 重构全程未改变外部行为(测试前后一致)。
- [ ] 每个小步后都跑过测试并保持绿色。
- [ ] 未夹带任何功能变更/bug 修复。
- [ ] 公开 API(签名/接口/返回值)未变。
- [ ] 复杂改动的旧逻辑注释已保留至验证通过。
- [ ] 命名准确、无魔法数、无残留死代码。
- [ ] 未引入新的循环依赖或更紧耦合。
- [ ] `refactor-plan.md` / `refactor-report.md` / `refactor-report.json` 三件齐备。
- [ ] 已建议(或已执行)code-review 复核。
- [ ] 每步独立可回滚,失败可安全回到上一绿色状态。
