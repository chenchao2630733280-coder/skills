# 程序化美术交付纪律 (procedural-art-forge)

## 一、定位与职责

**程序化美术** = 画稿是代码，不是位图。它的价值不是"省美术"，而是**可复算、可参数化、可 diff、零外部依赖**。

**适用**：关卡/地图皮肤、图标族、头像/角色占位、数据色块图（热力图、拼贴）、低分辨率像素风、需要随数据变化的插图。
**不适用**：需要精细插画的成品图（走生图 / 手绘）、摄影级素材、复杂光影。

**核心命题：机制全绿 ≠ 认得出。**
所有功能校验通过，画面照样可能读不出是什么。本 skill 的一半篇幅在讲"怎么看图"，因为另一半——"怎么画"——通常不是瓶颈。

---

## 二、三件套（缺一个就会退化成手工改数据）

| 件 | 职责 | 反面 |
|---|---|---|
| **原语库** | 提供 `rect / line / disc / ellipse / poly / mound / wave / paint` 等落到统一网格的图元 | 每个元素写一段 ad-hoc 像素循环 ⇒ 不可复算 |
| **配方脚本** | 一张画 = 一个函数 + 一组参数（尺寸、配色、密度）；生成器只负责"画 → 定量 → 断言 → 落盘" | 手工改产物 JSON ⇒ 下次重跑全部丢失 |
| **三级校验** | 字符图 → PNG 预览 → 实机截图 | 只跑功能校验 ⇒ 上线才发现"画糊了" |

**关键约束：画与量必须分离。**
画稿函数只产出网格；拆单元/算难度/写 JSON 由生成器统一做。混在一起会导致"为了凑某个数值去改画面"，最后画和机制互相污染。

原语语义与组合套路见 `references/primitives.md`。

## 三、可辨识度六纪律

| # | 纪律 | 违反的症状 | 改法 |
|---|---|---|---|
| 1 | **粒度预算**：块状 ≥3×3 格；**曲线形体的直径 ≥7×7**（5×5 的圆算出来是菱形，读成十字） | 人物读成"带球的柱子"；太阳读成十字、云读成方块 | 块状画不出就删；**曲线形体别指望参数化，见纪律 6** |
| 2 | **同色必须隔离**：同色不同物体不许相接 | 云和雪冠连成一条白带、山尖消失 | 改位置：把两者放到画面两端；**不要靠加色解决** |
| 3 | **背景色不能画前景**：主色不能用来描述"前景物体" | 用天空色画海面 ⇒ 海面出现一个个"洞" | 前景一律用与背景有明度差的色 |
| 4 | **线宽 ≥ 2 格**：1 格线在 16px 格上是噪点 | 浪脊读成灰霾、树干读成电线杆 | 线加厚；或用"块"代替"线" |
| 5 | **前景不抢中景**：框景元素只放边角 | 四棵树从顶端长到底，主体被盖成一条缝 | 主体区（画面中部 60%）必须留空 |
| 6 | **形状表优先**：≤32 格宽的画面，或任何"细节形体"（梗/叶/窗/门/高光），一律用**逐格形状表**，不用 `poly`/`disc`/`ellipse` | 参数化画出的圆是多边形、叶片是尖三角、梗细到消失 | 用 `stamp([...多行字符])` 贴形状表；参数化只留给 40+ 格的大形体（山、海、云带） |

配套三条经验：

- **参数化原语的天花板是格点，不是代码。** `disc` 按格心判定，直径 5 输出的是「1-3-5-3-1」菱形，
  直径 7 才勉强读成圆。**这不是实现 bug，是像素艺术的固有约束** —— 人眼要的圆是「四角挖掉」，
  算法给的是「逐行等距收窄」，两者在小尺寸上必然分叉。实测过一次：18×11 画布上
  `disc(r=0.2)` 画太阳，出来是个十字，改用 7 行形状表立刻像太阳。
- **颜色不够用时改位置，不要加色。** 加一个色会改变玩法难度（并发位与类别的比值全变），是设计决策不是美术决策。
- **同色分层靠位置和大小，不靠颜色。** 远浪/近浪同色 → 靠高度差 + 中间那道浪脊分开；中景林/近景树同色 → 靠树尖高度和前后遮挡分开。

完整案例表（症状 / 病根 / 改法，含 12 条实测）见 `references/readability-rules.md`；
原语与形状表的选型判据见 `references/primitives.md` §五。

## 四、构图分层：层数由纵向格数决定

粗算：**每 5 行 ≈ 一层**。

| 纵向行数 | 能容纳的层数 | 典型结构 |
|---|---|---|
| 14–15 | 3 层 | 天 → 山/主体 → 地 |
| 18 | 3 层（+1 层勉强） | 同上，细节靠悬空物体补 |
| 20 | 4 层 | 天 → 远 → **中** → 近 |
| 24+ | 5 层 | 天 → 远 → 中 → 近 → 前景框景 |

**中景是最常缺的一层。** 只画"远 + 近"时，画面会读成"两块色块叠在一起"；补一层中景（远山与主体之间的树林/丘陵/城墙/栏杆）通常比继续加细节有效得多。

### 相对坐标画法

形状按"**距边界几行/几列**"定义，不按绝对行号：

```python
# ✅ 换尺寸不会塌
top = rows - 5                      # 地平线永远在底部往上 5 行
g.poly([(cols*0.1, top), (cols*0.5, 2), (cols*0.9, top)], 'mountain')

# ❌ 只在这一个尺寸下成立
g.poly([(3, 15), (18, 2), (33, 15)], 'mountain')
```

绝对行号会让"雪冠填到第 6 行"在另一个尺寸下变成"填满半座山"。

## 五、三级校验（逐级上，不许跳）

| 级 | 工具 | 看什么 | 耗时 |
|---|---|---|---|
| L1 字符图 | 直接把网格打成 ASCII（每个色一个字母） | 拓扑：有没有空洞、有没有断列、形状是否闭合 | 秒 |
| L2 PNG 预览 | 零依赖渲染（`scripts/preview_grid.py`）+ 纪律自检（`scripts/check_readability.py`） | 比例、明度对比、色块是否黏连；**面积不足/单行噪点/糊满/同色多块**由自检脚本报警 | 秒 |
| L3 实机截图 | 真实运行时截图 | **真实像素尺寸、边距、背景对比、UI 遮挡** | 分 |

- L1 用来抓"结构性错误"（列内空洞、元素越界），改一次看一次。
- L2 是主要迭代循环，比启动游戏快一个数量级。
- **L3 不能省。** 在 750px 设计宽度下 36 列时单格只有 16px，"看起来能认"和"真机上能认"是两件事；边距、外框、UI 压盖也只有实机看得出来。

实施细节见 `references/preview-pipeline.md`。

## 六、反模式

| 反模式 | 后果 |
|---|---|
| 先生成图 → 再降采样成网格 | 细节全丢、出现近重复色（双绿）、抗锯齿混色把底色污染成"粉白" |
| 按绝对行号/列号填形状 | 换尺寸即塌：雪冠变平顶、倒影变金字塔 |
| 每版只跑机制校验不看图 | 机制全绿、画面读不出；返工成本是看图成本的 10 倍 |
| 用 1 列黑柱代表树/杆/柱 | 读成电线杆/烟囱，且会把画面劈成两半 |
| 前景元素从顶端长到底 | 主体被盖掉，只剩一条缝 |
| 用"更复杂"来救"看不清" | 复杂度和可辨识度经常负相关：**删元素往往比加元素更有效** |

## 七、交付物

| 产物 | 内容 |
|---|---|
| 画稿脚本 | 一张画一个函数，参数化尺寸/配色/密度，文件头写画法纪律 |
| 生成器 | 画 → 定量 → 断言（守恒/连续/容量）→ 落盘；**人工改产物视为 bug** |
| 预览脚本 | 零依赖 PNG 渲染，支持整套图横向拼一张对比 |
| 验收图清单 | 每张画的最终预览 + 实机截图，附"这版改了什么" |
| 配色说明 | 新增颜色必须写"为什么不能复用已有色"（颜色即难度） |

## 九、质量检查清单

- [ ] 画稿是代码（可重跑得到同一产物），不是手工改过的 JSON
- [ ] 画与量分离：画稿函数不含难度/拆单元逻辑
- [ ] 形状用相对坐标（距边界几行/列），不写绝对行号
- [ ] 六纪律逐条自检：粒度（块状3×3/曲线7×7）、同色隔离、背景色、线宽、前景占比、形状表优先
- [ ] 至少出过 L2 PNG 预览；**最终出过 L3 实机截图**
- [ ] 同色不同物体之间至少隔 1 格，或靠位置/大小分开
- [ ] 新增颜色有书面理由（否则视为设计变更，回到难度环节重评）
- [ ] 每张画能一句话说清"画的是什么"，且不依赖文字说明
