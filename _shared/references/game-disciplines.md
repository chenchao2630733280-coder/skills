# 游戏工程写作纪律（三条）

> 适用：`game-spec` / `game-code-forge` / `game-quality-gate` / `game-integrate` / `game-polish`。
> 三条都是**写文档与写代码时的口径约束**，不是流程步骤，不占阶段。
> 与 `engineering-constraints.md` 的分工：那份是通用开发约束（项目隔离/技术栈/密钥/追溯等 10 条），本文是游戏工程特有的三条写作口径。

---

## 1. 规则单一来源

**同一规则只允许一份实现。** 出现第二份（求解器、校验器、预览器、测试桩、审计脚本）时，先收敛成被双方 `import` 的模块，再加一条"两个入口结果一致"的断言。

反例（都真实发生过）：

- 求解器自写一遍合法性判定 → 改玩法只改了运行时 → 提示给出非法解，玩家信任一次就没了。
- 审计脚本与生成器各写一份 `runLen` / `blobPct` → 两边口径缓慢分叉，审计结论与生成结果对不上。
- 两个入口各写一份剪枝逻辑 → 改一处忘一处，两个入口的判定口径分叉。

**验法**：`grep` 关键函数名，第二处出现即视为欠债；或加断言"随机 N 个输入，两边输出完全相同"。

> 这条与"禁止硬编码"不同：硬编码管的是**数值**从哪来，这条管的是**规则**由谁实现。

---

## 2. 属性归属表

**写状态机之前，先写属性归属表：每个字段只允许一个 owner 写。**

| 字段 | owner | 谁可以读 | 典型双写事故 |
|---|---|---|---|
| 位置 / 坐标 | 逻辑层 | 渲染层 | 动画补间改了终值，逻辑按旧值判定 |
| 生命值 / 计数 | 逻辑层 | UI、特效 | UI 本地加减后回写，覆盖逻辑层结果 |
| 可见性 | 逻辑层 | 渲染层 | 用渲染层 depth 推导"能不能点" |
| 缩放 / 旋转 | 渲染层 | — | 逻辑层也参与，回正时机冲突 |

反例：动画补间把 `y` 直接改到终点，而逻辑层仍按旧 `y` 判定碰撞 → 视觉上已经落地，判定还在空中。
反例：`visible` 与 `interactive` 共用一个字段 → 淡出过程中仍可点击。

**判据**：任何字段出现第二个写入点，要么合并 owner，要么显式声明"渲染层只读"。写进 `TECH_DESIGN` 的状态机小节，评审时逐字段过。

---

## 3. 不变式优先

**先写"永远为真的句子"，再写验证清单。** 每条不变式必须对应至少一条断言，否则它只是文案。

```
不变式（任何时刻都成立）
  I1 任一元素只属于一个容器
  I2 容器内元素的相对顺序在压实前后不变
  I3 一次操作只改变一个容器的内容

验证清单（一条不变式至少一条断言）
  A1 随机 1000 个局面，断言 I1
  A2 移除元素后压实，断言相对顺序与 I2 一致
  A3 单次操作前后快照 diff，断言只命中一个容器
```

反例：验证清单写成"测了跳跃 / 落地 / 受伤"，全是功能名、没有一条恒等式——全通过也不代表系统一致。
反例：用"跑一遍没报错"当断言——什么都没发生也算通过（这就是静默假绿的通用形态）。

**判据**：拿一份验证清单去审，若找不出"恒等式"，说明它测的是功能覆盖，不是正确性。

> 配套问法：一条不变式如果被违反，哪个断言会红？答不出来，说明它还没进清单。
